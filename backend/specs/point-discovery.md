# 设备点位范围扫描（point-discovery）

> 与 [device-scan.md](device-scan.md)（局域网设备扫描发现）是**并列的两件事**，
> 不是同一篇的续。两者的支点相反，见 §1。两篇必须互相改，理由在 §12。

## 1. 这个功能是什么，不是什么

设备扫描解决的是"网段里有哪些 PLC"。设备建成之后，运维仍要手工录入每一个点位：
翻图纸、查寄存器表、逐条填地址/类型/标签。本功能在**设备地址页**加一个
「自动发现点位」按钮，对**一台已存在的设备**发起一次范围扫描，把读得到的地址与
当前值列出来，勾选后批量建成 `device_address` 行。

**必须先把它的性质说清楚，这决定了整个界面与文档的措辞：**

> 设备**不会告诉你**它有哪些点位。

除少数协议（OPC UA 的 Browse、ABB 的 RWS 信号表、DLT645 的数据标识字典）之外，
Modbus / S7 / 三菱 / FINS / CIP **都没有任何标准枚举手段**。所以本功能产出的是
**「该范围内读得到的地址清单」，是候选清单，不是点位表**：

- 非零的地址不一定有意义（标定表、计数器、别人的数据都可能）；
- 读得到 0 的地址可能恰恰是有效值（还没开机的状态、本来就应该为 0 的量）；
- 没列出来的地址既可能不存在，也可能只是**那一段请求被设备整体拒绝了**。

前端因此必须常驻显示插件声明的 `Description`（每个协议的局限不同），
并且**不做任何"这就是全部点位"的暗示**。

### 与 device-scan 的对照

| | device-scan | point-discovery（本篇） |
|---|---|---|
| 目标 | **网络**里的主机（网关规划、展开网段） | **一台已存在的设备**（由 deviceId 指定） |
| 一次 RPC | 一个目标 | 一整段地址范围 |
| 会话 | **无会话**，不持有跨调用资源 | **复用设备自己的采集会话** |
| 可取消 | 是（任务在内存里，Cancel 掐掉在飞探测） | **否**（同步 RPC，插件侧没有"取一部分"的入口） |
| 谁负责读取与降级 | 网关只管规划，prober 自己拨号 | **插件**（对半降级、错误分类） |
| 结果 | 一批 `DiscoveredDevice` | 一批 `DiscoveredPoint` + 三个计数 + 两个标志 |
| 失败语义 | 逐目标失败不中断整批 | 连接类错误**中止**并返回部分结果 |

*（2026-09 更新，与 [device-scan.md](device-scan.md) 同步维护。）*

## 2. 总体架构

```
前端 设备地址页
  │  ① GET  /deviceScan/pointCapability?protocolName=X     ← 能力（按钮是否可用）
  │  ② POST /deviceScan/discoverPoints {deviceId, options} ← 同步，最坏 ~9s
  │  ③ POST /deviceScan/createAddresses {deviceId, items}  ← 批量建点，逐条失败不中断
  ▼
DeviceScanService（service/devicePointScanService.go）
  │  ② 从 device 行取 protocolJson（**不采信客户端**）→ PointScanSource.DiscoverPoints
  │  ③ 逐行校验 + 库内/批内双重去重 + 整体事务
  ▼
pluginhost.Manager.DiscoverPoints(ctx, protocol, protocolJSON, options)
  │  超时 = min(插件声明, 7000ms) + 2s   ← 见 §4
  │  每次现算能力，**不建缓存表**（见 §12）
  ▼
pluginwire：method = "discoverPoints"，载荷 JSON
  ▼
driversdk（插件进程内 handleDiscoverPoints）
  │  选会话（§5 的回退表）→ 复用 or 临时实例
  │  finder(req) 按块调用 req.Session.Do，**块间释放锁**（§6）
  ▼
协议实现（如 modbusdrv.ScanPoints）
     取驱动内部 client 与 cfg → 分块 → 对半降级 → 错误分类
```

关键分工：**网关只做三件事** —— 把能力声明给前端、把请求发给对的进程、给这次
同步 RPC 定超时。扫描怎么读、怎么降级、值怎么渲染，全部是插件的事。

## 3. 能力声明（插件侧）

```go
// driversdk.Meta.Protocols[] 里
{Name: "ModBus.TCP", PointDiscovery: modbusdrv.PointDiscovery()}
```

| 字段 | 说明 |
|---|---|
| `Title` | 弹窗标题。必填。 |
| `Description` | **用户理解本功能性质的主要来源**（"我们列出的是读得到的地址"）。应写清该协议的局限。 |
| `FormJSON` | 扫描参数表单（form-create schema）。用户填的内容原样透给 finder。 |
| `DefaultCommonDataType` | 结果里类型的默认值，必须是该协议 **`TypeMap` 的 key**（通用类型名，如 `Word`）。写成内部裸名（`word`）会被启动期校验拒掉。 |
| `MaxBudgetMs` | **整段扫描硬预算**，取值 `[500, 30000]`。注意网关还会再钳一道（§4）。 |
| `MaxPoints` | 单次最多返回多少点位，取值 `[1, 20000]`。达到即停止并置 `truncated`。 |

**与 `Discovery` 的关键不对称：串口协议可以、且应当声明 `PointDiscovery`。**

`Discovery` 的目标是"网段里的一个 IP"，与串口无关，因此串口声明它会被拒；
而点位扫描的目标是**一台已存在的设备**，串口设备同样有"它有哪些点位"这个问题，
而且串口恰恰是会话复用最重要的场景（§5）。这两个校验函数在 `driversdk/meta.go`
里**刻意分开写**，就是为了让这条差异活下来 —— 合并之后它会变成两个 `if` 之间的
微妙差别，下一个人只会看到"同样是扫描能力，为什么一个禁串口一个不禁"。

实现放在 `driversdk.Capabilities.PointFinders`（见 §7），
声明了却漏配 finder ⇒ **插件启动即失败**。

### "能声明"不等于"必须声明"——两种合法的少声明

上面的不对称说的是**允许**。实际上有两种情况，插件应当**只给一部分协议**声明它：

- **同一个插件里有还没验证过会话复用的传输形态。** FINS 插件刻意只给
  `Omron.FINS.UDP` 与 `Omron.FINS.TCP` 声明点扫，串口与 Host Link over TCP 不声明
  —— 后者连的是串口服务器，会话复用路径（`finsDriver.matchConfig` 只为串口而设）
  与 Host Link 的帧格式都没有真机验证过。**能力一旦声明出去前端就会出现按钮**，
  而按下去的结果没人验证过。验证之后再补，只需在 `meta()` 里加一行。

  反过来，**当那条路径已经实现、且已在别的入口上被真机使用时，串口就应当声明它**。
  `Mitsubishi.MC.Serial` 就是这么定的：MC 驱动实现了 `driver.ConnectionMatcher`
  （`mcDriver.matchConfig` 只为串口而设），「测试连接」走的正是同一条复用路径，
  而点扫复用的 4C 帧传输就是采集路径上一直在用的那一份实现。差别不在"串口能不能扫"，
  在**那条路有没有可依据的实现**。代价要如实写进 `PointDiscoverySpec.Description`：
  9600bps 上大范围扫描会经常落在 `Incomplete` 上（网关侧 7000ms 的钳制，见 §4）。
- **契约形状根本落不下来，或没有可依据的实现。** `Omron.CIP` 只有设备扫描、
  没有点扫：CIP 的点位是**符号名**（`MotorSpeed`、`Recipe.Setpoint`、`Array[3]`），
  不是可枚举的地址空间，"从某个字起扫 N 个字"无处安放；要枚举标签只能走另一条
  服务（CIP Symbol Object，类 0x6B），而**欧姆龙 NJ/NX 那套对象模型在本仓库里
  没有可依据的实现**（其变量访问走的是它自己的对象模型，而对真机的实例属性表
  从来没有核过）。**不做而不是猜着做**：写错的表现是返回一份空清单，
  用户会从"一个标签都没有"得出"这台设备没有点位"的结论，正是本篇通篇在防的
  那类错误。这条由 `driversrc/omroncip/main_test.go` 的 `TestNoPointDiscovery` 钉住。
  **注意别把 `Rockwell.CIP` 当成反例**：同一个类号、同一条服务，它**做了**点扫，
  见下面第三条 —— 差别不在协议名，在**有没有可依据的实现**。

### 第三种形态：原生枚举（`Rockwell.CIP`）

上面两条讲的是"少声明"，这一条讲的是**另一种实现形态**（不是少声明，而是
"扫"这个字在这里根本不成立）：

| | Modbus / S7 / FINS | Rockwell.CIP |
|---|---|---|
| 扫什么 | 一段**地址范围** | 设备**自报的标签表**（CIP Symbol Object，类 0x6B） |
| 产出 | "这段里哪些地址读得到"（候选清单） | **标签名本身** + 设备给的类型码 |
| 协议 | 逐块读，`Session.Do` 每块一次 | 一次调用枚举完整张表 |
| 采样值 | 有 | **没有**（多读一遍值等于把请求数翻倍） |
| 超预算 | 返回部分结果 + `Incomplete` | **返回错误**（见下） |

它落在这个框架预留给"原生枚举"的位置上（见 `driversdk.FindPointsRequest.Session`
的注释："原生枚举类实现根本不需要读设备……这条留白就是本框架为它们留的位置"），
只有一处不同：**它仍然需要设备**，所以照样走 `Session`。

四处必须记住的实现事实（完整说明在
[`driversrc/rockwellcip/rockwellcipdrv/pointscan.go`](../driversrc/rockwellcip/rockwellcipdrv/pointscan.go)
的文件头）：

1. **布局不猜，用库。** 请求构造与应答解码直接复用本仓库既有依赖
   `goindustrial` 的 `cip/symbol.go` 与 `Client.ListTags` —— 而 Omron.CIP 之所以
   不做点扫，正是因为当初**没有**这样一份可依据的实现。这条差别值得写在两个插件的
   注释里，否则下一个人会以为"S7 能扫、CIP 也能扫"是随手加上的。
2. **枚举是整只对象的操作，超预算时拿不到部分结果。** 于是本 finder **报错**
   而不是返回空清单 + `Incomplete` —— 后者会渲染成一张 0 行的表，而用户会从
   "一个标签都没有"得出"这台设备没有点位"，正是本篇通篇在防的那类误读。
   注意与**截断**的不对称：达到 `MaxPoints` 时枚举其实已经跑完了，只是映射停手，
   那种情况**是**有部分结果的。
3. **失败模式是"挂住"，所以必须自己兜 deadline。** 库的 TCP 传输不设读超时、
   也不看 ctx，一个"TCP 通、CIP 不应答"的设备会让枚举永久阻塞。finder 因此用
   goroutine + select 兜住，并依赖调用方收尾时的 `drv.Close()` 关掉套接字、
   把阻塞的读解开（这条依赖由 `client_test.go` 的 `TestClientListTagsUnblocksOnClose` 钉住）。
4. **不读采样值 ⇒ 结果级的 `AssumedCommonDataType` 留空**，这是一条**跨端约定**：
   前端据它为空隐藏「显示 0 值」开关与零值统计，并换一套"列出/跳过"的措辞。
   每个点位的类型改由 `DiscoveredPoint.CommonDataType` 逐点给出（见 §8 末）。

### 第四种形态：Browse 原生枚举（`OPC.UA`）

与 Rockwell 同属"原生枚举"这一族，**但三处关键差别**让它不能照抄那一份
（完整说明在
[`driversrc/opcua/opcuadrv/pointscan.go`](../driversrc/opcua/opcuadrv/pointscan.go)
的文件头）：

| | Rockwell.CIP | OPC.UA |
|---|---|---|
| 枚举手段 | CIP Symbol Object（类 0x6B），**一次列完** | Browse 地址空间，**按层推进** |
| 产出 | 平铺的标签名 + 类型码 | **树**：只有变量是点位，对象/文件夹只用于下行 |
| 分块 | 无（一次调用） | 有（一块一次 `Session.Do`，见 §6） |
| 采样值 | 没有 | **没有**（同一个选择，理由也一样） |
| 超预算 | **返回错误**（拿不到部分结果） | **部分结果 + `Incomplete`**（能拿到） |

四处必须记住的实现事实：

1. **"没有部分结果"这条在 OPC UA 不成立，所以不能照抄那个报错。** 按层推进的
   遍历停在哪儿、手上就有多少，正好落进契约第 1 条要求的形态。把 Rockwell
   那个"报错"搬过来，会让用户丢掉几百个已经问出来的点位。
2. **瓶颈是请求数，不是节点数 —— 所以 Browse 与属性读取都必须批量。**
   `ua.BrowseRequest.NodesToBrowse` 是切片，一次能问一整块；
   `DataType` 属性按 `MaxBatch` 切子批批量读。退化成"一节点一请求"不会报任何错，
   只是扫描会在预算耗尽时停在半程 —— 症状是"清单莫名其妙断了一半"。
   另外**不要用库的 `Node.References`**：它一次只发一个 `BrowseDescription`，
   且收续页时只读 `results[0]`，多节点时其余节点的续页会被**静默丢掉**。
3. **类型要沿逆 `HasSubtype` 上溯**：节点的 `DataType` 属性是**另一个节点的 NodeID**，
   自定义枚举与厂商结构体都活在服务器自己的命名空间里。上溯**一层一个
   `BrowseRequest`** 覆盖该层全部待解析类型（不是一类型一请求），并有层数上限；
   解析不出来就跳过并计入"未列出"。
4. **地址往返在这里的理由与 Modbus/S7 **不同**，别照抄那一套论证。**
   `opcuaDriver.Read` 对 `*parseError` 与 `ua.StatusCode` 都是**逐点** Quality=0
   继续 —— 这一点现在 Modbus/S7/FINS/MC 也一样了（见 §8：解析不出的地址在规划前
   就被拆出去），但**它们防的东西不同**。那四个防的是"这个地址根本不存在"，
   一个点位没有值而已。真正的危险是**解析到另一个节点** —— `parseAddress` 把任何含 `/` 的串当浏览路径，于是一条
   `ns=2;s=Room1/Temp` 会被解析成一条**别的**路径；只要服务器上恰好有一条同名
   路径，这个点位就会永远采到另一个节点的值，而那条曲线看起来完全合理。
   因此渲染出来的每一个地址都要**再解析回来逐段比对**，比对不过就不产出它
   （见 §8 的补充）。

### 第五种形态：字典枚举**且带采样值**（`DLT645.Serial` / `DLT645.TCP`）

与前四种都不同的一处：**它既从一份已知清单里枚举，又读采样值。**

| | Rockwell / OPC UA | DLT645 |
|---|---|---|
| 点位从哪来 | 设备自报（CIP 标签表 / Browse 地址空间） | **协议自带的数据标识字典**（本仓库冻了 2007 版 44 条、1997 版 18 条，见 `dlt645drv/dictionary.go`） |
| 每个点位的类型 | 设备自报（CIP 类型码 / `DataType` 属性） | **由数据标识本身决定**（长度/小数位/符号/编码都在 DI 里，见 `dlt645drv/decode.go`） |
| 采样值 | 没有（多读一遍值等于把请求数翻倍） | **有**："读一遍"既是判定这块表有没有该数据标识的手段，也顺带得到了值 |
| 结果级 `AssumedCommonDataType` | 留空 | **非空**（`Float`） |

**于是 §8 那个标题「逐点类型（原生枚举专用）」与 `driver/pointDiscovery.go` 里
「只有原生枚举类协议会填它」，边界要这样读**：逐点类型不是"原生枚举"的特权，而是
「**同一个协议里每个点位的类型可以不同**」时唯一说得通的表达 —— 读一段地址的协议
整段共用一个假设类型（所以不需要它），而 645 **既有不同的类型、又有采样值**，
两个字段于是同时非空。

**结果级那个非空的值不是"为了保证能读而假设的类型"。** 对 645 而言类型**从不影响
读取**（长度、小数位、符号、编码全在数据标识里），它在这里的实际作用是**告诉前端
"本次结果带采样值"** —— 前端据它显示「显示 0 值」开关、并换用「读得到/读不到」的措辞
（见 `frontend/.../PointDiscoveryDialog.vue` 的 `sampled`）。留空会隐藏那枚开关，
而 645 的零值是常态（未接线相的电流就是 0），用户会因此看不到一整类点位。

四处必须记住的实现事实：

1. **不做「读到第一个读不到就停」。** 数据标识字典**不是连续地址空间**：一块表
   完全可能实现了高位的某个电力参量、而没有低位的另一个。照抄 FINS/MC 那条捷径
   会让清单从第一个空洞处静默截断。
2. **不做请求数上限。** 降级树是有界的（每块最多一次批量帧 + `maxDIsPerRead` 次单读，
   不是 S7/MC 的满二叉树 `2n-1`），不需要 S7 那样的 `pointScanMaxRequests`。
3. **1997 版每帧只能带一个数据标识**（与 `plan.go` 的 `buildPlan` 逐字同一条规则）。
   照抄 `maxDIsPerRead` 会让单帧数据域超过 `maxDataLen1997`，而 `parseAt` 对超长的
   `L` 直接判"不是帧头"——设备的**合法应答永远解析不出来**，症状是每一帧都超时
   （看起来像"设备不在"，而不是"参数配错了"）。
4. **成帧打包要先核对数据域总长。** 回显校验只保证"这一项的标识对"，不保证
   "这一项的数据落在正确的位置"：设备少回一项的数据时，后面每一项的窗口都会整体
   前移，解出的是**看似合理实为别处**的值，而它会被算成"读到了"。总长不足是这一
   情形的必要条件，因此拿它当判据降级为逐个重读。**这一条是 645 独有的**（它一帧
   打包多个数据标识，且各项长度不同）。

还有一处**有意偏离 §6「连接类错误必须中止」**：645 的「静默」有歧义 —— 规范规定
设备对不支持的数据标识回异常应答（0xD1），但老表与廉价表常常**干脆不答**。因此一个
数据标识静默（超时）之后，先**复探一次**各版本最普遍实现的数据标识（与 Ping 用的是
同一个）把"设备掉线"排除掉：通了 ⇒ 该数据标识记「读不到」并继续；不通 ⇒ 中止。
这与 FINS「结束码错误也算设备」是同一类取舍（**拒绝应答也证明对面在**）。
**它成立的前提（静默 == 这块表没有这个 DI）无法从仓库验证，需要真机确认**；若真机上
不支持的数据标识其实都会回异常应答，这条分支就是死代码（无害）。

实现见 [../driversrc/dlt645/dlt645drv/pointscan.go](../driversrc/dlt645/dlt645drv/pointscan.go)。

**类型映射只能是 Kind 等价，这不是将就**：OPC UA 的 `int32` / `uint64` /
`byteString` 在本系统里没有**同名**的通用类型（它们只有内部裸名，没有通用名入口），
而 `TypeMap` 的键集被黄金基线钉死（`pluginhost/testdata/parity/typemap/opcua.json`
只能由已移除的内置实现重新生成）。于是 Int32→Long、UInt64→DWord、SByte→Char、
ByteString→String。这在行为上正确：本协议**从不做字节级解码**（服务器返回原生值，
`DataType` 只决定 Kind），而这几对的 Kind 完全相同。名字上的差异由该行的 `Note`
补上（"OPC UA 基础类型 Int32"）—— 原生枚举下前端正是把 `Note` 渲染在「采样值」
那一列，那是用户唯一能看出差异的地方。

## 4. 预算与超时（与 `main.go` 的 10s 互锁）

这是本篇最需要小心的一处**跨文件耦合**。

```
main.go          srv.Shutdown(ctx)，ctx 超时 10s
                 ↓ http.Server.Shutdown **会等所有在飞 handler 跑完**
pluginhost       discoverPoints 的 RPC 超时
                 = min(插件声明的 MaxBudgetMs, pointScanGatewayBudgetCapMs = 7000ms)
                   + pointScanRPCGrace = 2s
                 ⇒ 最坏 9s < 10s
```

**超过 10s 的后果不是"报个错"**：`Shutdown` 会卡满整个宽限期再打一条
`context deadline exceeded`。在 Windows 服务管理器 / systemd 里，这表现为
**"网关停不掉"**，运维只能强杀进程。而 `device-scan` 没有这个问题 ——
那边是异步任务（登记即返回），扫描在后台 goroutine 上跑。

**因此 `pointScanGatewayBudgetCapMs` 与 `main.go` 的 10s 必须人工对齐：
改一个必须同时改另一个。** 可执行的证据在
`pluginhost/pointdiscovery_test.go` 的 `TestBudgetWithinGatewayCap`：它断言
`cap + grace < 10s`，把这条耦合变成一条会红的测试（这也是仓库里"两处默认值人工
对齐"的既有约定，见 `devicescan/engine.go` 与 `pluginhost/manager.go` 的同类常量）。

插件侧拿到的就是**被钳过的那个值**（`DiscoverPointsParams.BudgetMs`），
因此"插件是必须不超时的那一方"这条不变量依然成立，只是两边用的是同一个上限。

代价：**RTU 的大范围扫描会被截断**（9600bps 上 7000ms 大约只能扫两千多个寄存器）。
因此 `Incomplete` 必须在界面上显式显示出来，待遇同 device-scan 的 `Truncated`。

## 5. 会话复用与回退表（最关键的一节）

点位扫描必须读那台设备，而**在独占串口上，唯一能读的就是正在采集的那个会话**。
但这不等于"总是复用" —— 回落的规则与 `Ping` 完全不同：

| 情形 | 串口协议 | TCP 协议 |
|---|---|---|
| 有会话且 `MatchConnection` 命中 | **复用**（拿锁预算 ≤ 5s） | 不会命中（Modbus TCP 未实现 `ConnectionMatcher`），等同下一行 |
| 有会话但不是本次要连的那条 | **报错，不回退** | 走临时实例（第二个 socket 无害） |
| 该协议**一个会话都没有** | 走临时实例（端口按定义是空的） | 走临时实例 |
| 有会话、命中但锁不到 | 报「设备正忙」，**不回退** | 不适用 |

### 为什么串口那两格不能回退

`pingViaSession` 的取舍是"拿不到锁就跳过、回落临时实例"。那对 ping 是对的 ——
不能让"测 COM2 时因为 COM1 在忙"变成一次假失败。但**一次几十秒的长扫描回落成
临时实例会抢占串口的长时句柄**：扫描持有它期间，采集侧下一次重连报
`Access is denied` 并进入退避窗口。用户看到的现象是**"点一次扫描把设备打成离线"**。

只有"该协议一个会话都没有"才回落，因为那时端口按定义是空的 —— 打开它不可能
抢走任何人的句柄。

判据需要知道"这个协议是不是串口的"，SDK 在 `serve()` 启动期照 `probeBudgets`
再算一张 `serialProtocols` 表（来自 `Meta.Protocols[].SerialExclusive`）。

### 会话复用的机制：`SessionAccess.Do`

finder 不直接拿 `driver.Driver`，而是拿到一个 `SessionAccess`：

```go
type SessionAccess interface {
    Do(fn func(drv driver.Driver) error) error
}
```

**为什么不能把驱动的 `Read` 直接给 finder** —— 三条理由，每条都能致命：

1. **驱动自己的 `Read` 不是为扫描设计的**。它读设备的 cfg 做区间规划：
   Modbus 的 `groupAddrsByFC` / `CalcReadRanges` 都以"配置模式的
   `startAddress`/`functionCode`"优先。配置模式下扫描按功能区生成的地址会被
   当保持寄存器读、区间规划还会因为 `addr < StartAddress` 直接报错，
   而解析是越界安全的 —— **不 panic、不报错，只是静默给出错位的值**。
   更糟的是这些地址一旦建成 `device_address`，那个点位会**永远取到别处的数据**
   （在时序库里表现为一条完全合理的曲线，看不出任何异常），而错在哪一处无从追。
   所以点扫实现必须**先拒绝配置模式的设备**（见 §9）。
2. **会话是共享资源**。`Do` 每次进入才取锁、`fn` 返回即放锁，扫描因此可以在
   块与块之间把锁让出去（§6）。
3. **复用路径上那个实例正在采集**。它是采集引擎持有的对象，
   `fn` 内部**不得**调用 `drv.Close` / `drv.Connect`。

这一改还顺手消掉三个坑：不必合成 `po.DeviceAddress`（`filterAddrsByMap` 按 ID
建 map，**ID 重复会静默丢地址**）；不污染采集侧的 `planCache`
（`RangeCacheMaxEntries = 32`，溢出即清空重建）；而且**原生枚举**类实现
（不需要读设备的那种）根本不用调 `Do`，同一个接口就能容纳。

## 6. 锁纪律：块间必须让锁

finder **不能**用一次 `Do` 覆盖整段扫描。一次 `Read` 覆盖整批点位、在 9600bps 上
可能跑到十几秒，而那期间采集侧读不到这台设备 —— 与 `pingSessionBudget` 是同一个
理由。

正确形态是**主循环每块一次 `Do`**：

```
for 每块 {
    if 已过 deadline { Incomplete = true; 收工 }
    sess.Do(func(drv) error {
        s := 取驱动内部 client 与 cfg      // 每次现取，别缓存
        walk(块起点, 块长)                  // 块内做对半降级
    })
}
```

三条实现细节：

- **每次 `Do` 都可能换一个实例**（热刷新会重建驱动、重连会换 client），
  所以驱动指针不能跨 `Do` 缓存 —— 缓存下来的读的是一个已经 `Close` 的句柄。
- `sessionAccess.Do` 的等待预算取 `min(剩余时间, 5s)`：整段扫描已经跑掉的时间
  必须从这次等待里扣掉，否则最后一块会拿着整个预算去等锁。
- 拿不到锁 ⇒ 立刻回「设备正忙：采集正在读取这台设备，请先停用该设备再扫描」，
  **不无限等**。无限等会撞网关侧 RPC 超时并累积插件卡死计数，
  连续几次会把整个插件进程连同它下面所有协议、所有设备一起重启。

回归见 `driversdk/pointscan_test.go` 的
`TestDiscoverPointsReleasesLockBetweenChunks`（闸门驱动 + 在块之间插一次并发
`read`，断言它能拿到锁）。

### 块内降级：把"地址不存在"与"设备掉线"分开

整段读失败时对半降级（整段 → 对半 → … → 单点），因为设备对**含空洞的区间**会
整段拒绝，不拆到单点就问不出"哪几个地址真的不存在"。块内还有两条不变量：

- **对半降级必须有一条请求数上限**，不能只靠 `deadline`。对一段整段都读不到的
  地址，降级会退化成一棵满二叉树（最坏 `2n-1` 次请求）；只在循环里判时间，
  耗时就会随网络延迟漂移 —— 本地 PLC 上几百次请求可能只要几百毫秒（于是照样
  跑完），慢链路又跑不完。S7 的 `pointScanMaxRequests` 就是这道上界，
  触顶置 `incomplete` 并返回已得结果。
- **连接类错误必须中止，绝不能被记成"地址不存在"。** 把设备掉线记成"这里没有
  点位"，用户会从一份几乎全是空的清单里得出与事实完全相反的结论，而采集侧此时
  已经在重连了 —— 两边的结论互相矛盾。

### 一种比"对半降级"更省的做法：连续地址空间可以"读到末尾就停"

FINS 的内存区是**连续的**（DM 从 0 起、CIO 从 0 起，各自一整片），因此"某个字
不存在"只可能是"已经越过这个区的末尾"。那里因此不需要把降级做完整棵树：

> 单点读不到 ⇒ 记下"第一个读不到的下标"，**它之后的地址一律直接记为读不到**，
> 不再逐个去问。

反过来若继续逐点去问，一次 `count` 填大了的扫描会在末尾之后发出几百个必然失败的
请求，最后撞上请求数上限、给用户一份标着"未扫完"的结果 —— 而它其实早就扫完了。

这条推断成立的前提正是上一节那条排除：**可恢复的节点/PLC 状态错误不能算地址问题**。
少了那边的排除，一次"目标节点忙"就会把清单从中间截断。

**这不是通用做法，只在地址空间连续时成立。** 实现里的"对半降级"仍然保留：
它负责把可读前缀摘出来与定位边界，只是找到第一个读不到的点之后不再往右走。
回归：`finsdrv/pointscan_test.go` 的 `TestScanPointsStopsAtAreaEnd`、
`TestScanPointsStopsAtFirstUnreadable`、`TestScanPointsStopsAtRequestQuota`。

**MC 是这条"不通用"的具体反例。** 同一个插件里，`D/R/ZR/M/L` 是单片连续的，
而 **`X`/`Y`（物理 I/O，按槽位分配）与 `B`/`W`（链接区，按模块分配）中段可以有空洞**
—— 没插模块的槽位读不到，它后面的槽位完全可能是好的。照抄那条捷径的后果是
清单**从空洞处断掉**，而 `Truncated`/`Incomplete` 都不置位：用户看到一份短了一截、
却看不出任何异常的清单。因此 MC 的实现里有一张显式的
「是否单片连续」表（`mitsubishi` 的 `pointScanOptions.contiguous`），
非连续的软元件上单点失败**不**返回 `hitEnd`、继续降级右子树，
最坏 `2n-1` 次请求 —— 而那正是请求数上限本来就要兜住的形态。
回归：`mitsubishidrv/pointscan_test.go` 的 `TestScanPointsNonContiguousKeepsScanning`
与 `TestContiguousOnlyForSolidAreas`。

第二条的**判定手段随协议而异**，这是最容易踩坑的地方：

| 协议 | 怎么判"地址不存在" |
|---|---|
| Modbus | 结构化异常码：`goburrow.ModbusError.ExceptionCode` 是 `IllegalFunction` / `IllegalDataAddress`，可以 `errors.As` |
| S7 | **只能靠字符串匹配**：gos7 把 PLC 回的项级错误码经 `CPUError`/`ErrorText` 翻译成一句人话，一路都是 `fmt.Errorf` 的裸字符串，没有可 `errors.As` 的类型。此时应当维护一张**只收"明确表示地址/对象不存在"**的白名单，其余（含连接错误）一律中止 |
| FINS | 结束码是两字节（高字节主码 + 低字节细分），**按主码排除**：`0x01` 本机节点错误 / `0x02` 目标节点错误（不在网络上、无此节点、**忙**、响应超时）/ `0x03` 控制器错误，这三类是**可恢复的节点/设备状态**，与地址无关，一律中止；其余当作地址问题。（`0x00` 走不到这里 —— 结束码为 0 已是成功。） |
| Rockwell（原生枚举） | **不适用**：没有"这个地址读不到"这回事。判据是两条各自独立的门槛 —— ① 名字过不过 `ParseRockwellAddress`（硬门槛：不过就是建一个**永远没有值**的点位，采集侧会把它摘出计划、标 `QualityBadAddress`；`describeSymbol` 因此直接跳过它）；② 类型能不能映射成通用类型名（软处理，映射不了就跳过）。跳过的标签计入 `Unreadable`，而它在界面上叫**「未列出」**：原因是类型/名字，与地址是否存在无关 |
| MC | **白名单，而且只能白名单**：MC 的结束码是单个 16 位值，**没有 FINS 那种"高字节是主码、可以成组排除"的结构**，而且同一个语义在不同家族上还是两个码值 —— QnA 兼容那一套写 `0xC0xx`（`0xC051` 设备指定错误、`0xC056` 地址范围外、`0xC05B` 点数指定错误），iQ 那一套写 `0x4xxx`（`0x4031` 指定软元件编号超出范围，**与上面两条语义完全相同**；真机实测：`D`/`W` 越过已配置范围、以及文件寄存器区为空时的任何 `ZR`/`R` 地址都回它）。`0xC05B` 看着像"我们的请求形状错了"，但扫描期间子命令与软元件恒定、只有范围在变，而拆到单点后点数恒为 1 必然能读 —— 归进地址问题只会让请求数变多（对数级），不会截断清单，收益是"老型号的单请求上限比配置值小"这类情形能自愈。**`0xC0EF`（通信错误 / PLC 忙）明确不收**：它是可恢复的设备状态，拿它做推断会让一次偶然的忙把清单从中间截断。回归：`mitsubishidrv/pointscan_test.go` 的 `TestIsAddressEndCode`（白名单与黑名单各断言一遍）、`TestScanPointsTreatsDeviceRangeEndCodeAsAddressEnd` 与 `TestScanPointsAbortsOnBusyEndCode` |

**码值不齐是这条路最容易出的事，而它的表现不是"扫得慢"、是"扫不了"。**
白名单按**码值**列，而同一个语义在不同 CPU 家族上可以是两个值（MC 的 `0xC0xx` 与
`0x4xxx` 就是两套码表）—— 漏掉一个的表现是把"这里没有点位"报成"扫描失败"：
第一次在真机上暴露，就是一台没配置文件寄存器的 PLC 上扫 `ZR`，每个地址都回
`0x4031`，而白名单只认 `0xC0xx`，于是整次扫描中止。**收的时候按语义收**
（"这一段地址读不到"），别按某一台设备的码表收；每个码值都要有实测或手册出处。

S7 那侧的白名单写法值得抄一条取舍：**把"兜底桶"也收进来是有意的** ——
能拿到项级错误码就说明 PLC 确实应答了（连接是活的），此时剩余的歧义只是
"这个码是什么意思"；而保守地判成中止，会让 S7-1200/1500 上一份本来能扫出东西的
清单直接变成一个错误。真正的连接失败走的是另一条路（`net.Error` / `io.EOF`），
过不了白名单。回归见 `s7drv/pointscan_test.go` 的 `TestIsUnreadableAddrErr`
（白名单与黑名单逐条断言）。

## 7. finder 线协议与契约

### 线协议

`pluginwire.MethodDiscoverPoints = "discoverPoints"`。

```go
type DiscoverPointsParams struct {
    Protocol     string `json:"protocol"`      // Meta.Protocols[].Name
    ProtocolJSON string `json:"protocolJson"`  // 网关从 device 行取，不采信客户端
    Options      string `json:"options,omitempty"` // 用 string 而非 RawMessage，理由同 ProbeParams
    BudgetMs     int    `json:"budgetMs,omitempty"`
}
type DiscoverPointsReply = driver.PointScanResult
```

**只走 JSON**（不实现 `pluginwire.BinaryEncoder`）：点扫是冷路径，
一次扫描最多一次调用，二进制编码省不下任何可感知的东西，而"意外实现
`BinaryEncoder` 导致静默换编码"是 `pluginwire` 注释里警示过的失败模式。
`TestDiscoverPointsParamsStayJSON` 钉住这条。

### 插件侧的五条契约

1. **必须在 `req.Budget` 内返回**。超预算时的正确做法是**带上已完成的部分结果
   正常返回**并把 `Incomplete` 置位，不是返回 error。
2. **空结果不是错误**。"这个范围里一个地址都读不到"是正常答案，
   报 error 会让用户以为功能坏了。
3. `error` 只用于"这次扫描根本没法进行"（选项解析不出来、设备处于配置模式、
   连接直接断开）。中止时**把已经拿到的部分结果一起返回**。
4. **不得 `Close`/`Connect` `req.Session` 里的驱动**。
5. panic 会被 `handle` 的 recover 兜住并降级成一次 RPC 错误，
   但那次扫描白做了 —— 边界自己判。

### `Capabilities`：第三种能力已经在路上

```go
driversdk.Main(factories, meta, driversdk.Capabilities{
    Probers:      probers(),      // 局域网扫描（Discovery）
    PointFinders: finders(),      // 点位扫描（PointDiscovery）
})
```

第三个参数由裸 `Probers` 改成结构体，是因为**第三种能力（原生枚举）已经可以
预见**，而每加一种能力就要把改动在 `Main` / `Serve` / `ServeConn` 三个入口重复
一遍、并在仓库内 25 处调用点（9 个插件 main + 16 处测试）各改一次。
字段零值即"没有这个能力"。

## 8. 地址写法：每个协议选自己那一种，但都必须能往返

**共同的不变量只有一条**：生成的地址串必须能被该协议自己的解析器反向解析回
**同一个位置**。脱离这条不变量，其余全是协议各自的选择 —— Modbus 选 IEC 风格
（理由见下），S7 选 `DB1.DBW100` / `DB1.DBX0.1` / `M0.1` / `MW100`（与前端
`addressSyntax.js` 里 s7 规格的示例一致，S7 的往返测试是 `s7drv/pointscan_test.go`
的 `TestPointNameRoundTrip`）。

### Modbus 为什么必须是 `%MW/%IW/%MX/%IX`

传统写法在下面三处都会坏（都是实测行为）：

| 格式 | 问题 |
|---|---|
| 满量程 `%MW65535` | 传统写法是 `"465536"`（`4` + 6 位 1-based `65536`），`ParseUint(s[1:], 10, 16)` 解不出 65536 ⇒ **整个串解析不出来** ⇒ 该点位从区间规划里被摘出、永远采不到值，只报一条「地址无效」（修复前是 `CalcReadRanges` 报错 ⇒ 整台设备的采集全部失败 + 误报断联） |
| 差一 | 传统写法是 1-based，`"465535"` 指的是偏移 **65534** 而不是 65535 |
| 功能区丢失 | 线圈区的偏移 `10000` 写成 5 位是 `"10000"`，它落进**纯数字分支**（`functionCode = 0`，未知）而不是线圈区，读它的 FC 由设备的 `cfg.FunctionCode` 决定 —— 也就是被当成保持寄存器读 |
| **IEC `%MW100`** | **无问题**：`tryIECFormat` 纯 0-based，`ParseUint(numStr, 10, 16)` 恰好覆盖 uint16 满量程 |

| 界面选项 | FC | 生成 | 还原 |
|---|---|---|---|
| 保持寄存器 | 3 | `%MW<off>` | (3, off) |
| 输入寄存器 | 4 | `%IW<off>` | (4, off) |
| 线圈 | 1 | `%MX<off>` | (1, off) |
| 离散输入 | 2 | `%IX<off>` | (2, off) |

**`%MW100` 已经是前端与 i18n 里明示支持的写法**，且 0-based 与扫描表单的
`startAddress` 同基准，不会出现差一错误。

**这条不只是"好看"**：一个解析不出来的地址写进 `device_address` 之后，这个点位永远
采不到值、只会报一条「地址无效」，运维得去改配置才恢复。

> 这条后果**曾经严重得多**，值得记下来免得被改回去：那时 `CalcReadRanges`
> 全量解析、遇第一个非法地址就返回 error，`Read` 于是整个失败 —— 采集侧看到的只是
> 一个 `err`，便把它当成**设备故障**（`incError` + `reportState(false)`），连续三轮
> 落一条**断联**报警并推通知，而设备全程在线（`IsConnected()` 为真，重连逻辑根本
> 不启动），`forEachBatch` 还会把坏地址之后的批次一起跳过。**一个点位把整台设备
> 拖垮，还把运维引向"查网络"这个完全无关的方向。** 现在六个区间规划器
> （modbus / s7 / fins / mitsubishi / Omron.CIP / Rockwell.CIP）都在规划前把解析
> 不出的地址拆出去，`Read` 不报错，只让这一个点位报坏（回归见各包 `badaddr_test.go`）。

所以结果里的**地址列在前端只读** —— 点扫产出的是候选清单，不该让用户顺手改成一份
自家解析器认不出的写法。往返由 `modbusdrv/pointscan_test.go` 的 `TestPointNameRoundTrip`
钉住（0 / 1 / 9999 / 10000 / 32767 / 65534 / 65535 × 四个功能区）。

### FINS 用 `D100` / `CIO100` / `W100` / `H100`，位地址补零到两位

区前缀取自前端 `addressSyntax.js` 里 fins 规格的示例（`D100`、`CIO0.00`、`W1.2`），
DM 用短写 `D` 而不是 `DM` —— 两者的解析结果相同，但 `D100` 是手册与现场习惯里
更常见的写法。位地址写成 `D100.05`（补零到两位，前端示例 `CIO0.00` 也是这个形态）。

**一处分寸必须守住**：位模式下一个字展开成 16 个点位，对半降级会把起点切到字中间
（例如从第 5 位起扫 8 个位）。此时字区间**只能按 `start/16` 与 `(start+n-1)/16`
算**，用 `idx × 每点位字数` 会落到别的字上 —— 读到的是**别处**的数据，而值看着
完全合理，用户不会发现。这条由 `finsdrv/pointscan_test.go` 的
`TestWordSpanCoversEveryPoint` 逐组合钉住。

往返由同文件的 `TestPointNameRoundTrip` 钉住（4 个内存区 × 3 种粒度 × 5 个起点，
含 65530 这种贴上限的起点）。

### MC 用 `D100` / `D100.5` / `M10`，X/Y 是八进制

写法取自前端 `addressSyntax.js` 里 mc 规格的示例（`D100`、`M0`、`X30`）。四条协议特有的取舍：

- **位软元件（`M/L/X/Y/B/S/V/F/…`）只允许位粒度。** 字单位读位软元件是驱动支持的
  （`MCAddress.Word` 会按 16 位对齐），但产出的是 `M0/M16/M32` 这种"看着像位、
  其实是 16 点一组"的名字，而值是整字。用户不会发现，直到采上来的数据对不上。
  字软元件取位则写成 `D100.5`（字内位号 0~15）—— 与 `parser.go` 的 `IsBit` 分支
  同一个基准，不需要任何换算。
- **`X`/`Y` 按八进制解释，其余按十进制。** 这是 `ParseMCAddress` 的行为
  （`mcDevices` 表里只有这两个设备带 `octal: true`），扫描表单的「起始地址」
  因此对它们收的是**八进制数字串**（填 `30` 表示 `X30`，即十进制的 24），
  非法位（8/9）**报错而不是静默按十进制解析** —— 后者会让用户扫到一段完全不同的
  地址，而结果看着完全正常。表单那一栏是文本框而不是数字控件，正是为了让这个意图
  写得出来。
- **`buildMCBody` 只发 3 字节的首地址号**，超上限的地址会被静默截断成另一个位置。
  因此扫描主循环有一条与 FINS 那条 16 位回绕守卫同形的越界检查。
- **单请求点数上限随「软元件类别 × 粒度」变四档**，不是一个常数：`cfg.MaxReadWords`
  的语义是"读了多少字/位"，而一个点位占多少字/位是另一回事（位软元件 1 点 = 1 位、
  字软元件取位 1 点 = 1 位、字 1 点 = 1 字、双字 1 点 = 2 字）。当成同一个常数会
  静默错两档：字软元件扫位时请求数变成 16 倍（一段本来扫得完的地址会撞上请求数
  上限、拿到一份标着"未扫完"的清单），双字时每帧字数翻倍（配置贴近型号上限的现场
  直接超限）。回归：`TestPointsPerRequestPerMode` 与 `TestSpanWithinSingleRequestLimit`。

往返由 `mitsubishidrv/pointscan_test.go` 的 `TestPointNameRoundTrip` 钉住
（9 个软元件 × 各自允许的粒度 × 含 `maxDeviceNumber` 附近的起点），
八进制那一半另有 `TestOctalStringRoundTrip`。

**值来自哪个位置必须另行钉住。** 地址生成（`pointName`）与偏移换算（`span` +
`buildPoint`）是两段独立代码，它们对"第 idx 个点位在哪里"的看法一旦分叉，
产出的就是一份地址正确、**值却来自别处**的清单 —— 而值看着完全合理。
因此测试用一个"字 w 的值就是 w"的自描述假设备，断言每个点位的值恰好是**它的名字
指向的那个位置**上的值。回归：`TestScanPointsValueMatchesName`（四种读法 × 含落在
字中间的起点）。

### 逐点类型：`DiscoveredPoint.CommonDataType`（原生枚举专用）

上面三个协议**整段共用一个假设类型**，所以类型是结果级的
（`PointScanResult.AssumedCommonDataType`），前端把它套到每一行。

原生枚举协议（Rockwell.CIP）不是这样：每个标签的类型是**设备自己报的**
（CIP 类型码），DINT 与 REAL 混在同一张表里，用一个值去表达必然出错 ——
而错的方式很隐蔽：用户看着"类型"那一列被填好了就提交，建出的点位采出来的值是错的。

因此契约里多了一个**可选**的逐点字段：

```go
CommonDataType string `json:"commonDataType,omitempty"`   // TypeMap 的键，如 "Long"
```

前端那一行的初值是三级回退：`Points[].commonDataType` → 结果级
`assumedCommonDataType` → 规格里的 `defaultCommonDataType`。老协议不填它，
走的还是原来那两级，因此这个字段与既有协议**完全向后兼容**（可选字段 ⇒
不递增 `APIVersion`）。

OPC.UA 走同一格，但**多一道约束**：它每一行的 `CommonDataType` 都是
"Kind 等价"的近邻（Int32→Long 等），近邻关系由该行的 `Note` 说明
（"OPC UA 基础类型 Int32"）。那条 Note 不是装饰 —— 它是用户在结果表里唯一能
对上设备手册的地方，所以**只在真的不一致时才加**：每一行都挂一条会让那一列
变成噪声，真正需要注意的行反而被埋掉。回归：
`opcuadrv/pointscan_test.go` 的 `TestTypeNoteOnlyForApproximate` 与
`crawl_test.go` 里那条"每一行都必须自带 `CommonDataType`"的断言。

### 地址往返在 OPC.UA 上是另一回事（别照抄 Modbus/S7 的论证）

前面三个协议的往返规则防的是"**这个地址根本不存在**"—— 一个点位永远没有值而已
（修复前是整台设备的采集全部失败加误报断联，见 §8 的补注；现在六个区间规划器
都是规划前就把解析不出的地址拆出去，`Read` 不报错）。OPC.UA **不是这样**：
`opcuaDriver.Read` 对 `*parseError` 与 `ua.StatusCode` 都是逐点 Quality=0 继续 ——
同样是一个点位没有值，但**成因与危险都不同**。

危险在这里，而且更难发现：`parseAddress` 把**任何含 `/` 的串**当浏览路径。
于是一个完全合法的字符串 NodeID `ns=2;s=Room1/Temp` 会被解析成一条两段路径 ——
解析不到还算好，**解析到另一个同名节点才是灾难**：那个点位会永远采到别人的值，
在时序库里表现为一条完全合理的曲线。这条陷阱早已作为手工输入的坑写在前端
（`pitfallOpcuaSlash`），这里只是让 finder **自己不去产生**它：

- 地址优先写 `NodeID.String()`，但**先用 `parseAddress` 解析回来、逐字比对**，
  不一致就作废；
- 作废后退到**下行时逐段累积**出来的浏览路径（按构造可达），渲染完同样再解析
  回来逐段比对；
- 两条都不行 ⇒ 该点位计入"未列出"。**绝不放一个没验证过的地址进结果。**

路径段的渲染规则也是逐条对着 `parsePathSegment` 的分支写的：名字为空 / 含 `/` /
首尾空白一律拒绝（分别对应"静默丢空段""拆成两段""末段被 TrimSpace"），
而 `ns` 前缀**不是**"ns!=0 才写"，是"ns!=0 **或** 名字里有 `:` 就写" ——
裸写 `Motor:1` 会被解析器读成命名空间 `Motor` 并当场报错。

同父下**重名**的兄弟也走这条：它们会渲染出同一条地址串（撞
`(device_id, name)` 复合唯一，且路径解析只取第一个目标），因此那一支整体放弃
路径写法 —— 但**不丢**这些点位，它们仍然可以用 NodeID 寻址。

### DL/T 645 用裸数据标识，字典外才写显式后缀

| 界面选项 | 生成 | 还原 |
|---|---|---|
| 内置字典里的条目 | 裸数据标识（`02010100` / 1997 的 `9010`） | 字典命中 → 长度/小数位/符号/编码全部还原 |
| 字典外的厂商私有数据标识 | `DI:字节数:小数位[:标志]`（如 `12345678:4:2:s`） | 显式给出长度，不依赖字典 |

**字典条目刻意不写全后缀**：`ParseAddress` 会从字典把长度、小数位、符号、编码补齐
（见 `address.go`），把字典的默认值抄进位点地址只是多了一份可能与字典不一致的副本
—— 而字典改一次，两份就分叉了。反过来，字典**未收录**的数据标识**必须**显式写出
长度：`ParseAddress` 对它们宁可报错也不猜一个长度（猜错会静默解出错位的值，见
`address.go` 的注释）。裸数据标识也是前端 `addressSyntax.js` 里 dlt645 规格给出的
形态（它的示例就是 `02010100`、`00000000`、`12345678:2:0:s`）。

扫描表单里的「附加数据标识」就是这条的用户入口：按手册抄一条 `12345678:4:2:s`，
它原样成为点位地址；**与字典条目重复时以附加的为准**（位置不动，顺序因此稳定）——
静默让字典赢，就是"用户改了配置但它没生效"那类最难查的问题。

往返由 `dlt645drv/pointscan_test.go` 的 `TestScanTargetsRoundTrip` 钉住
（两个版本的全部字典条目 + 一批贴着上下限的附加规格：8 字节 / 16 位小数、
有符号 + 二进制、与字典条目重复的覆盖）。

## 9. 结果语义与已知局限

### 三个计数 + 两个标志

```
scanned    本次尝试读取的地址数
readable   有应答的地址数（**含值为 0 的**）
unreadable 读不到的地址数
truncated  达到 MaxPoints，后面的地址**根本没试**
incomplete 预算耗尽，范围还没扫完
```

不变量：`len(points) <= readable <= scanned`，且 `readable + unreadable == scanned`
（`incomplete` 时三者都只是已完成部分的统计）。

**`truncated` 与 `incomplete` 是两个不同的标志，前端不能混**：前者是"结果条数到
上限"，后者是"范围还没扫到"，而它们与"读不到"是三回事。合并成一句话会让用户
得出错误的结论。

### 值的语义

- **零值点位照样列出来**：插件侧**不做零值过滤**（过滤放在前端的一枚开关）。
  在所有寄存器都是 0 的设备上，插件侧过滤会返回一份空列表，用户据此得出
  "这里没有点位" —— 与"没扫到"同型的错误。
- **"零"的判据是原始字节全 0**，不是解析后的值：按 Float 解析时 `0x00000001`
  会得到一个极小的非零数，"显示 0 值"这枚开关会漏掉它。
- **值只是各块读取时刻的采样**（列头标注"采样值"）：每块释放锁 ⇒ 同一次扫描
  **不是原子快照**。「地址存在」与值无关、稳定；「值」会变。全仓没有 `Write`
  路径，所以读到中间态只可能来自 PLC 自身在变。
- **`AssumedCommonDataType` 为空 == 本次结果没有采样值**（原生枚举协议，
  §3 第三种形态）。这不是"没填"，是在表达一件事实，前端据此隐藏「显示 0 值」
  开关与零值统计（否则那个开关一关就清空整张表、而"值为 0"会显示成全表条数）。
  这条约定写在 `driver.PointScanResult` 与 `vo.PointScanResultVO` 的注释里 ——
  **下一个让这个字段空着的协议作者必须先读那两段**，否则会静默失去那个开关。

### 已知局限（都要如实写在文档与界面上）

| 局限 | 说明 |
|---|---|
| **不可取消** | 同步 RPC，插件侧一次扫描覆盖整段、没有"取一部分结果"的入口。前端因此不做"取消扫描"按钮，只用预算把它钳在 9s 以内。 |
| **TCP 二连** | 非串口协议回落临时实例时会多开一个 socket。对 TCP 无害（与采集连接并存），但要显式写在文档里，否则将来某个"连接数有上限"的设备会莫名其妙。 |
| **扫描期间插件停机会被强杀** | 这是整条链路上唯一一处"理论上不该发生、但必须承认"的：`handleDiscoverPoints` 在锁外回复，但插件进程若在扫描途中被监管杀掉，网关侧只会得到一次 RPC 失败。 |
| **配置模式被拒**（Modbus 特有） | `protocol_json` 里 `startAddress > 0` 的设备一律拒绝（§5 理由 1）。Modbus 插件当前的解析结构其实**不读** `startAddress`，因此这条守卫防的是"将来有人把它加回表单"。**别的协议没有这种形态就不要照抄**：S7 就没有（`StringLen`/`MaxGap` 只影响采集侧的区间规划，不改变地址的含义），照抄只会凭空多出一条拒绝条件。 |
| **优化块访问的 DB 读不到**（S7 特有） | S7-1200/1500 在 TIA Portal 里默认给 DB 勾上「优化的块访问」，那种块**无法按绝对地址读取**，整段都会报错，表现为 `readable = 0`、`unreadable = scanned` —— 与"这一段确实没有点位"在界面上无法区分。因此**必须写进 `PointDiscoverySpec.Description`**，随弹窗常驻显示。 |
| **范围截断** | 网关侧 7000ms 的钳制会截断 RTU 大范围扫描，表现为 `incomplete`。 |
| **读到内存区末尾就停**（FINS 特有） | 第一个读不到的地址之后一律按读不到计（理由见 §6）。因此 `unreadable` 会包含**没有被逐个读过**的地址 —— 那是推断值，但它成立的前提（地址空间连续）是协议性质，不是猜测。 |
| **单次请求的字数上限取设备自己的 `maxReadWords`**（FINS 特有） | 不写死一个更大的值：采集时的区间规划用的就是它，它对这台 PLC 是已知能用的；照搬更大的值会让扫描在"单请求最大 100 字"的老型号上一片都读不到。 |
| **没有 label 来源** | 设备不会告诉你"这个寄存器是温度"。所以 `label` 为空时**服务端兜底为 `name`**（在界面上是预填、可就地改）。 |
| **取不到部分结果**（Rockwell 特有） | 枚举是"整只对象"的操作，超预算那一刻手上零个标签，没有"部分"可交。因此这里是**报错**而不是"部分结果 + incomplete"，与 §7 契约第 1 条的一处有意偏离（理由见 §3 第三条）。注意与**截断**不对称：达到 `MaxPoints` 时枚举已跑完，那种情况**是**有部分结果的。 |
| **不读采样值**（Rockwell 特有） | 枚举每个标签一次请求，再读值等于翻倍。结果里的"采样值"列是空的，`AssumedCommonDataType` 也留空（见上面"值的语义"）。 |
| **数组只列第 0 个元素**（Rockwell 特有） | 设备不提供数组维度，只能给出一定存在的第 0 个元素（`Arr[0]`）。其余元素请手工补 —— 这一条写在弹窗常驻的 `Description` 里。 |
| **结构体与无通用类型的标签被跳过**（Rockwell 特有） | TIMER/COUNTER/UDT 等一切 Logix 派生类型都回 `STRUCT`(0x02A0)，没有成员布局；LINT 与 BYTE/WORD/DWORD 在 `commonTypeMap` 里没有入口（补一个要动冻结的黄金基线）。跳过数在**「未列出」**里可见 —— 它**不等于**「读不到」。 |
| **「读到就停」对数字 I/O 与链接区不成立**（MC 特有） | `X`/`Y` 按槽位分配、`B`/`W` 按模块分配，中段可以有未分配的空洞。因此这四种软元件上**不做**"第一个读不到就收工"的推断，而是逐段降级继续往后扫（最坏 `2n-1` 次请求，由请求数上限兜住）。代价是慢，换来的是清单不会从空洞处静默断掉。`D/R/ZR/M/L` 等单片连续的软元件不受影响。 |
| **位软元件只能用位粒度**（MC 特有） | `M/L/X/Y/B/S/V/F` 等本身就是位，字单位读法会产出 `M0/M16/M32` 这种"看着像位、其实是 16 点一组"的地址，而值是整字。插件侧直接拒绝这种组合（报错而不是猜），字软元件取位则写成 `D100.5`。 |
| **X/Y 的起始地址是八进制**（MC 特有） | 与它们在图纸上的写法一致（`X30` = 八进制 30 = 十进制 24）。扫描表单的「起始地址」对这两个软元件收八进制数字串，填 8 或 9 会**报错**而不是静默按十进制解析 —— 后者会扫到一段完全不同的地址，而结果看着完全正常。 |
| **设备回结束码错误时整段不可读**（MC 特有） | MC 没有 FINS 那种可按主码成组排除的结构，白名单逐条列**码值**：`0xC051`/`0xC056`/`0xC05B`（QnA 家族）与 `0x4031`（iQ 家族，与前两条同义），其余（含 `0xC0EF` PLC 忙这类可恢复状态）一律**中止并带上已得的部分结果报错**。`0xC051`/`0x4031` 会让本型号不支持的软元件、或可用范围为空的分区整段记成"读不到"（`readable=0`）—— 界面上与"这个区确实没有点位"无法区分，只能靠选对软元件来避免（真机例子：文件寄存器没配置的 PLC 上扫 `ZR`，每个地址都回 `0x4031`）。 |
| **串口大范围扫描会经常未扫完**（MC 特有） | 9600bps 上一帧几十字，而网关侧 7000ms 的预算钳制对串口是硬约束。这一条写在弹窗常驻的 `Description` 里 —— 它最容易被误读成"这个功能坏了"。 |
| **不读采样值**（OPC.UA 特有） | 与 Rockwell 同一个选择，但理由不同：**类型来自 `DataType` 属性，与值无关**，所以不读值不影响类型。结果里的「采样值」列是空的，`AssumedCommonDataType` 也留空。 |
| **类型名是 Kind 等价的近邻**（OPC.UA 特有） | Int32→Long、UInt64→DWord、SByte→Char、ByteString→String。本系统里没有这几个的**同名**通用类型（只有内部裸名），而 TypeMap 的键集被黄金基线钉死。行为上正确（本协议不做字节级解码，Kind 完全一致），名字上的差异由该行的 `Note` 标出。 |
| **只列变量，且 `Server` 诊断节点也会被列出**（OPC.UA 特有） | 对象/文件夹只用于往下走，方法/视图/类型定义直接跳过。默认起点是 `Objects` 文件夹，而服务器自己的 `Server` 对象也挂在它下面 —— 那批诊断变量**会**出现在清单里，这是刻意的（不做静默省略，要缩小范围就把起始节点填成设备子树）。 |
| **自定义/枚举类型可能被跳过**（OPC.UA 特有） | 类型是另一个节点的 NodeID，需要沿逆 `HasSubtype` 上溯到内建类型（有层数上限）。结构体、Guid、NodeID、LocalizedText 这类"没有对应通用类型"的会被跳过，跳过数在「未列出」里可见 —— 它**不等于**「读不到」。 |
| **少数地址是浏览路径**（OPC.UA 特有） | 标识符里带 `/` 的字符串 NodeID 写不成 NodeID（会被当成浏览路径），改用从 Root 起的浏览路径。那类地址**每次设备重连后的首次采集要多一次服务器解析**（驱动的浏览路径缓存会在 `Connect` 时清空）。这一条写在弹窗常驻的 `Description` 里。 |
| **同父重名的兄弟不给路径**（OPC.UA 特有） | 它们会渲染出同一条地址串（撞 `(device_id, name)` 复合唯一，路径解析还只取第一个目标）。此时那一支整体放弃路径写法 —— 但**不丢**这些点位，它们仍然可以用 NodeID 寻址。 |
| **起始节点拼错会明确报错**（OPC.UA 特有） | 解析器对裸词是宽容的（没有 `i=`/`s=` 前缀的串会被当成 ns=0 的字符串 NodeID），所以"从 Objects 开始"写成 `Objects` 会被解析成 `s=Objects` —— 一个不存在的节点。因此起始节点会**先确认存在性**再往下扫，报错里带上服务器的状态码，而不是给出一份空清单。 |
| **字典里有、这块表没实现的很多**（DLT645 特有） | 数据标识字典是**协议**的，不是这块表的。1997 版与廉价单相表往往只实现其中几条 —— 「读不到」的条数因此是个**正常数字**，不是异常信号，也不代表链路有问题。 |
| **部分老表对不支持的数据标识干脆不答**（DLT645 特有） | 规范规定回异常应答（0xD1），但 1997 与廉价表常常保持沉默。这类表每问一个都要等到超时（默认 3s），扫一遍字典会很快撞上网关侧 7000ms 的钳制。finder 用一次存活复探把"掉线"排除掉后再记「读不到」（见 §3 末），但那条前提需要真机确认。 |
| **1997 版每帧只带一个数据标识**（DLT645 特有） | 18 条字典 ⇒ 18 帧。2400bps 上很容易撞上 7000ms 的钳制，表现为 `incomplete`。这是**协议约束**（1997 的读命令数据域固定为一个 2 字节数据标识），不是实现取舍。 |
| **不读后续帧**（DLT645 特有） | 驱动刻意不支持拼接「读后续数据」(0xB1 / 0xB2)：各厂商手册对帧序号是否回显、回显在哪儿描述不一，臆测布局会把序号字节当成数据拼进去，得到一个**看似合理实则错位**的值。因此应答带后续帧标志的条目一律记「读不到」——负荷曲线那类跨帧数据项会在这一列上消失。 |
| **逐点类型与结果级类型同时非空**（DLT645 特有） | 见 §3 第五种形态。前端的三级回退（逐点 → 结果级 → 规格默认）因此不冲突；但**结果级那个值不是"假设类型"**（645 的类型从不影响读取），它只是"本次结果带采样值"的载体，用来点亮「显示 0 值」开关。 |

### `(device_id, name)` 复合唯一

以迁移 `002_device.sql` 为准（`po` 的 `uniqueIndex` tag 与迁移不一致）。
因此必须**库内 + 批内双重去重**：少了批内那层，同一次扫描里勾选重复的地址会撞
SQLite 约束，用户看到一条数据库错误。

## 10. HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/deviceScan/pointCapability?protocolName=X` | 能力查询。**不支持是 200 + `supported:false`，不是错误** —— 前端进页面就问一次，据它决定按钮可用/置灰。 |
| POST | `/deviceScan/discoverPoints` | `{deviceId, options}` → `PointScanResultVO`。**同步**，最坏 ~9s。 |
| POST | `/deviceScan/createAddresses` | `{deviceId, items[]}` → `ExcelImportResultVO`（逐条失败不中断，HTTP 始终 200）。 |

**请求里没有 `protocolJson`**：连接配置由服务端从 `device` 行读取后透传给插件
（照 `CreateDevices` 的先例）。它决定网关去连哪台设备，属于跨信任边界的数据。

**不开新的总开关**：点扫复用 `deviceScan.enabled`。两个开关会让人只关掉一个，
然后在另一个入口重新遭遇他以为已经关掉的功能。

错误码：复用 `40021`（未启用）/ `40026`（参数非法，根因原样带上）；
只新增 `40027 该协议不支持点位扫描`。为什么不为执行期失败再分一套码：
那些原因几乎全是动态的（"设备正忙"、"该串口配给了别的设备"），
回一句固定的译文等于把最有用的信息丢掉。

## 12. 与 device-scan 共享的三条道理

**改一篇必须同时改另一篇，否则必然漂移。** 这三条在两篇里是同一条：

1. **不建能力缓存表。** 热升级只替换 `lp.meta`，而 `registrationSig` 只含
   `scope` / `protocols` / `types` / `typeMap`，**不含 `PointDiscovery`** ——
   一个只改了扫描声明的新二进制升级后不会触发重注册。若把能力另存一张表，
   它会停在旧值上，症状是"插件明明改了、前端却一直显示旧的"，
   且两边日志都写着成功。每次遍历 `m.plugins` 现算则一致性自动成立。
   回归：`TestPointDiscoverySpecsRefreshAfterHotUpgrade`。
2. **预算是每协议的属性，网关侧的 RPC 超时按插件声明推导。** 不设全局配置旋钮
   —— 那种旋钮配小了就是"RPC 先超时、插件还在跑、用户看到扫不到东西"，
   而日志里只有一条 timeout。点扫额外多一道**上限**（§4），但下限与推导方式相同。
3. **串口独占与会话复用。** 两篇都必须在串口面前做取舍：device-scan 直接
   **禁止**串口声明能力（目标是 host/port）；point-discovery 则**必须**支持串口，
   并为此写了整张回退表（§5）。同一条物理约束，两个方向相反的答案 ——
   这正是两篇不能合并的原因。

**一个具体的例子（2026-10，DLT645 点位扫描）**：只改本篇是不够的。那个协议
**只做点位扫描、不做设备扫描**（理由见 [device-scan.md](device-scan.md) §9 末行），
于是 device-scan.md 必须补一行"它扫不到设备是刻意不做"—— 否则运维点开扫描页
找不到 DLT645 时，两篇文档都没有一处能回答"是漏配还是不做"。
而第 3 条（串口独占）正是这一处的支点：同一个物理约束下，device-scan 的答案是
"禁止声明"，point-discovery 的答案是"必须支持，并复用会话"。

## 13. 给插件作者的最小清单

1. 在 `Meta.Protocols[]` 里填 `PointDiscovery`（§3 的字段表；串口协议也照填）。
2. 在 `driversdk.Main(..., driversdk.Capabilities{PointFinders: ...})` 里给出实现。
3. 实现里守住五条契约（§7），特别是**在 `req.Budget` 内返回**与
   **不要 Close 会话里的驱动**。
4. **每块一次 `req.Session.Do`**，块内自己写降级（§6）——
   不要复用为采集设计的区间读取助手：它在整段失败时会整段标记为读不到，
   "整块→子段→单地址"根本不会发生。
5. 生成的地址必须能被**你自己的**解析器还原回同一个位置，并用一条往返测试钉住
   （§8）。
6. **先拒绝你的协议里"地址含义由配置决定"的形态**（如 Modbus 的配置模式），
   否则你会静默给出一份错位的清单（§5 理由 1）。
   **如果你的协议没有这种形态，就不要照抄这条守卫** —— 它凭空多出一条拒绝条件
   （S7 就没有）。
7. 块内降级要有**请求数上限**，并且**把"地址不存在"与"设备掉线"分开**
   （§6 末）：判定的手段随协议而异（Modbus 能 `errors.As`，S7 只能字符串匹配，
   FINS 按主码排除），但两条要求相同。写测试时把**白名单与黑名单各断言一遍** ——
   这个分类错在哪个方向都有明确的坏结果。
8. **地址空间连续时，读到第一个读不到的点就收工**（§6 前半）。逐个探测只会把
   一次"扫到末尾"变成几百次必然失败的请求，最后撞上请求数上限、给用户一份标着
   "未扫完"的结果 —— 而它其实早就扫完了。**地址空间不连续（有空洞）时不要照抄。**

参考实现：[`driversrc/modbus/modbusdrv/pointscan.go`](../driversrc/modbus/modbusdrv/pointscan.go)。
