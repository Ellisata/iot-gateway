# loadtest 端到端采集容量压测

进程内跑完整采集链路（采集引擎 + worker 池 + 协议驱动 + **假 PLC 服务器**），
扫描（设备数 × 单设备点位）矩阵，量化每种协议在网关侧可支撑的**设备容量**与**点位容量**。

核心思路：**点位容量不是点数决定的，是帧数 × 往返延迟决定的。** 假服务器只按请求返回
合法响应、不做协议上限校验，把被测对象收敛到网关侧本身。

## 用法

```bash
go run ./cmd/loadtest -protocol modbus -devices 10,50,100 -points 500,2000,5000
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `-protocol` | `modbus` | `modbus` / `mc` / `fins` / `s7` / `cip` / `rockwell` |
| `-devices` | `10,50,100` | 设备数矩阵（逗号分隔） |
| `-points` | `500,2000,5000` | 单设备点位矩阵 |
| `-scan` | `1000` | 采集频率（毫秒），收紧到 200/100 探测饱和点 |
| `-run` / `-warmup` | `5` / `2` | 测量窗口 / 预热秒数 |
| `-servers` | `4` | 假 PLC 服务器池大小（设备轮询分配） |
| `-sparse` | `false` | 稀疏地址布局（间隙 > 合并窗口，**1 帧/点**，帧数最坏情况） |
| `-latency` | `0` | 每事务注入固定延迟毫秒（模拟真实 RTT，仅 CIP 系：`cip` / `rockwell`） |
| `-cpuprofile` / `-memprofile` | - | 覆盖最大组合的 pprof 画像 |

## 指标含义

- **drop%**（核心判定）：`1 - 实际记录数 / 预期记录数`。预期 = 设备数 × 点数 × (窗口/采集频率)。
  非 0 即说明设备轮询周期 > 采集频率被跳过（in-flight 防堆积）或 worker 池满丢轮。
- **actual/s**：sink 实际收到的记录数/秒（sink 只计数，替换真实推送引擎，隔离推送干扰）。
- **cycleMs**：dev-0 成功采集时间差分的轮询周期（仅 `scan>=1000ms` 时读数有意义，
  低于 1s 被时间戳秒级精度抹平）。
- **heapMB / goroutines / errors**：测量窗口峰值；errors 来自引擎错误计数。

判定「可支撑」：drop%=0 **且** errors=0 **且** good%=100。

## 工作原理

```
testutil/fake/           假 PLC 服务器（真实 TCP 监听，逐帧解析请求回合法响应）
  server.go              共享 TCP 骨架：每连接一 goroutine，Close 关闭所有连接
  modbus.go              MBAP + FC1/2/3/4/5/6/15/16
  mc3e.go                MC 3E（SLMP）帧批量读（字单位 / 位单位）
  fins.go                FINS/TCP（连接握手 + 内存区读 0x0101）
  s7.go                  S7（ISO CR/CC + PDU 协商 + 读变量，与 gos7 逐字节对齐）
  cip.go                 EtherNet/IP（Register Session + SendRRData + 0x4C 读；
                         欧姆龙方言 NewCIP / AB 方言 NewCIPAB / 带 RTT 的 *WithLatency）
  integration_test.go    真实驱动连假服务器互操作测试（防帧格式漂移）
cmd/loadtest/
  harness.go             造数 seeder（真实迁移建库）+ 计数 sink + 测量采样器 + 协议适配器
  main.go                参数解析 + 假服务器池 + 扫描矩阵
```

- 设备与点位写入临时 SQLite（走 `database/sqlite.InitDB` 真实迁移，与生产 schema 一致）。
- 采集引擎参数与 `wire.go` 一致：worker 池 `NumCPU*2` + 1024 队列。
- 日志静音到 WARN 并落到临时目录，`configFile` 用 loadtest 自身嵌入配置，
  避免运行目录 `default.yaml` 的 DEBUG 级别污染测量。

## 已测协议首轮结果

环境：8 核 / Windows / loopback。**数值为网关侧上限，随机器核数、设备真实往返时延变化。**

### Modbus.TCP（连续布局，默认 mergeWindow=125，帧=125 寄存器）

scan=1000ms：10/50/100 设备 × ≤5000 点全部 **0% 掉点**（最高 100 设备 × 5000 点 ≈ 50 万记录/秒）。

| 设备 | 点/台 | 扫描频率 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 50 | 5000 | 1000ms | 250k | 299k | 0.0 |
| 100 | 5000 | 1000ms | 500k | 600k | 0.0 |
| 200 | 2000 | 200ms | 200万 | 208万 | 0.0 |
| 200 | 5000 | 200ms | 500万 | 448万 | **10.4** |
| 100 | 5000 | 100ms | 500万 | 410万 | **17.9** |

**边界**：本机 0% 掉点吞吐约 **200 万记录/秒**；500 万/秒时掉点 10%~18%。
单设备在 100ms 频率下 ≤2000 点是安全上限，5000 点轮询周期 >100ms 触发跳过。

### Modbus.TCP（稀疏布局，1 帧/点，上限 520 点/台受寄存器地址空间限制）

100 设备 × 500 点 = 5 万帧/秒，scan=1000ms 仍 **0% 掉点**——帧数本身不是瓶颈，瓶颈在解码与调度。

### MC 3E（默认 maxReadWords=100，帧=100 字）

scan=1000ms 与 Modbus 同矩阵全 **0% 掉点**（最高 100 设备 × 5000 点 ≈ 50 万记录/秒）。
MC 默认单帧 100 字，帧数约为 Modbus 的 1.25 倍；调大 `maxReadWords`（上限 960）可显著降帧数。

| 设备 | 点/台 | 扫描频率 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 50 | 5000 | 1000ms | 250k | 250k | 0.0 |
| 100 | 2000 | 1000ms | 200k | 240k | 0.0 |
| 100 | 5000 | 1000ms | 500k | 500k | 0.0 |

### FINS.TCP（默认 maxReadWords=100，帧=100 字）

scan=1000ms 全矩阵 **0% 掉点**（最高 100×5000 ≈ 50 万记录/秒），与 MC/Modbus 同级。

| 设备 | 点/台 | 扫描频率 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 100 | 2000 | 1000ms | 200k | 240k | 0.0 |
| 100 | 5000 | 1000ms | 500k | 500k | 0.0 |

### Siemens.S7（byte 区，gos7 按 PDU 480 分块 ≤462 字节）

scan=1000ms 全矩阵 **0% 掉点**（最高 100×5000 ≈ 50 万记录/秒）。S7 帧数最低
（5000 字节 ≈ 11 个 PDU 请求），是帧数最省的一档。

| 设备 | 点/台 | 扫描频率 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 100 | 2000 | 1000ms | 200k | 200k | 0.0 |
| 100 | 5000 | 1000ms | 500k | 599k | 0.0 |

### Omron.CIP（默认单点单往返；可开 0x0A 多服务批量读）

**单读（maxTagsPerRequest=0/1）**：每点 1 个 SendRRData 往返，帧数 = 点数，容量被锁死。

| 设备 | 点/台 | 扫描频率 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 100 | 2000 | 1000ms | 200k | 216k | 0.0 |
| 50 | 5000 | 1000ms | 250k | 214k | **14.4** |
| 100 | 5000 | 1000ms | 500k | 151k | **69.8**（周期飙到 3s） |

**批量读（`maxTagsPerRequest=100`，一个 0x0A 报文读 100 个标签）**：
往返从 N 次降到 ceil(N/100) 次，容量直接回到与其它协议同级（~200 万记录/秒通用上限）。

| 设备 | 点/台 | 扫描频率 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 100 | 5000 | 1000ms | 500k | 599k | 0.0（单读 69.8%）|
| 50 | 5000 | 100ms | 250万 | 255万 | 0.0 |
| 100 | 5000 | 200ms | 250万 | 259万 | 0.0 |
| 100 | 5000 | 100ms | 500万 | 268万 | **46.4**（通用 worker 池上限）|

【真机核实】0x0A 多服务报文是 CIP 驱动新特性，由 device.protocol_json 的
`maxTagsPerRequest` 开启（默认 0 = 单读，零回归）。报文字节布局以 HslCommunication
OmronCipNet 简洁格式为参照（`0x0A | 服务数 | 拼接的 0x4C 请求`），**上线前必须在目标
NJ/NX 上验证**；若与真机不符，仅需调整 `driver/omron/cip/frame.go` 的
`buildMultipleDataTableRead` / `parseMultipleDataTableRead` 两处。

### Rockwell.CIP（Logix 标签寻址；数组标签 ≤125 元素/帧合并，独立标签逐点串行往返）

驱动按标签名分组读：`Arr[N]` 形态的同基数组点位按下标排序切成 ≤125 元素的
Read Tag Elements 分块（`maxTagElements`，PDU 508 字节上限）合并读；
`Tag_x` 独立标签每点 1 次 0x4C 串行往返（客户端适配器互斥锁，无 0x0A 多服务）。

**连续布局（Arr[i]，数组合并最好情况，scan=1000ms）**：全矩阵 **0% 掉点**，
50 设备 × 5000 点（25 万点，≈40 帧/设备/周期）实际 29.3 万记录/秒，与 Modbus 基线同级。

| 设备 | 点/台 | 布局 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 50 | 5000 | 连续 | 250k | 293k | 0.0 |
| 10 | 5000 | 连续+RTT 1ms | 50k | 60k | 0.0（40 帧×1.4ms≈56ms/周期，余量充足） |
| 50 | 5000 | 连续+RTT 1ms | 250k | 300k | 0.0 |

**稀疏布局（Tag_i 独立标签，1 帧/点，串行往返最坏情况，scan=1000ms）**：
零 RTT 时 50×5000 掉 35%（每周期 5000 次串行往返 ≈ 2s，超过 1s 采集频率即跳轮）；
RTT 1ms 时单设备 1000 点即开始掉点（周期 ≈ 1.2s）。

| 设备 | 点/台 | 布局 | 预期记录/秒 | 实际记录/秒 | drop% |
|---|---|---|---|---|---|
| 50 | 2000 | 稀疏 | 100k | 120k | 0.0（边界） |
| 50 | 5000 | 稀疏 | 250k | 162k | **35.2**（周期 2s） |
| 1 | 1000 | 稀疏+RTT 1ms | 1k | 0.6k | **40.0**（周期 2s） |
| 10 | 2000 | 稀疏+RTT 1ms | 20k | 8k | **60.0** |

**边界结论**：
- 数组规整布局（推荐）：点位容量与 Modbus 同级（本机 25 万点 @1s 零掉点），
  帧数 = ceil(同基数组点数/125) 之和；
- 独立标签布局：单设备容量 ≈ 采集频率 / 单次往返时延（1s 周期、1ms RTT 下
  约 800 点/台封顶），多设备受 worker 池与 CPU 共同约束。生产配置应尽量把
  连续采集点规划为 `Base[N..N+k]` 数组标签；
- 修复记录：>125 点的数组组此前整组放弃合并退化为逐点读（5000 点 = 5000 往返），
  已改为按下标排序分块合并（5000 点 = 40 帧），修复前 50×5000 连续布局掉点 35.2%。

## 已知观察（供后续优化）

1. **帧数决定点位容量**：Modbus 125 寄存器/帧、MC 960 字/帧、FINS 100 字/帧、
   S7 462 字节/PDU、CIP 默认 1 点/往返。同点数下帧数差 1~2 个数量级，容量随帧数线性走。
   CIP 开 `maxTagsPerRequest` 批量后帧数降到 batch 点/往返，回到通用档位（本仓库实测
   从 69.8% 掉点降到 0%）。稀疏点位（间隙 > 合并窗口）帧数按点数量级放大——生产配置
   应尽量连续/规整地址。
2. **配置 watcher 全表 checksum 是扩展瓶颈**：`collector.Engine.loadConfigChecksum` 每 10s
   `SELECT * FROM device_address WHERE status=1` 全表加载+哈希。100 万地址时单次 1.7s、
   内存数 GB，与大点位场景直接冲突。点位海量时建议改为增量/db 变更感知，或拉长巡检间隔。
3. **高吞吐掉点是 CPU 上限，不是 worker 池**。压测验证：`worker pool full` 日志在
   ≤200 设备时从不触发（队列 1024 ≫ 最大排队量）；且把 worker 数从 32 加到 64，
   掉点反而从 16.1% 恶化到 19.4%（CPU 已饱和，加并发徒增上下文切换）。profile 显示
   热点是驱动解码/格式化 + 采集记录构建 + GC 分配压力。已优化 `collector.toRecords`
   （每记录两次 map 查询 → 索引对齐直取，实测 toRecords CPU 从 13.7% 降到 1.7%）；
   后续可再优化驱动侧格式化（值未变跳过重格式化）与每轮 `RangeSig` 缓存键重算。
