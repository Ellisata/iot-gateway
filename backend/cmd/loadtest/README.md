# loadtest 端到端采集容量压测

[简体中文](README.md) | [English](README.en.md)

进程内跑完整采集链路（采集引擎 + worker 池 + **进程外协议驱动插件** + 假 PLC 服务器），
扫描（设备数 × 单设备点位）矩阵，量化每种协议在网关侧可支撑的**设备容量**与**点位容量**。

协议驱动**全部**来自 `backend/driversrc/*` 编出的进程外插件（内置驱动实现已随插件化移除，
见 [docs/driver-plugins.md](../../../docs/driver-plugins.md)），因此 **loadtest 运行前必须先有插件**。

核心思路：**点位容量不是点数决定的，是帧数 × 往返延迟决定的。** 假服务器只按请求返回
合法响应、不做协议上限校验，把被测对象收敛到网关侧本身。

## 用法

### 运行前先准备插件（必做）

插件目录为空时 loadtest **直接报错退出**，不会跑出一张「协议不支持、全 0 记录」的假表。
先把要压测的协议编出来：

```bash
cd backend

# 方式一：只编要测的那个协议。产物名必须是 iot-driver-<driversrc 目录名>
go build -o ./plugins/iot-driver-modbus ./driversrc/modbus

# 方式二：一次编出全部插件（在仓库根执行，与发行包同款构建）
./build.sh
```

> **Windows 下产物必须带 `.exe` 后缀**（`-o ./plugins/iot-driver-modbus.exe`）。
> 没有扩展名时 `os/exec` 找不到可执行文件，日志里先是几轮「启动失败」告警、
> 再以握手超时收场，最终表现为「协议未注册」。

然后按需加上 `-plugins-dir`（默认 `plugins`）：

```bash
go run ./cmd/loadtest -protocol modbus -devices 10,50,100 -points 500,2000,5000 -plugins-dir ./plugins
```

**`-plugins-dir` 的解析顺序**（相对路径）：

1. **可执行文件所在目录**下的该路径 —— 与网关 `plugin.dir` 的语义一致
   （`pluginhost.resolvePluginDir` 只认这一条）；`go build -o ./loadtest ./cmd/loadtest`
   且二进制与 `plugins/` 同层时命中；
2. **调用 loadtest 时的工作目录**下的该路径 —— `go run` 会把二进制产在临时目录，
   靠这条回退才能用 `-plugins-dir ./plugins` 在 `backend/` 下直接跑起来。

两条都不命中就直接报错退出，并打印它试过的全部绝对路径。

| 参数 | 默认 | 说明 |
|---|---|---|
| `-protocol` | `modbus` | `modbus` / `mc` / `fins` / `s7` / `cip` / `rockwell` / `opcua` / `dlt645` |
| `-plugins-dir` | `plugins` | 插件目录；相对路径**先按可执行文件所在目录、再按调用时的工作目录**解析（不是只看 cwd），见上节 |
| `-devices` | `10,50,100` | 设备数矩阵（逗号分隔） |
| `-points` | `500,2000,5000` | 单设备点位矩阵 |
| `-scan` | `1000` | 采集频率（毫秒），收紧到 200/100 探测饱和点 |
| `-run` / `-warmup` | `5` / `2` | 测量窗口 / 预热秒数 |
| `-servers` | `4` | 假 PLC 服务器池大小（设备轮询分配） |
| `-sparse` | `false` | 稀疏地址布局（间隙 > 合并窗口，**1 帧/点**，帧数最坏情况） |
| `-latency` | `0` | 每事务注入固定延迟毫秒（模拟真实 RTT，**8 个协议全部支持**） |
| `-serial-baud` | `0` | **模拟串口链路**：按该波特率与协议帧字节数折算线路时间，**叠加到** `-latency` 上（详见下方「串口链路怎么压测」）。`0` = 关闭；只对帧布局已知的协议有效，其余**直接报错退出** |
| `-cip-batch` | `0` | CIP 0x0A 多服务批量读的标签数：`1` = 逐标签单读，`>1` = 批量；`0` = 不带该字段、用驱动默认（**注意驱动默认是 64**） |
| `-opcua-batch` | `0` | OPC UA maxBatch（单 ReadRequest 节点数，0 = 驱动默认 100） |
| `-dlt645-dis` | `0` | DL/T 645 `maxDIsPerRead`（单请求打包的数据标识数，1~12；0 = 不带该字段、用驱动默认 **12 = 协议上限**；传 `1` 可复现「一帧一个点」的保守配置） |
| `-dlt645-interframe` | `-1` | DL/T 645 `interFrameDelayMs`（发送后等多久开始读应答；**`-1` = 用驱动默认：TCP `0` / 串口 `30ms`**，`0` = 关闭） |
| `-cpuprofile` / `-memprofile` | - | 覆盖最大组合的 pprof 画像 |

## 指标含义

- **drop%**（核心判定）：`1 - 实际记录数 / 预期记录数`。预期 = 设备数 × 点数 × (窗口/采集频率)。
  非 0 即说明设备轮询周期 > 采集频率被跳过（in-flight 防堆积）或 worker 池满丢轮。
- **actual/s**：sink 实际收到的记录数/秒（sink 只计数，替换真实推送引擎，隔离推送干扰）。
- **cycleMs**：dev-0 成功采集时间差分的轮询周期（仅 `scan>=1000ms` 时读数有意义，
  低于 1s 被时间戳秒级精度抹平）。
- **heapMB / goroutines / errors**：测量窗口峰值；errors 来自引擎错误计数。

判定「可支撑」：drop%=0 **且** errors=0 **且** good%=100。

## 工作原理

```
testutil/fake/           假 PLC 服务器（真实 TCP 监听，逐帧解析请求回合法响应）
  server.go              共享 TCP 骨架：每连接一 goroutine，Close 关闭所有连接
  modbus.go              MBAP + FC1/2/3/4/5/6/15/16（NewModbusTCP / *WithLatency）
  mc3e.go                MC 3E（SLMP）帧批量读（字单位 / 位单位，*WithLatency）
  fins.go                FINS/TCP（连接握手 + 内存区读 0x0101，*WithLatency）
  s7.go                  S7（ISO CR/CC + PDU 协商 + 读变量，与 gos7 逐字节对齐，*WithLatency）
  cip.go                 EtherNet/IP（Register Session + SendRRData + 0x4C 读；
                         欧姆龙方言 NewCIP / AB 方言 NewCIPAB / 带 RTT 的 *WithLatency）
  opcua.go               OPC UA（复用 gopcua 进程内 server 包 + Read 覆盖处理器注值；
                         地址空间 ns=1;i=≥1001 全公式化，带 RTT 的 NewOpcUaWithLatency）
  dlt645.go              DL/T 645-2007 电能表（读数据命令回显数据标识 + 定长数据，
                         数据值由数据标识导出；带 RTT 的 NewDLT645WithLatency）
cmd/loadtest/
  harness.go             造数 seeder（真实迁移建库）+ 计数 sink + 测量采样器 + 协议适配器
  pluginLoader.go        插件目录解析 + pluginhost.Manager 启停 + 协议注册校验
  main.go                参数解析 + 假服务器池 + 扫描矩阵
```

- 设备与点位写入临时 SQLite（走 `database/sqlite.InitDB` 真实迁移，与生产 schema 一致）。
- 采集引擎参数与 `wire.go` 一致：worker 池 `NumCPU*2` + 1024 队列。
- 日志静音到 WARN 并落到临时目录，`configFile` 用 loadtest 自身嵌入配置，
  避免运行目录 `default.yaml` 的 DEBUG 级别污染测量。
- 插件通过网关自己的 `pluginhost.Manager` 加载，**与生产完全同一条链路**：
  `Start()` 的首次扫描是同步的，先于任何一次采集引擎启动（时序同 `main.go` 的
  `deps.DriverManager.Start()`），因此引擎建任务时协议已就位。压测期间目录扫描间隔
  被拉长到 1 小时，避免「驱动集变化 → 采集配置热刷新」在测量窗口里重建任务。

## 插件化后基线（2026-09 实测）

本节是**插件版的第一份有效基线**，取代此前全部「驱动还在网关进程内」时期的读数
（那批数字已随插件化失效，见 [specs/capacity-testing.md](../../specs/capacity-testing.md)）。
全部驱动跑在进程外插件里，网关每轮每设备多一次 RPC（请求编解码 + IPC + 响应编解码），
**下面的数字已经含这笔开销**。

环境：**16 核** / Windows / loopback / 4 个假 PLC 服务器 / worker 池 32 + 队列 1024。
**数值为网关侧上限**，随机器核数、设备真实往返时延变化，现场请按目标机器重测。

矩阵：每协议 `-devices 10`，`-points 500/2000/5000`，`-scan 1000/200/100ms`，`-latency 0/10/20ms`；
另有聚合档 `-devices 50 -points 5000 @ RTT=0`。**全部 237 组读数 errors=0、good%=100。**

### 帧数模型（后面每个数字都由它解释）

**单设备单轮周期 ≈ 帧数 × RTT**，帧数由各协议的合并窗口与地址布局决定，与驱动跑在哪个进程无关。

用 `-latency 100 -scan 1000 -devices 1 -points 5000` 实测反推（读 cycleMs），
7 个协议的实测帧数与公式逐一吻合（DL/T 645 另见下方专节）：

| 协议 | 默认合并窗口（可调项） | 5000 点/台帧数 | 实测单轮周期 @RTT=100ms |
|---|---|---|---|
| ModBus.TCP | `mergeWindow` 125 寄存器 | 40 | 5000ms |
| Mitsubishi.MC.TCP | `maxReadWords` 100 字（可调至 960） | 50 | 6000ms |
| Omron.FINS.TCP | `maxReadWords` 100 字 | 50 | 6000ms |
| Siemens.S7 | gos7 按协商 PDU 480 → 462 字节/帧 | 13 | 2100ms |
| Omron.CIP | `maxTagsPerRequest` **64**（硬上限 64） | 80 | 9000ms |
| Rockwell.CIP | `maxTagElements` 125 元素（仅数组标签） | 40 | 5000ms |
| OPC.UA | `maxBatch` 100 节点（可调至 1000） | 50 | 6000ms |
| DLT645.TCP | `maxDIsPerRead` **12**（协议上限）+ `interFrameDelayMs` **0**（TCP） | 417 | 见下方专节 |

实测周期比「帧数 × 100ms」略大（MC 50 帧 → 6000ms 而非 5000ms），差值是采集引擎的
tick 对齐：周期不是采集频率的整数倍时，轮询顺延到下一个 tick。

> ⚠️ **贴近边界的单元读数会跳变（重要）**：当「帧数 × RTT」恰好落在采集频率附近时，
> 周期在两个 tick 之间抖动，掉点率会在两档之间**双稳**。实测复现：
> Modbus 与 Rockwell 的 5000 点 @RTT=20ms/scan=1000ms（40 帧 × 20ms = 800ms，紧贴 1s 频率）
> 重复 3 次得到 `16.8 / 0.0 / 0.0` 与 `0.0 / 40.0 / 0.0` 两组值。
> 本节的表记录的是**其中一次采样**，这类单元应理解为「**在边界上，可能掉点**」，
> 不要当作稳定承诺。判断某个组合是否安全，请以「帧数 × RTT 是否**明显小于**采集频率」为准
> （留 20%~30% 余量），而不是以表里那一格的 0.0 为准。

**RTT=20ms**

| 协议 | scan=1000ms | scan=200ms | scan=100ms |
|---|---|---|---|
| ModBus.TCP | 0.0 | 79.7 | 89.0 |
| Mitsubishi.MC.TCP | 40.0 | 81.6 | 90.8 |
| Omron.FINS.TCP | 40.0 | 81.6 | 90.8 |
| Siemens.S7 | 0.0 | 56.0 | 74.4 |
| Omron.CIP | 40.0 | 88.0 | 92.0 |
| Rockwell.CIP | 0.0 | 79.2 | 89.6 |
| OPC.UA | 63.2 | 88.6 | 94.3 |

（表内为 drop%，越小越好；0.0 = 该组合可支撑。**注意**：贴近边界（帧数 × RTT ≈ 采集频率）
的格子读数会在 0 与更高档之间双稳，见上方「贴近边界的单元读数会跳变」。）

**三条结论：**

1. **RTT 一旦进入 10~20ms 量级，帧数就是唯一瓶颈**，CPU 反而完全不是问题。
   10 设备时 5000 点/台的绝对吞吐只有 5~6 万记录/秒，网关 CPU 大量空闲，
   但掉点已达 64%~94%——因为**单设备周期 = 帧数 × RTT** 已经超过采集频率，
   轮询被 in-flight 防堆积跳过。降低单设备点数或放宽采集频率是唯一的解法。
2. **scan=1000ms 是分水岭**：RTT=20ms 时只有帧数 ≤40 的协议（Modbus 40、S7 13、
   Rockwell 40）还能 0% 掉点；帧数 50 的 MC/FINS 掉 40%，帧数 80 的 CIP 掉 40%，
   OPC.UA 因假服务器单 goroutine 串行分发叠了额外排队，掉 63.2%。
3. **帧数少的协议在收紧采集频率时余量最大**：S7（13 帧）到 scan=100ms 才掉 74.4%，
   而 MC/FINS（50 帧）在 scan=100ms 已掉 90.8%。这直接印证「帧数决定容量」。

#### DLT645.TCP（DL/T 645 电能表）

DL/T 645 与其余协议有一个根本区别：**帧数不是由地址布局或合并窗口决定的，而是由
`maxDIsPerRead` 决定的**（帧数 = ⌈点数 / maxDIsPerRead⌉，5000 点 / 12 = 417 帧）。
它的出厂默认是 **12（协议上限）**，TCP 下 `interFrameDelayMs` 默认 **0**
（30ms 是 RS-485 收发器换向预留，透传链路由串口服务器 / DTU 自己处理；串口侧见下方注意事项）。

**驱动默认配置**（`maxDIsPerRead=12`、TCP `interFrameDelayMs=0`）：

| 点/台 | 扫描 | RTT 0 | RTT 10 | RTT 20 | 实际记录/秒（RTT=0） |
|---|---|---|---|---|---|
| 500 | 1000ms | 0.0 | 0.0 | 0.0 | 6k |
| 500 | 200ms | 0.0 | 64.0 | 76.0 | 25k |
| 500 | 100ms | 0.0 | 78.0 | 88.0 | 51k |
| 2000 | 1000ms | 0.0 | 40.0 | 60.0 | 24k |
| 2000 | 200ms | 0.0 | 88.0 | 92.0 | 104k |
| 2000 | 100ms | 0.0 | 94.0 | 96.0 | 204k |
| 5000 | 1000ms | 0.0 | 68.0 | 80.0 | 50k |
| 5000 | 200ms | 13.8 | 93.6 | 96.0 | 215k |
| 5000 | 100ms | 0.0 | 96.8 | 98.0 | 505k |

**抗 RTT 能力是各协议默认配置里最差的**：帧数只由 `maxDIsPerRead` 决定，而 12 已是协议上限，
所以 5000 点就是 417 帧 —— 比 MC / FINS 的 50 帧多 **8.3 倍**，抗 RTT 能力相应差 8 倍
（同为 5000 点 / 1000ms，RTT=10ms 时 MC / FINS 掉 0%、645 掉 68%；RTT=20ms 时是 40% 对 80%）。
「帧数 × RTT < 采集频率」这条容量公式对 645 同样成立，只是它的帧数把这条线压得很低 ——
500 点 / 42 帧在 RTT=20ms 下要 840ms，200ms 档必然掉点（实测 76.0%）；5000 点 / 417 帧
即使在 RTT=10ms 下也要 4.2s，所以 1000ms 档就掉 68%。

> ⚠️ **5000 点 / 200ms 那一格与左右不单调**（实测 13.8%，而更紧的 100ms 档反而是 0.0%）。
> 驱动侧不是瓶颈：`BenchmarkReadTCP`（`driversrc/dlt645/dlt645drv`，5000 点 / 12 = 417 帧）
> 实测单帧往返 21µs、47,482 帧/秒，一轮只要 8.7ms，远低于任何采集间隔。这一格疑似
> 采集引擎在该频率档的 tick 对齐取样问题，**不要据它推断驱动容量**；判容量请用
> 「帧数 × RTT」公式或该 benchmark。

**串口（DLT645.Serial）的注意事项**：

- `maxDIsPerRead=12` 也是串口默认值。
- `interFrameDelayMs` **保持默认 30ms 不要动** —— 它是收发器换向时间的预留，
  而假表是 TCP 的、**模拟不了 485 换向**，上表实测所用的「零延时」不适用于直连串口。
  现场要调小，请按「帧数 × 单帧实测周期 < 采集频率」逐步下探并观察丢帧。
- 串口的 Drain 只在上一轮没干净收尾时才真的去读：串口空口读一次要空等
  `serialReadTimeout`(20ms)，这个代价乘以帧数同样是纯开销。

##### 串口容量（无需串口硬件，用 `-serial-baud` 折算后实测）

**每帧往返实测**（单设备、`maxDIsPerRead=12`、每标识 4 字节数据、8E1；取 `scan=100ms`
使**轮时长成为唯一约束**，此时 `每帧 = 轮时长 ÷ 帧数`，量化误差 0.1s/15s ≈ 0.7%）：

| 波特率 | 点数 | 帧数 | 轮时长 | **每帧实测** | 每帧模型 | 偏差 |
|---|---|---|---|---|---|---|
| 2400 | 200 | 17 | 14.00s | **823.5ms** | 820ms | +0.4% |
| 9600 | 800 | 67 | 16.33s | **243.8ms** | 242.5ms | +0.5% |
| 115200 | 3000 | 250 | 17.00s | **68.0ms** | 66.0ms | +3.0% |

每帧模型 = 线路时间 + 表处理时间。线路时间 = 帧字节数 ÷ 波特率，2007 版读命令一帧为
`12 + 4N`（请求）+ `12 + N×(4 + 每标识数据字节)`（应答）= 168 字节（N=12）；表处理时间
取 50ms（见下方「实测输入」）。三档偏差都在 3% 以内，多出的是本机队列开销（每帧 1~2ms）。

**单表点数上限**（按 `帧数 × 单帧周期 ≤ 采集频率 × 0.7` 留 30% 余量）：

| 波特率 | scan=10s | scan=30s | scan=60s |
|---|---|---|---|
| 2400 | **~96 点** | ~300 点 | ~610 点 |
| 9600 | **~336 点** | ~1030 点 | ~2060 点 |
| 115200 | **~1220 点** | ~3700 点 | ~7400 点 |

边界另用 10 设备 × scan=10s 的对照跑印证过：100 / 300 / 1500 点均 0% 掉点，翻倍后
（200 / 800 / 3000 点）全部掉点，与该表一致。那一组的具体 drop% 数值不建议引用 ——
轮时长与测量窗口同量级时读数会双稳（见开头的边界警告）。

**提波特率的收益递减**（把每帧拆开看）：

| 波特率 | 线路时间 | 表处理（按 50ms 假设） | 线路占比 |
|---|---|---|---|
| 2400 | 770ms | 50ms | **94%** |
| 9600 | 192ms | 50ms | 79% |
| 115200 | 16ms | 50ms | **24%** |

交叉点在约 **38400bps**（168 字节 × 11 位 ÷ 50ms ≈ 37kbps）—— 超过它之后线路时间已小于
表处理时间，再提速几乎不再提升容量。2400 → 9600 拿到 3.4 倍，9600 → 115200 只有 3.6 倍
（本该是 12 倍）。**现场若表跑在 2400bps，提到 9600/19200 收益最大；提到 115200 之前
要先确认表本身的应答速度。**

**实测输入（引用上面数字前必须知道）**：

- **表处理 50ms 是假设值，不是实测** —— 合成假表给不出它，这是唯一需要真表校准的量，
  且波特率越高它对结果影响越大（115200 下占每帧的 76%）。校准办法：拿一块真表，
  看每帧实测比纯线路时间多出多少，那个差值就是它。
- 每标识按 **4 字节数据**（造数公式 `%08X:4:2` 的约定）。真表上不同 DI 是 2 / 3 / 4 字节，
  小一个字节即每帧少 12 字节 —— 2400bps 下少 55ms/帧。
- **8E1**（11 位/字节）；8N1 会快约 9%。
- 打包 12 相比逐点读仍快 2.6×（每点 64ms vs 165ms），串口上比 TCP 上更值得开。
- **上面 TCP 那张表对串口只有「帧数模型」可参考，绝对值不可套用。** 现场若真有上千点的表
  挂在 2400bps 上，调驱动参数救不了，只能提波特率或拆表。

**复现**：

```bash
# 单设备 + scan=100ms：轮时长成为唯一约束，每帧 = 轮时长 ÷ 帧数
go run ./cmd/loadtest -protocol dlt645 -devices 1 -points 200 -scan 100 \
  -warmup 20 -run 60 -serial-baud 2400 -latency 50
```

`-serial-baud` 按帧字节数折算线路时间并**叠加**到 `-latency`（后者留给表处理时间），
折算过程会打印出来供复核：

```
serial modeled: 2400bps 8E1 (11 bits/byte) × 168 bytes/frame = 770ms line time (+ -latency 50ms = 820ms per frame)
```

帧字节数**随打包数变化**，故 `-dlt645-dis` 会连带改变线路时间；不带它时按驱动默认的 12
折算。`-run` / `-warmup` 要按轮时长放大 —— 低波特率下一轮动辄几十秒，默认的 2s/5s
连一轮都跑不完。

> ⚠️ **别用虚拟串口对**（com0com / socat）压测串口：它们按内存速度传数据、
> **不模拟波特率时序**，每帧时间会接近 0，给出严重乐观的容量数字 —— 比不测更危险。

> 另注：`cycleMs` 列不可用于 645 的细粒度分析 —— 它取自 `DeviceLastSuccessTime`，
> 而该字段是**秒级**字符串，轮询周期小于 1s 时读数会被压平到 1s 的整数倍。上面串口实测的
> 轮时长都在 14s 以上，不受此影响；TCP 表的 drop% 与记录/秒是直接计数，同样不受影响。

### 优化方向
1. **帧数决定点位容量**：Modbus 125 寄存器/帧、MC 100 字/帧（可调 960）、FINS 100 字/帧、
   S7 462 字节/PDU、CIP 64 标签/帧（批量，可调）、Rockwell 125 元素/帧（数组）、
   OPC UA 100 节点/帧。同点数下帧数差 1~2 个数量级，容量随帧数线性走。
   CIP 批量读的收益本次已量化：5000 点从 5000 帧降到 80 帧，RTT=10ms 时掉点从
   80% 降到 0%（见上方「单读对照」表）——**批量读是 CIP 可用的前提**。
   **DL/T 645 是同一条规律最极端的例子**：帧数只由 `maxDIsPerRead` 决定，出厂即
   12（协议上限），5000 点/台 @1s 为 417 帧，50 设备 × 5000 点（25 万点）实测
   30 万记录/秒、drop 0.0%。详见上方 645 专节。
   稀疏点位（间隙 > 合并窗口）帧数按点数量级放大——生产配置应尽量连续/规整地址。
2. **配置 watcher 全表 checksum 是扩展瓶颈**：`collector.Engine.loadConfigChecksum` 每 10s
   `SELECT * FROM device_address WHERE status=1` 全表加载+哈希。100 万地址时单次 1.7s、
   内存数 GB，与大点位场景直接冲突。点位海量时建议改为增量/db 变更感知，或拉长巡检间隔。
3. **高吞吐掉点是 CPU 上限，不是 worker 池**。压测验证：`worker pool full` 日志在
   ≤200 设备时从不触发（队列 1024 ≫ 最大排队量）；且把 worker 数从 32 加到 64，
   掉点反而从 16.1% 恶化到 19.4%（CPU 已饱和，加并发徒增上下文切换）。profile 显示
   热点是驱动解码/格式化 + 采集记录构建 + GC 分配压力。已优化 `collector.toRecords`
   （每记录两次 map 查询 → 索引对齐直取，实测 toRecords CPU 从 13.7% 降到 1.7%）；
   后续可再优化驱动侧格式化（值未变跳过重格式化）与每轮 `RangeSig` 缓存键重算。
   **【待复核】** 以上 worker 数实验采自**进程内驱动时期**；插件化后热点多了
   插件 RPC 的请求/响应编解码与 IPC，本轮 237 组读数**没有重跑该实验**，
   「加 worker 反而恶化」这一条在新架构下尚未验证，暂按定性参考。
