### Added

- **DL/T 645 插件新增点位扫描：`DLT645.Serial` 与 `DLT645.TCP`**（插件版本 1.0.0 → 1.1.0）。至此电能表也能在设备地址页用「自动发现点位」按钮把一块表读得出来的数据标识列成清单。**网关侧与前端零改动**：扫描能力本来就由插件在 `Meta` 里声明、由 `pluginhost` 每次遍历 `m.plugins` 现算（不建缓存表），`APIVersion` 不变；DL/T 645 在 premium 侧没有黄金基线（`pluginhost/testdata/parity/**` 里本来就没有它），所以也没有东西需要重新生成。前端 `addressSyntax.js` 里 dlt645 的写法规格（`02010100`、`00000000`、`12345678:2:0:s`）早就存在，这次只是让扫描结果真的落在那一族写法上。
  **这是第五种形态：字典枚举，且带采样值。** 前四种（Modbus/S7/FINS/MC 扫一段地址、Rockwell 让设备交标签表、OPC UA 按层 Browse）都不是这个形状 —— DL/T 645 有一份**标准化的数据标识字典**（`dlt645drv/dictionary.go`，2007 版 44 条 / 1997 版 18 条），所以点位来自**协议自己的一张清单**而不是设备自报；同时"读一遍"既是判定这块表有没有该数据标识的手段、又顺带取到了值，于是**结果级 `AssumedCommonDataType` 与逐点的 `CommonDataType` 同时非空**。两处必须说清楚，否则下一个人会按 Rockwell/OPC UA 那份照抄：① **逐点类型不是因为"原生枚举"才有的**，而是因为**同一协议里每个点位的类型可以不同**（645 的输出形态由数据标识本身决定 —— 表号是 6 字节 BCD 数字串、运行状态字是二进制位域、电量是 2 位小数的工程值，全都在 DI 里，见 `decode.go`）；② **结果级那个非空的值不是"为了保证能读而假设的类型"** —— 对 645 而言类型从不影响读取，它的实际作用是**告诉前端"本次结果带采样值"**（前端据它点亮「显示 0 值」开关、并换用「读得到/读不到」的措辞）。留空会隐藏那枚开关，而 645 的零值是常态（未接线相的电流就是 0），用户会因此看不到一整类点位。
  **一处只有"一帧打包多项、且各项长度不同"的协议才会遇到的判据：成帧打包要先核对应答数据域的总长。** 回显校验（应答回显的数据标识必须与请求一致）**只保证"这一项的标识对"，不保证"这一项的数据落在正确的位置"**：设备少回一项的数据时，后面每一项的窗口都会整体前移，解出的是一个**看似合理实为别处**的值，而它会被算成"读到了"——真机上完全看不出来。总长不足是这一情形的必要条件，因此拿它当判据降级为逐个重读；单点读时窗口无从错位。顺带把"回显校验"这套逻辑从采集路径的 `fillResults` 里抽成了一个**纯函数**（`codec.go` 的 `fieldSlice`），两处共用同一份实现，而四条失败分支的用户可见日志文案**逐字未动**。
  **还有两处协议特有的形态**：① **1997 版每帧只能带一个数据标识**（与 `plan.go` 的 `buildPlan` 逐字同一条规则）——照抄 `maxDIsPerRead` 会让单帧数据域超过 `maxDataLen1997`，而 `parseAt` 对超长的 `L` 直接判"不是帧头"，**设备的合法应答永远解析不出来**，症状是每一帧都超时（看起来像"设备不在"，而不是"参数配错了"）；② **不做「读到第一个读不到就停」**（FINS/MC 那条捷径）——数据标识字典**不是连续地址空间**，一块表完全可能实现了高位的某个电力参量而没有低位的另一个；**也不做请求数上限**——降级树是有界的（每块最多一次批量帧 + `maxDIsPerRead` 次单读，不是 S7/MC 的满二叉树）。这两条都在代码注释里写明是**有意为之**，不是漏配。
  **一处有意偏离 `specs/point-discovery.md` §6「连接类错误必须中止」**：645 的「静默」有歧义 —— 规范规定设备对不支持的数据标识回异常应答（0xD1），但老表与廉价表常常**干脆不答**。因此一个数据标识静默（超时）之后，先**复探一次**各版本最普遍实现的数据标识（与「测试连接」用的是同一个）把"设备掉线"排除掉：通了 ⇒ 该数据标识记「读不到」并继续；不通 ⇒ 中止并带上已得的部分结果。这与 FINS「结束码错误也算设备」同类（**拒绝应答也证明对面在**）。**它成立的前提（静默 == 这块表没有这个 DI）无法从仓库验证，需要真机确认**，这条已写进代码注释与 `Description`。同块内只复探一次，否则一张有 n 个静默条目的表要花 2n 帧才问得完；而一块里只要有**一个**静默条目，超时定位不到是哪一个，所以那一块会整体降级为逐个重问 —— 不这样做的话同块其余十几个会被一个不答的条目一起废掉。
  **地址写法：字典条目写裸数据标识，字典外的才写显式后缀。** 字典命中的条目（`02010100` / 1997 的 `9010`）由 `ParseAddress` 从字典把长度、小数位、符号、编码全部补齐，把字典的默认值抄进位点地址只是多了一份可能与字典不一致的副本；字典**未收录**的厂商私有数据标识则**必须**显式写出长度（`12345678:4:2:s`），因为 `ParseAddress` 对它们宁可报错也不猜一个长度。扫描表单因此只有一个可选项「附加数据标识」（按同一套地址语法，逗号/分号/顿号/换行分隔，最多 64 条），**与字典条目重复时以附加的为准** —— 静默让字典赢就是"用户改了配置但它没生效"那类最难查的问题。标签取字典自带的中文名并附上单位（`A相电压（V）`）：本功能里少见的"确实有标签来源"的情形。
  **设备扫描刻意不做**（两个协议都不声明 `Discovery`），由 `main_test.go` 的 `TestNoDeviceScan` 钉住，免得被后人顺手加上：`DLT645.Serial` 按契约不得声明（目标模型是 host/port，表达不了 comPort）；`DLT645.TCP` 虽然可以，但它连的是**串口服务器 / DTU**，与 `Omron.FINS.HostLinkTCP` 同形，而 FINS 也刻意不声明。DL/T 645-2007 确有广播「读通信地址」(控制码 13H → 应答 93H，应答帧地址域回填真实表号) 能枚举**一条 RS-485 总线上的表**，但那回答的是"这条总线上挂着哪些表"，不是"网段里有哪些主机" —— 是另一个功能（对应 `specs/device-scan.md` §9 里"串口的「总线上有哪些站号」"那一格），且 1997 版的广播语义无依据、无真机可验证。按"不做而不是猜着做"：留 nil，并在两篇 spec 里各写清理由。
  **测试抓到的一个真缺陷**：附加数据标识那一栏是 textarea，用户按手册**一行一个**粘进来时换行在 JSON 里正是以 `\n` 的形式过来的，而容错文本类型的实现最初只把首尾引号 trim 掉、没有做 JSON 反转义 —— 结果是每一条附加数据标识都带着一个字面量 `\n` 去解析，报错还说的是"标志无法识别"，指着完全无关的地方。改成走 `json.Unmarshal` 解字符串后修复（`TestParsePointScanOptions` 的"分隔符与容错文本"那格就是它的回归）。
  验收：`dlt645drv/pointscan_test.go` 覆盖地址往返（**两个版本的全部字典条目** + 一批贴着上下限的附加规格：8 字节 / 16 位小数、有符号 + 二进制、以及与字典条目重复的覆盖，并断言字典条目**原位**保留）、逐点类型与解码内部类型自洽（且 2007 字典确实覆盖日期/表号/位域/数值四类）、**值来自它自己那个数据标识的位置**（假设备把"值"设成点位自己的地址写法，错位立刻显形，同时断言交给设备的请求顺序恰好是目标清单按序分组的结果）、零值点位照样列出且只给 note、整块被拒 ⇒ 降级逐个（且此后不再重试批量）、单点被拒 ⇒ 记"读不到"且**不触发**存活复探（异常应答分明证明设备答了）、后续帧标志 ⇒ 该点位记"读不到"、**静默但链路仍通 ⇒ 记"读不到"并继续（同块内只复探一次）**、静默且复探也不通 ⇒ 中止且 `readable`/`unreadable` 都是 0、中止时带部分结果、预算耗尽 ⇒ `Incomplete` 且**不报错**、一开始就过期 ⇒ 一个请求都不发、三条计数不变量、`MaxPoints` 截断时超出的条目**不计入统计**；另有**走真实封帧/收发/解析路径**的四条（正常应答逐项取值、回显不符只跳过那一项、数据域短了报整帧不可采信、控制码带后续帧标志被拒）与 `fieldSlice` 四种结论、`ScanPoints` 的预检（未连接）、以及**整本 44 条字典走完 `ScanPoints` 的端到端**；`dlt645/main_test.go` 补能力/实现配对、声明字段（`DefaultCommonDataType` 必须是 `TypeMap` 的键、两个协议的声明逐字段相同）与 `TestNoDeviceScan`；`pluginhost/dlt645plugin_test.go` 用**真实的插件产物**跑一次 `DiscoverPoints`（能力过线、帧 RPC、插件进程内的临时实例建连、逐点类型能在网关侧 `LookupDataType` 命中、假表没回数据的数据标识如实记成"读不到"而不是整段丢弃）。
  **DL/T 645 gains point scan: `DLT645.Serial` and `DLT645.TCP`** (plugin version 1.0.0 → 1.1.0). Electricity meters can now have the data identifiers a meter actually answers listed, via the "Discover points" button on the device-address page. **No gateway change and no front-end change**: scan capability is declared by the plugin in `Meta` and recomputed on every call by `pluginhost` (which walks `m.plugins` rather than caching), `APIVersion` is unchanged, and DL/T 645 has no golden fixture in the first place (`pluginhost/testdata/parity/**` never held one), so there is nothing to regenerate. `addressSyntax.js` already carried the dlt645 address spec (`02010100`, `00000000`, `12345678:2:0:s`); this change is what makes scan results land in it.
  **This is a fifth shape: dictionary enumeration that also carries sample values.** None of the four existing ones look like it — Modbus/S7/FINS/MC sweep an address range, Rockwell has the device hand over its tag table, OPC UA browses level by level — because DL/T 645 has a **standardised data-identifier dictionary** (`dlt645drv/dictionary.go`, 44 entries in the 2007 edition and 18 in the 1997 one). So the points come from **the protocol's own list** rather than from the device, and since reading is both how readability is decided and how the value arrives, **the result-level `AssumedCommonDataType` and the per-point `CommonDataType` are non-empty at the same time**. Two things must be spelled out or the next author will copy the Rockwell/OPC UA entry instead: ① **per-point types are not a privilege of "native enumeration"** — they belong to any protocol where **the type can differ from one point to the next** (DL/T 645's output form is decided by the identifier itself: a meter number is a 6-byte BCD digit string, a status word is a bit field, energy is an engineering value with two decimals — all of it inside the DI, see `decode.go`); ② **the non-empty result-level value is not "the type assumed in order to read"** — for DL/T 645 the type never affects reading, and its real job is to tell the front end **that this result carries sample values** (that is what lights up the "show zero values" toggle and switches the wording to "readable / unreadable"). Leaving it empty hides that toggle, and zeros are normal on a meter (the current of an unconnected phase is exactly 0), so a whole class of points would go unseen.
  **One criterion only a protocol that packs several items into one frame — with each item a different length — can run into: a packed frame must check the total length of the response data field.** The echo check (the identifier echoed back must match the one requested) **only proves "this item's identifier is right", not "this item's data sits in the right place"**: when a device omits one item's data, every later item's window shifts forward and what comes out is a **plausible-looking value belonging to somewhere else**, counted as "read successfully" — invisible on real hardware. A short total is a necessary condition for that situation, so it is the trigger for degrading to one identifier per frame; a single-identifier read has no window to shift. While there, the echo check was extracted from the collection path's `fillResults` into a **pure function** (`fieldSlice` in `codec.go`) shared by both callers, with all four failure branches' user-visible log text left **byte-for-byte unchanged**.
  **Two more protocol-specific shapes**: ① **the 1997 edition carries exactly one data identifier per frame** (word for word the same rule as `buildPlan` in `plan.go`) — copying `maxDIsPerRead` pushes the data field past `maxDataLen1997`, and `parseAt` rejects an over-long `L` as "not a frame header", so **a legitimate reply can never be parsed** and the symptom is that every frame times out (looking like "the device is absent" rather than "the parameter is wrong"); ② **no "stop at the first unreadable point"** (the FINS/MC shortcut) — the identifier dictionary **is not a contiguous address space**, and a meter may well implement a high-valued electrical quantity while lacking a low one; **and no request-count cap** — the degradation tree is bounded (at most one packed frame plus `maxDIsPerRead` single reads per chunk, not S7/MC's full binary tree). Both are called out in comments as **deliberate**, not as omissions.
  **One deliberate deviation from `specs/point-discovery.md` §6 ("connection-class errors must abort")**: silence is ambiguous on DL/T 645 — the spec says a device answers an unsupported identifier with an exception response (0xD1), but old and cheap meters routinely **simply don't answer**. So after a silent (timed-out) identifier the finder **probes once** for the data identifier every edition implements (the same one "Test connection" uses) to rule out "the device is gone": if it answers, that identifier is recorded as "unreadable" and the scan continues; if not, the scan aborts with the partial results in hand. This is the same family of trade-off as FINS's "an end-code error still means a device" (**a refusal to answer also proves the peer is there**). **The premise it rests on (silence == this meter lacks this DI) cannot be verified from the repo and needs hardware confirmation** — stated in the code comment and in the `Description`. The probe happens at most once per chunk, otherwise a meter with n silent entries would take 2n frames to get through; and because a timeout cannot say *which* identifier was ignored, a chunk containing even one silent entry degrades wholesale to one identifier per frame — without that, the other eleven entries in the same chunk would be written off along with the one that stayed quiet.
  **Address form: bare data identifiers for dictionary entries, explicit suffix only outside the dictionary.** A dictionary hit (`02010100`, or `9010` on the 1997 edition) has its length, decimals, sign and encoding filled in by `ParseAddress` from the dictionary — copying the dictionary's defaults into the point address only creates a second copy that can drift; a vendor-private identifier **not** in the dictionary **must** state its length (`12345678:4:2:s`), because `ParseAddress` would rather fail than guess a length. The scan form therefore has a single optional field, "additional data identifiers" (same address syntax, separated by commas, semicolons, enumeration commas or newlines, at most 64), where **an entry colliding with the dictionary wins** — silently letting the dictionary win is the "I changed the config but it didn't take effect" class of bug. Labels come from the dictionary's own Chinese name with the unit appended (`A相电压（V）`): one of the rare cases in this feature where a label source genuinely exists.
  **Device scan is deliberately not implemented** (neither protocol declares `Discovery`), pinned by `TestNoDeviceScan` in `main_test.go` so nobody adds it by reflex: `DLT645.Serial` may not declare it by contract (the target model is host/port and cannot express a comPort), and while `DLT645.TCP` could, it connects to a **serial server / DTU** — the same shape as `Omron.FINS.HostLinkTCP`, which deliberately declines as well. DL/T 645-2007 does have a broadcast "read communication address" (control code 13H → response 93H, with the response echoing the real meter address) that enumerates **the meters on one RS-485 bus**, but that answers "which meters hang off this bus", not "which hosts are on this subnet" — a different feature (the "which stations are on the bus" cell in `specs/device-scan.md` §9), and the 1997 edition's broadcast semantics have no basis and no hardware verification. Per the repo's "not doing it rather than guessing" rule: nil, with the reasoning recorded in both spec files.
  **A real defect the tests caught**: the additional-identifier field is a textarea, and when a user pastes one identifier per line the newlines arrive in the JSON as `\n`; the tolerant text type originally only trimmed the surrounding quotes without JSON-unescaping, so every pasted identifier went to the parser carrying a literal `\n` — and the error blamed an "unrecognised flag", pointing somewhere entirely unrelated. Fixed by decoding through `json.Unmarshal` (the "separators and tolerant text" case in `TestParsePointScanOptions` is its regression).
  Acceptance: `dlt645drv/pointscan_test.go` covers address round-tripping (**every dictionary entry in both editions** plus awkward additional specs: 8 bytes / 16 decimals, signed + binary, and an override colliding with a dictionary entry, asserting dictionary entries keep their **original positions**), per-point type matching its decoding internal type (with 2007 actually covering the date / meter-number / bit-field / numeric classes), **values coming from the position of their own data identifier** (the fake device sets each "value" to the point's own address string so a mix-up is immediately visible, while also asserting the request order handed to the device is exactly the target list grouped in order), zero-valued points still being listed with a note and no value, a rejected chunk degrading to single reads (and no longer retrying batching afterwards), a single rejection counting as "unreadable" **without** triggering the liveness probe (an exception response plainly means the device answered), the follow-up-frame flag marking that point unreadable, **a silent identifier on a live link counting as "unreadable" while the scan continues (probing at most once per chunk)**, silence with a dead link aborting with `readable`/`unreadable` both zero, aborts carrying partial results, budget exhaustion yielding `Incomplete` **without** an error, an already-expired deadline issuing no request at all, the three counting invariants, and `MaxPoints` truncation leaving the over-limit entries **uncounted**; plus four cases driving the **real framing / transport / parsing path** (a normal reply decoding item by item, an echo mismatch skipping only that item, a short data field marking the whole frame untrustworthy, and a follow-up-frame control code being refused), the four `fieldSlice` verdicts, `ScanPoints`' preflight (not connected), and an **end-to-end run of `ScanPoints` over all 44 dictionary entries**; `dlt645/main_test.go` gains the capability/implementation pairing, the spec fields (`DefaultCommonDataType` must be a `TypeMap` key, both protocols' declarations identical field by field) and `TestNoDeviceScan`; `pluginhost/dlt645plugin_test.go` runs `DiscoverPoints` against the **real plugin binary** (capability crossing the wire, the frame RPC, the throwaway instance connected inside the plugin process, per-point types resolving through the gateway's `LookupDataType`, and identifiers the fake meter returned no data for being recorded as "unreadable" rather than discarding the whole chunk).

- **OPC UA 插件新增设备扫描与点位扫描：`OPC.UA`**（插件版本 1.0.0 → 1.1.0）。至此 OPC UA 服务器也能在「局域网扫描发现」页被扫出来、在设备地址页用「自动发现点位」按钮拿到它地址空间里的节点清单。**网关侧与前端零改动**：扫描能力本来就由插件在 `Meta` 里声明、由 `pluginhost` 每次遍历 `m.plugins` 现算（不建缓存表），`APIVersion` 不变，黄金基线（`pluginhost/testdata/parity/**`）也不需要重新生成 —— 前端 `addressSyntax.js` 里 opcua 的写法规格（`ns=2;s=Temperature`、`Root/Objects/2:Device/2:Temp`）早就存在，这次只是让扫描结果真的落在那一族写法上。
  **设备扫描的判据是「读回一份自洽的端点表」，不是「4840 端口开着」**——4840 上跑着 HTTP 管理页、串口服务器、另一个厂商的私有协议都很常见，而它们不会回一份 OPC UA 二进制编码的 `EndpointDescription` 列表。探测调的是 OPC UA **自带的发现服务** `GetEndpoints`：规范允许它在「只建立了 SecureChannel、尚未 `CreateSession`」时调用，所以一次探测是「拨号 → OpenSecureChannel → GetEndpoints → 关闭」，**不建立会话、也不校验认证**。最后那半句必须写进 `Description`：用户名密码错、证书不受信的服务器照样会被列出来，这要到采集时才会暴露，用户不会从界面上别的地方看出来。
  **这里有一条别处没有的三分法，是本功能最需要小心的一处**：不是 OPC UA / **是 OPC UA 但拒绝了我们的安全参数** / 是 OPC UA。判据落在错误的**来源**上：`*uacp.Error` 与服务级 `ua.StatusCode` 只有 OPC UA 对端发得出来，因此都算命中；其中安全策略与证书那一族状态码（`BadSecurityPolicyRejected` / `BadSecurityModeRejected` / `BadCertificate*` 等）另走「照样列出 + 在 `Extra` 里明确告警」那一支——一台只提供加密端点的服务器是**真实存在的设备**，静默不报会让用户从「扫不到」得出「那里没有 OPC UA 服务器」的错误结论，而网关当前未实现客户端证书、建了也确实连不上，这两件事都要让用户同时看到。反面则要挡住 gopcua **本地合成**的 `StatusBadTimeout`：它既可能是「对面根本不应答」也可能是「对面在 OPN 之后用裸 ERRF 静默拒绝」（两者无从区分），一律按「不是我们的设备」处理——**误报一台连不上的幽灵设备比漏报更费用户的时间**。另外**只做 `GetEndpoints`、不调 `FindServers`**：后者能列出同一台主机上在 LDS 注册的其它服务器，但那是「一个目标产出多台设备」的形态，而 `discoveryUrls` 里的主机名未必可解析、指向本机的 URL 未必指向被探测的那台，逐主机单播 + 一台设备的结果可预期得多。
  **点位扫描走 `Browse` 原生枚举**，落在 `specs/point-discovery.md` §1 点名、`driversdk.FindPointsRequest.Session` 注释预留的那个位置上（与 Rockwell 的 CIP Symbol Object、ABB 的 RWS 信号表、DLT645 的数据标识字典同类）。**但有三处不能照抄 Rockwell 那份**：① Rockwell 的枚举是「整只对象」操作、**超预算时拿不到部分结果**，所以它报错；OPC UA 是按层推进的、停在哪儿就有多少，因此**带着已完成的部分正常返回并把 `Incomplete` 置位**，把那个报错搬过来只会让用户丢掉几百个已经问出来的点位。② 它**有分块**（一块一次 `Session.Do`，块间让锁），Rockwell 没有。③ 它的瓶颈是**请求数**，所以 Browse 与属性读取都必须批量——`ua.BrowseRequest.NodesToBrowse` 是切片、一次能问一整块，`DataType` 属性按 `MaxBatch` 切子批读；退化成「一节点一请求」不会报任何错，只是扫描会在预算耗尽时停在半程，症状是「清单莫名其妙断了一半」。顺带避开一个静默坑：库里 `Node.References` 一次只发一个 `BrowseDescription`，收续页时又只读 `results[0]`，多节点时其余节点的续页会被**静默丢掉**（客户端自己实现了 `BrowseBatch`，续页合并成一次 `BrowseNext`）。
  **自定义/枚举类型要沿逆 `HasSubtype` 上溯。** 一个节点的类型是**另一个节点的 NodeID**，而自定义枚举与厂商结构体都活在服务器自己的命名空间里——现实里最常见的链是「自定义枚举 → `Enumeration` → `Int32`」两跳，所以「只看直接父节点」的实现会把一整类点位判成不可映射而丢掉。上溯**一层一个 `BrowseRequest`** 覆盖该层全部待解析类型（不是一类型一请求），层数与类型数都有上限，解析不出来就跳过并计入「未列出」。
  **类型映射只能是 Kind 等价，这不是将就。** OPC UA 的 `int32` / `uint64` / `byteString` 在系统里没有**同名**的通用类型（`opcuadrv/metadata.go` 早就写明了它们只有内部裸名、没有通用名入口），而 `TypeMap` 的键集被黄金基线钉死（`pluginhost/testdata/parity/typemap/opcua.json` 只能由已移除的内置实现重新生成，加第 12 个键就是让那条 parity 测试变红）。于是 Int32→Long、UInt64→DWord、SByte→Char、ByteString→String。**这在行为上正确**：本协议的采集路径从不做字节级解码（服务器返回原生值，`DataType` 只决定 Kind），而这几对的 Kind 完全相同、格式化结果也一致；名字上的差异由该行的 `Note` 补上（「OPC UA 基础类型 Int32」）——原生枚举下前端正是把 `Note` 渲染在「采样值」那一列，那是用户唯一能对上设备手册的地方，因此它**只在真的不一致时才加**，每一行都挂一条会让那一列变成噪声。
  **地址往返在这里的理由与 Modbus/S7 完全不同，别照抄那套论证。** 那三个协议防的是「一个解析不出来的地址让**整台设备的采集**全部失败」（驱动的区间规划全量解析、遇第一个非法地址就报错）；OPC UA 不是这样——`opcuaDriver.Read` 对 `*parseError` 与 `ua.StatusCode` 都是**逐点** Quality=0 继续。危险在别处，而且更难发现：`parseAddress` 把**任何含 `/` 的串**当浏览路径，于是一个完全合法的字符串 NodeID `ns=2;s=Room1/Temp` 会被解析成一条**别的**路径；解析不到还算好，**解析到另一个同名节点才是灾难**——那个点位会永远采到别人的值，在时序库里表现为一条完全合理的曲线。这条陷阱早已作为手工输入的坑写在前端（`pitfallOpcuaSlash`），这里只是让 finder **自己不去产生**它：地址优先写 `NodeID.String()` 但**先用 `parseAddress` 解析回来逐字比对**，不过就退到**下行时逐段累积**出来的浏览路径（按构造可达），再不过就计入「未列出」——绝不放一个没验证过的地址进结果。路径段的渲染规则也逐条对着 `parsePathSegment` 的分支写：名字为空 / 含 `/` / 首尾空白一律拒绝，而 `ns` 前缀**不是**「ns!=0 才写」而是「ns!=0 **或** 名字里有 `:` 就写」（裸写 `Motor:1` 会被解析器读成命名空间 `Motor` 并当场报错）。同父下**重名**的兄弟会渲染出同一条地址串（撞 `(device_id, name)` 复合唯一，路径解析还只取第一个目标），因此那一支整体放弃路径写法——但**不丢**这些点位，它们仍然可以用 NodeID 寻址。
  **三处「不做而不是猜着做」**：① **不读采样值**（与 Rockwell 同一个选择，理由不同：类型来自 `DataType` 属性、与值无关，不读值不影响类型），因此结果级的 `AssumedCommonDataType` 留空、每个点位自带 `CommonDataType`，前端走已有的原生枚举分支（隐藏「显示 0 值」开关、换用「列出/未列出」文案）；② **不实现 `ConnectionMatcher`**，点扫开临时实例，与 Rockwell/S7/Modbus TCP 的惯例一致（网关现有的「测试连接」走的就是这条路，已在现场验证过），代价是扫描期间多一个会话；③ **不猜型号厂商**：`GetEndpoints` 不带会话、服务器不报这些，`Vendor/Model/Version` 一律留空——拿协议名冒充设备自述会让用户以为那是设备说的。
  验收：`opcuadrv/probe_test.go` 打真实套接字与真实服务器，覆盖命中（含**端口不是默认 4840** 的那一格）、HTTP 服务/连上就断/端口全闭三种「没扫到」、不可达目标的耗时上界（防的是漏传 `DialTimeout`/`RequestTimeout` 让库默认的 10s 兜底）、广播目标被跳过、**`protocol_json` 能被插件自己的 `ParseOpcUaConfig` 原样还原且端口是数字**（写成字符串会被 `json.Unmarshal` 静默丢弃、回落成 4840，用户改过端口的设备一键建出来就连不上）、以及**三分法的 12 个判据逐条**（含"本地合成的超时一律按不是我们的设备处理"）；`opcuadrv/pointscan_test.go` 对**真服务器 + 真驱动**跑通整棵树（含每个地址都能被 `parseAddress` 还原回同一节点、结果级类型必须留空、每一点都必须自带 TypeMap 的键），另有段渲染/路径往返/NodeID 往返/内建类型映射（14 个可映射码 + 8 个必须拒绝的码 + 三个上溯终止节点）/Note 只对近似映射出现/选项解析各一组；`opcuadrv/crawl_test.go` 用可控桩覆盖真服务器上造不出来的形态：**DataType 必须批量读**（250 个变量按 `MaxBatch` 恰好 3 次请求）、**Browse 续页收干净**、`MaxPoints` 截断且 `readable+unreadable==scanned` 不破、**请求数触顶 ⇒ 带部分结果 + `Incomplete` 而不报错**、`maxDepth` 只挡往下的层级、标识符里带 `/` 的字符串 NodeID **退到浏览路径**、同父重名兄弟双双进「未列出」而对照组照常列出、单节点读不回来只跳过它、方法与视图不计数；`testutil/fake/opcua.go` **附加式**新增一个带可浏览地址空间的假服务器（原来的压测假服务器没有引用关系、Browse 不到任何东西，拿它测等于什么都没测），并记下两处 gopcua server 包的脾气：节点必须挂在 **ns=0** 的 Objects 文件夹上（`NewNodeNameSpace` 建的是命名空间局部的 `ns;i=85`），且不能用 `AddObject`/`AddVariable`（它们留 nil 反向指针、也不登记进命名空间 map）；`opcua/main_test.go` 补两条能力/实现配对的不变式（漏配会让插件**启动即失败**）与规格钉住（4840、unicast、各项预算落在 `Meta.Validate` 的区间内、`DefaultCommonDataType` 必须是 `TypeMap` 的键）。
  **OPC UA's plugin gains both device scan and point scan: `OPC.UA`** (plugin version 1.0.0 → 1.1.0). OPC UA servers can now be discovered from the "LAN device scan" page and have their address space listed from the "Discover points" button on the device-address page. **No gateway change and no front-end change**: scan capability is declared by the plugin in `Meta` and recomputed on every call by `pluginhost` (which walks `m.plugins` rather than caching), `APIVersion` is unchanged, and no golden fixture needs regenerating (`pluginhost/testdata/parity/**`) — `addressSyntax.js` already carried the opcua address spec (`ns=2;s=Temperature`, `Root/Objects/2:Device/2:Temp`), and this change is what makes scan results land in it.
  **Device scan's criterion is "a self-consistent endpoint table came back", not "port 4840 is open"** — HTTP admin pages, serial servers and other vendors' protocols all sit on 4840, and none of them answer with an OPC UA binary-encoded `EndpointDescription` list. The probe calls OPC UA's **own discovery service**, `GetEndpoints`, which the spec permits before `CreateSession` on a freshly opened SecureChannel, so one probe is "dial → OpenSecureChannel → GetEndpoints → close": **no session, and no authentication check**. That last half must be stated in the `Description` — a server with wrong credentials or an untrusted certificate is still reported, and that only surfaces at collection time, which the user cannot tell from anywhere else in the UI.
  **There is a three-way verdict here with no precedent in the other plugins**: not OPC UA / **is OPC UA but rejected our security parameters** / is OPC UA. The test is where the error came from: `*uacp.Error` and service-level `ua.StatusCode` can only be emitted by an OPC UA peer, so both count as a hit; within those, the security-policy and certificate family (`BadSecurityPolicyRejected` / `BadSecurityModeRejected` / `BadCertificate*`) takes the "list it anyway plus a clear warning in `Extra`" branch — a server offering only encrypted endpoints **is a real device**, and staying silent would drive the user from "not found" to the wrong conclusion "there is no OPC UA server there"; at the same time the gateway has no client-certificate support today, so a device created from that row genuinely will not connect, and both facts have to be visible at once. The converse must be blocked: gopcua **synthesises** `StatusBadTimeout` locally, and it is equally consistent with "the peer never answered" and "the peer silently rejected us with a bare ERRF after the OPN" — the two are indistinguishable, so it is treated as "not our device", because **a ghost device reported as connectable costs the user far more time than a miss**. Also **`GetEndpoints` only, no `FindServers`**: the latter would list other servers registered with a host's LDS, but that is the "one target, many devices" shape, and the `discoveryUrls` in it may name unresolvable hosts or point at a different machine than the one probed — per-host unicast with one device per host is far more predictable.
  **Point scan uses `Browse` native enumeration**, landing exactly on the slot named in `specs/point-discovery.md` §1 and reserved by `driversdk.FindPointsRequest.Session`'s comment (alongside Rockwell's CIP Symbol Object, ABB's RWS signal table and DLT645's identifier dictionary). **But three things cannot be copied from the Rockwell implementation**: ① Rockwell's enumeration is an all-or-nothing operation with **no partial results on budget exhaustion**, so it errors; OPC UA walks level by level, so wherever it stops it already holds results — it therefore **returns normally with the completed portion and `Incomplete` set**, and transplanting that error would only throw away several hundred points the scan had already asked for. ② It **has chunking** (one `Session.Do` per chunk, releasing the lock in between), which Rockwell does not. ③ Its bottleneck is the **request count**, so both Browse and attribute reads must be batched — `ua.BrowseRequest.NodesToBrowse` is a slice, so one request covers a whole chunk, and the `DataType` attribute is read in `MaxBatch`-sized sub-batches; degrading to one request per node reports no error at all, it just stops the scan halfway through the budget, and the symptom is "the list mysteriously ends in the middle". One silent trap is dodged in passing: the library's `Node.References` sends a single `BrowseDescription` and only reads `results[0]` when draining continuations, so with several nodes every other node's continuation is **silently dropped** (the client grew its own `BrowseBatch`, merging continuation handling into one `BrowseNext`).
  **Custom and enum types must be walked up the inverse `HasSubtype` chain.** A node's type is **another node's NodeID**, and custom enums and vendor structures live in the server's own namespace — the commonest chain in practice is "custom enum → `Enumeration` → `Int32`", two hops, so an implementation that only inspects the immediate parent drops an entire class of points as unmappable. The walk issues **one `BrowseRequest` per level** covering every still-unresolved type at that level (not one request per type), with bounds on both depth and distinct types; anything unresolved is skipped and counted as "not listed".
  **The type mapping can only be Kind-equivalent, and that is not a compromise.** OPC UA's `int32` / `uint64` / `byteString` have no **same-named** common type in this system (`opcuadrv/metadata.go` has said all along that they have only internal bare names and no common-name entry point), and the `TypeMap` key set is pinned by a golden fixture (`pluginhost/testdata/parity/typemap/opcua.json` can only be regenerated by the removed built-in implementation; adding a 12th key turns that parity test red). Hence Int32→Long, UInt64→DWord, SByte→Char, ByteString→String. **This is behaviourally correct**: this protocol's collection path never does byte-level decoding (the server returns native values and `DataType` only picks the Kind), and each of those pairs shares a Kind and formats identically; the name difference is covered by a per-row `Note` ("OPC UA base type Int32") — under native enumeration the front end renders `Note` in the "sample value" column, which is the only place a user can line a row up against the device manual, so it is added **only when the names genuinely differ**; one on every row would turn that column into noise.
  **The address round-trip argument here is entirely different from Modbus/S7 — do not copy that reasoning.** Those three guard against "an address that fails to parse **stops the whole device from collecting**" (the driver plans ranges by parsing every address and errors on the first bad one); OPC UA is not like that — `opcuaDriver.Read` treats both `*parseError` and `ua.StatusCode` as **per-point** Quality=0 and moves on. The danger lies elsewhere and is harder to spot: `parseAddress` treats **any string containing `/`** as a browse path, so a perfectly legal string NodeID like `ns=2;s=Room1/Temp` is parsed as a **different** path; failing to resolve is the benign outcome, and **resolving to a different node with the same name is the disaster** — that point then reads someone else's value forever, showing up in the time-series store as a perfectly plausible curve. The trap has long been documented for hand-typed addresses in the front end (`pitfallOpcuaSlash`); this change is about making the finder **not produce** it: addresses prefer `NodeID.String()` but are **parsed back through `parseAddress` and compared character by character** first, falling back to a browse path **accumulated segment by segment during descent** (reachable by construction), and falling back to "not listed" if neither works — a verified address, or none at all. Segment rendering is likewise written branch by branch against `parsePathSegment`: an empty name, a name containing `/`, or leading/trailing whitespace is refused outright, and the `ns` prefix is **not** "write it only when ns!=0" but "write it when ns!=0 **or** the name contains `:`" (a bare `Motor:1` is read as namespace `Motor` and errors on the spot). Siblings sharing a **duplicate** BrowseName would render the same address string (colliding with the `(device_id, name)` composite unique key, and path resolution only takes the first target), so that branch abandons path addresses wholesale — without **dropping** those points, which remain addressable by NodeID.
  **Three cases of "not doing it rather than guessing"**: ① **no sample values are read** (the same choice as Rockwell for a different reason: the type comes from the `DataType` attribute and is independent of the value, so skipping values costs no type information), hence the result-level `AssumedCommonDataType` stays empty, every point carries its own `CommonDataType`, and the front end takes the existing native-enumeration branch (hiding the "show zero values" toggle and switching to "listed / not listed" wording); ② **no `ConnectionMatcher`**, so point scan opens a throwaway instance, matching the convention in Rockwell/S7/Modbus TCP (the gateway's existing "Test connection" walks that very path and has been exercised in the field), at the cost of one extra session during a scan; ③ **no guessing at model or vendor**: `GetEndpoints` carries no session and the server reports neither, so `Vendor/Model/Version` are left empty — passing a protocol name off as a device self-report would make the user believe the device said it.
  Acceptance: `opcuadrv/probe_test.go` drives real sockets against a real server, covering a hit (including the case where **the port is not the default 4840**), the three "not found" shapes (an HTTP service, connect-then-drop, and a fully closed port), a wall-clock ceiling on unreachable targets (which guards against omitting `DialTimeout`/`RequestTimeout` and letting the library's 10s default take over), broadcast targets being skipped, **`protocol_json` parsing back through the plugin's own `ParseOpcUaConfig` with a numeric port** (a string port is silently dropped by `json.Unmarshal` and falls back to 4840, so a device created from it will not connect to a server that was moved off the default port), and **all twelve verdict cases of the three-way split** (including "a locally synthesised timeout is always treated as not-our-device"); `opcuadrv/pointscan_test.go` runs a whole tree against **a real server and the real driver** (asserting every address parses back to the same node, that the result-level type stays empty, and that every point carries a `TypeMap` key), plus groups for segment rendering, path round-tripping, NodeID round-tripping, the built-in type map (14 mappable codes + 8 codes that must be refused + the three walk terminals), `Note` appearing only for approximate mappings, and option parsing; `opcuadrv/crawl_test.go` uses a controllable stub for the shapes a real server cannot produce: **DataType must be read in batches** (250 variables, exactly 3 requests at `MaxBatch`), **Browse continuations drained**, `MaxPoints` truncation with `readable+unreadable==scanned` intact, **request-budget exhaustion yielding partial results plus `Incomplete` rather than an error**, `maxDepth` blocking only deeper levels, a string NodeID containing `/` **falling back to a browse path**, duplicate-name siblings both landing in "not listed" while a control group lists normally, a single unreadable node being skipped alone, and methods and views not being counted; `testutil/fake/opcua.go` gains an **additive** browsable-address-space fake server (the existing load-test fake has no references and browses to nothing, so testing against it would test nothing at all), recording two gopcua server quirks: nodes must hang off the **ns=0** Objects folder (`NewNodeNameSpace` builds a namespace-local `ns;i=85`), and `AddObject`/`AddVariable` are unusable (they leave a nil back-pointer and never register the node in the namespace map);   **设备扫描的判据是「读到一次软元件数据」，不是「5007 端口开着」**——端口上跑着串口服务器、SCADA 网关、乃至另一个厂商的私有协议都很常见，而它们不会回一条子头（`0xD0`）与结束码都自洽的 MC 3E 应答。探测**完全复用驱动自己的传输层**（`newTransport` + `client.Read`），不另写裸帧：探测与采集因此走完全相同的封帧与路由字段，探测得通的设备采集必定也连得上。**与前三个插件不同，这里没有候选参数**：MC 3E 帧的网络号 / PC 号 / I-O 号 / 站号在本驱动里是写死的常量（`frame.go`），既不是 `protocol_json` 的字段、也不随目标变化，所以一次探测就是一次拨号加一次读取，S7 那条「多阶段握手要按剩余预算反推」在这里也用不上。**厂商与型号一律留空且刻意不猜**：MC 没有任何设备标识读取手段，本插件的驱动只实现了批量读（`0x0401`），仓库里也没有第二条可依据的 SLMP 命令实现——填 "Mitsubishi" 是拿协议名冒充设备自述，而 SLMP 并非只有三菱在用。设备回结束码错误**照样报成设备**（它应答了，只是拒绝了那次读取），与 FINS / Modbus 同一条取舍。
  **点位扫描按「软元件 + 起始地址 + 粒度（位/字/双字）」扫一段**，生成 `D100` / `D100.5` / `M10` / `X30` 这类写法。四处协议特有的取舍：① **单请求点数上限随「软元件类别 × 粒度」变四档**（位软元件 1 点 = 1 位、字软元件取位 1 点 = 1 位、字 1 点 = 1 字、双字 1 点 = 2 字），而 `maxReadWords` 的语义是"读了多少字/位"，当成同一个常数会静默错两档——字软元件扫位时请求数变成 16 倍（一段本来扫得完的地址会撞上请求数上限、拿到一份标着「未扫完」的清单），双字时每帧字数翻倍；② **位软元件（`M/L/X/Y/B/S/V/F`）只允许位粒度**——字单位读法产出的是 `M0/M16/M32` 这种"看着像位、其实是 16 点一组"的名字而值是整字，用户不会发现，所以直接拒绝这种组合；③ **`X`/`Y` 按八进制解释**（与图纸写法一致，`X30` = 十进制 24），扫描表单的起始地址对它们收八进制数字串、非法位报错而不是静默按十进制解析（后者会扫到一段完全不同的地址而结果看着完全正常）；④ **`buildMCBody` 只发 3 字节首地址号**，超上限的地址会被静默截断成另一个位置，因此主循环有一条越界守卫。
  **两处最关键的地方，都是前几份实现没有的形态。** 其一：**「读到第一个读不到就停」只对单片连续的软元件成立**。FINS 能把那条做成全局规则是因为它的内存区各自是一整片；MC 不是——`X`/`Y`（物理 I/O，按槽位分配）与 `B`/`W`（链接区，按模块分配）**中段可以有未分配的空洞**，照抄那条捷径会让清单**从空洞处静默断掉**，而 `Truncated`/`Incomplete` 都不置位，用户看到一份短了一截却看不出任何异常的清单。因此实现里有一张显式的「是否单片连续」表（`pointScanOptions.contiguous`），非连续的软元件上单点失败**不**收工、继续降级右子树，最坏 `2n-1` 次请求——那正是请求数上限本来就要兜住的形态。其二：**结束码只能列白名单，做不到排除法**。MC 的结束码是单个 16 位值，**没有 FINS 那种"高字节是主码、可以成组排除"的结构**，而且同一个语义在不同家族上还是两个码值 —— QnA 兼容那一套落在 `0xC0xx`、iQ 那一套落在 `0x4xxx`（`0x4031` 就是它的"地址范围外"，见本节 `### Fixed` 里 2026-09-29 那条：只收 `0xC0xx` 会把"这里没有点位"报成"扫描失败"）。收进来的是 `0xC051`（设备指定错误）、`0xC056`（地址范围外）、`0x4031`（iQ 家族的同一个语义）、`0xC05B`（点数指定错误，理由：扫描期间子命令与软元件恒定、只有范围在变，拆到单点后点数恒为 1 必然能读，故它只会让请求数变多而不会截断清单）；**`0xC0EF`（通信错误 / PLC 忙）明确不收**——它是可恢复的设备状态，拿它做推断会让一次偶然的忙把清单从中间截断，宁可中止并带上已得的部分结果如实报错。白名单与黑名单各写一遍测试。
  **`Mitsubishi.MC.Serial` 也声明点位扫描，这是与 FINS 的一处刻意相反。** `specs/point-discovery.md` §3 的默认立场是"串口可以、且应当声明"，FINS 当初不声明是因为它的 Host Link 帧格式与会话复用路径都没有真机验证过。MC 这边那条路是齐的：驱动实现了 `driver.ConnectionMatcher`（`mcDriver.matchConfig` 只为串口而设），「测试连接」走的正是同一条复用路径，而点扫复用的 4C 帧传输就是采集路径上一直在用的那一份实现——FX 系列 / C24 这类串口现场因此拿得到这个按钮。代价如实写进弹窗常驻的 `Description`：9600bps 上大范围扫描会经常标着「未扫完」返回。
  验收：`mitsubishidrv/probe_test.go` 打真实套接字，覆盖正常命中、**结束码错误仍算设备**、静默服务靠超时止损且**不突破预算**、拨号失败不是错误、以及**扫描结果里的连接配置能被插件自己的 `ParseMCConfig` 原样还原**（键名或类型写错就会让一键建出来的设备连不上）；`mitsubishidrv/pointscan_test.go` 覆盖地址往返（9 个软元件 × 各自允许的粒度 × 含贴上限的起点）、八进制往返、按粒度的地址空间截断（双字那格是差一陷阱）、单请求规模的四档换算、**"字 w 的值就是 w"的自描述假设备断言每个点位的值恰好是它的名字指向的那个位置**（地址生成与偏移换算是两段独立代码，分叉了值会看着完全合理）、读到末尾即停、**非连续软元件中间有空洞时其后仍被列出**、请求数上限、`MaxPoints` 截断、链路错误中止并带回部分结果、`0xC0EF` 中止、白名单/黑名单逐条、`maxReadWords` 装不下双字时的预检拒绝，以及**表单里的软元件选项与驱动自己的 `mcDevices` 表逐项核对**（位/字与八进制标注都不许漂移）；`pluginhost/scanplugin_test.go` 加三条端到端，其中点扫走完整条 `pluginwire` → `handleDiscoverPoints` → 临时实例建连 → 应答落地。
  **Mitsubishi gains both device scan and point scan: `Mitsubishi.MC.TCP` and `Mitsubishi.MC.Serial`** (plugin version 1.1.0 → 1.2.0). Mitsubishi (MC / SLMP, both the 3E and 4C framings) PLCs can now be discovered from the "LAN device scan" page and have a sweep of component addresses listed from the "Discover points" button on the device-address page. **No gateway change and no front-end change**: scan capability is declared by the plugin in `Meta` and recomputed on every call by `pluginhost` (which walks `m.plugins` rather than caching), `APIVersion` is unchanged, and no golden fixture needs regenerating (`pluginhost/testdata/parity/**`). The front end's `addressSyntax.js` already carried the mc address spec (`D100` / `M0` / `X30`); this change is what makes scan results actually land in that family.
  **Device scan's criterion is "a component read came back", not "port 5007 is open"** — serial servers, SCADA gateways and other vendors' protocols all sit on that port, and none of them answer with an MC 3E reply whose sub-header (`0xD0`) and end code are both self-consistent. Probing **reuses the driver's own transport** (`newTransport` + `client.Read`) rather than hand-rolling frames, so probe and collection share one framing path and one set of routing fields: anything the probe reaches, collection reaches too. **Unlike the previous three plugins there are no candidate parameters here**: the MC 3E frame's network / PC / I-O / station numbers are hard-coded constants in `frame.go`, neither `protocol_json` fields nor target-dependent, so one probe is one dial plus one read, and S7's "derive each stage's timeout from the remaining budget" rule does not apply. **Vendor and model are deliberately left empty and deliberately not guessed**: MC offers no device-identity read at all, this plugin's driver implements only bulk read (`0x0401`), and the repo holds no second source of truth for any other SLMP command — stamping "Mitsubishi" would pass a protocol name off as a self-reported vendor, and SLMP is not Mitsubishi-only. A device answering with an end-code error **is still reported as a device** (it replied, it merely refused that read), the same trade-off as FINS and Modbus.
  **Point scan sweeps component × start address × width (bit/word/dword)**, emitting addresses like `D100` / `D100.5` / `M10` / `X30`. Four protocol-specific trade-offs: ① **the per-request point cap varies across four tiers with (component class × width)** (bit device: 1 point = 1 bit; word device, bit width: 1 point = 1 bit; word device, word width: 1 point = 1 word; dword: 1 point = 2 words), while `maxReadWords` means "how many words/bits were read" — treating it as one constant silently misses by a factor of 16 or 2: a bit sweep over a word device multiplies the request count by 16 (a range that would have finished hits the request quota and comes back labelled "incomplete"), and dword mode doubles the words per frame; ② **bit devices (`M/L/X/Y/B/S/V/F`) allow bit width only** — the word-unit read produces names like `M0/M16/M32` that look like bits but are 16-bit groups whose value is the whole word, so the combination is refused outright rather than guessed at; ③ **`X`/`Y` are octal** (`X30` = decimal 24, matching the drawings), so the start-address field takes an octal digit string for those two and *rejects* an invalid digit instead of silently parsing decimal (which would sweep a completely different range while looking entirely normal); ④ **`buildMCBody` emits only a 3-byte start address**, so an over-range address is silently truncated into a different location, hence the bounds guard in the main loop.
  **Two things here have no precedent in the earlier implementations.** First: **"stop at the first unreadable point" only holds for components whose address space is one contiguous block.** FINS could make that a global rule because each of its memory areas is a single block; MC is not — `X`/`Y` (physical I/O allocated per slot) and `B`/`W` (link areas allocated per module) **can have unallocated holes in the middle**, and copying that shortcut makes the list **end silently at the hole** with neither `Truncated` nor `Incomplete` set: the user gets a list that is short by an unknown amount and shows nothing unusual. The implementation therefore carries an explicit "contiguous?" table (`pointScanOptions.contiguous`); for the non-contiguous components a single-point failure does **not** stop the scan and the right subtree keeps degrading, worst case `2n-1` requests — exactly the shape the request quota exists to bound. Second: **end codes can only be an allowlist, never an exclusion list.** MC's end code is a single 16-bit value with **no FINS-style "high byte is the main code, exclude by group" structure**, and the same meaning is even two different values across families — QnA-compatible in `0xC0xx`, iQ in `0x4xxx` (`0x4031` is its spelling of address-out-of-range, see the 2026-09-29 entry under `### Fixed`: allowlisting only `0xC0xx` reports "no points here" as "scan failed"). Included are `0xC051` (device designation error), `0xC056` (address out of range), `0x4031` (the iQ family's spelling of the same thing) and `0xC05B` (point count error — because the sub-command and component are constant throughout a scan and only the range varies, and once degraded to a single point the count is always 1 and necessarily readable, so it can only cost more requests, never truncate the list). **`0xC0EF` (communication error / PLC busy) is explicitly excluded** — it is a recoverable device state, and inferring from it would let one transient busy condition cut the list in half; aborting with the partial results in hand is the honest answer. Both the allowlist and the denylist are asserted.
  **`Mitsubishi.MC.Serial` declares point scan too, deliberately opposite to FINS.** The default position in `specs/point-discovery.md` §3 is that serial "may and should" declare it; FINS withheld it because neither its Host Link framing nor its serial session-reuse path had been verified against hardware. That path is complete on the MC side: the driver implements `driver.ConnectionMatcher` (`mcDriver.matchConfig` exists for serial alone), "Test connection" walks the very same reuse path, and point scan reuses the 4C framing that the collection path has been using all along — so FX-series and C24 sites get the button. The cost is stated permanently in the dialog's `Description`: over 9600 bps a large sweep will frequently come back labelled "incomplete".
  Acceptance: `mitsubishidrv/probe_test.go` drives real sockets and covers a clean hit, **end-code errors still being a device**, a silent service bounded by timeout **without exceeding the budget**, dial failure not being an error, and **the connection config in the scan result parsing back through the plugin's own `ParseMCConfig`** (a wrong key name or type produces a device that connects to nothing); `mitsubishidrv/pointscan_test.go` covers address round-tripping (9 components × their permitted widths × starts hugging the address-space ceiling), octal round-tripping, per-width address-space truncation (dword is the off-by-one trap), the four-tier per-request sizing, **a self-describing fake device whose word w holds the value w, asserting every point's value is exactly the one at the position its own name points to** (address generation and offset arithmetic are two independent pieces of code, and if they diverge the values still look entirely plausible), stopping at the area end, **a hole in the middle of a non-contiguous component leaving everything after it listed**, the request quota, `MaxPoints` truncation, transport errors aborting with partial results, `0xC0EF` aborting, the allowlist and denylist item by item, the preflight refusal when `maxReadWords` cannot fit a double word, and **every component option in the form cross-checked against the driver's own `mcDevices` table** (neither the bit/word nor the octal labelling may drift); `pluginhost/scanplugin_test.go` gains three end-to-end cases, one of which drives point scan through the entire `pluginwire` → `handleDiscoverPoints` → throwaway-instance connect → reply chain.

  **点位扫描走的是与 Modbus/S7/FINS 完全不同的形态：原生枚举。** 后三者扫的是一段**地址范围**，回答"这段里哪些地址读得到"，产出的是一份候选清单（设备不会告诉你它有哪些点位）；罗克韦尔这边用 **CIP Symbol Object（类 0x6B）** 让控制器把它自己的标签表交出来，产出的是**设备自报的标签名本身**，每个还带着自己的 CIP 类型码。这正是 `specs/point-discovery.md` §1 里点名的少数例外（与 OPC UA 的 Browse、ABB 的 RWS 信号表、DLT645 的数据标识字典同类），也是 `driversdk.FindPointsRequest.Session` 注释里预留的那个位置。
  **两处「不做而不是猜着做」的分野被重新划清**。`Omron.CIP` 当初拒绝实现点扫的理由是「Symbol Object 的布局在本仓库里没有第二处依据可对」——这条对罗克韦尔**不成立**：本仓库的既有依赖 `goindustrial` v0.3.0 已经实现了整条链路（`cip/symbol.go` 的请求构造与应答解码 + `Client.ListTags`），所以罗克韦尔**直接复用它**，不手搓一份会漂移的实现。欧姆龙 NJ/NX 走的是另一套对象模型，那份依据对不上、也没有真机核过，因此**它依旧不声明**（`omroncip` 只改了注释里那段已经变成假话的论证，`TestNoPointDiscovery` 一字未动）。这条差别写进了 `omroncip/main.go`、`rockwellcipdrv/pointscan.go` 的文件头与 `specs/point-discovery.md` §3，免得下一个人以为"S7 能扫、CIP 也能扫"是随手加上的。
  **一处与契约的有意偏离，必须说清楚**：枚举是"整只对象"的操作（`ListTags` 要么全给要么不给），所以**超预算时拿不到部分结果**——那一刻手上零个标签，没有"部分"可交。契约（`specs/point-discovery.md` §7 第 1 条）要求超预算时带上已完成的部分结果并把 `Incomplete` 置位；本 finder **报错**而不是返回空清单 + `incomplete`，因为后者会渲染成一张 0 行的表，而用户会从「一个标签都没有」得出「这台设备没有点位」——正是那篇文档通篇在防的误读。注意与**截断**的不对称：达到 `MaxPoints` 时枚举其实已经跑完了，只是映射停手，那种情况**是**有部分结果的。限制常驻写在弹窗顶部的 `Description` 里。
  **守护一个不看 ctx 的第三方库。** goindustrial 的 TCP 传输从头到尾不设读超时、`Session.SendRRData` 连 ctx 都不看，一个「TCP 通、CIP 不应答」的设备会让枚举永久阻塞——若不管，这次 RPC 会挂到网关侧超时并累积插件卡死计数，连续几次把整个插件进程连同下面所有协议、所有设备一起重启。finder 因此用 goroutine + select 兜住预算，而那个被落下的 goroutine 靠收尾的 `defer drv.Close()` 关掉套接字、让阻塞的读报错退出。**这条依赖库的内部行为**（`DirectTransport.Close` 不持锁、`Unregister` 只写不等），由 `client_test.go` 的 `TestClientListTagsUnblocksOnClose` 钉住：库哪天改成「Close 会等在飞的调用」，那条测试会红，而不是等现场去发现。为同一条路径还把适配器的 `connected` 改成了 `atomic.Bool`（`Close` 刻意不持锁，这是它唯一的并发写者）。
  **两道各不相同的门槛**：**硬门槛是名字**——产出的地址必须过 `ParseRockwellAddress`（判据只有它一个，正是采集侧规划前用的那一个：这里放行的采集一定认得出）；**类型是软处理**——映射不出来就**跳过**（TIMER/COUNTER/UDT 等衍生类型都回 `STRUCT`，LINT 与 BYTE/WORD/DWORD 在类型表里没有入口），不让它们进清单，否则会建出一批永远没有值的点位。跳过的标签计入 `Unreadable`，而界面上叫**「未列出」**——原因是类型/名字，与地址是否存在无关，这条同时写进了 `Description` 与中英文案。数组标签只列第 0 个元素（设备不提供维度信息）。（原文此处还有一句「不过就让整台设备采集全部失败」—— 那条形态已在上面的 `### Fixed` 里改掉：现在解析不出的名字由 `partitionBadTags` 在规划前摘出计划、只标 `QualityBadAddress`。跳过它的理由因此变成「列出来就是建一批永远没有值的点位」，而不是「否则整台设备全挂」。）
  **本协议不读采样值**（枚举每个标签一次请求，再读值等于翻倍），因此结果级的 `AssumedCommonDataType` **留空**。这不是"没填"而是一条**跨端约定**：前端据它为空隐藏「显示 0 值」开关与零值统计（那一列全是空的，开关一关就清空整张表、而"值为 0 的 N 个"会显示成全表条数），并换一套「设备共 N 个标签 / 已列出 / 未列出」的措辞——"可读到/读不到"与"缩小范围重扫"在枚举里都是错的。每个点位的类型改由新增的可选字段 `DiscoveredPoint.CommonDataType` 逐点给出（DINT 与 REAL 混在一张表里，结果级那一个值表达不了），前端的三级回退是 `逐点类型 → 结果级 → 规格默认`，老协议不填它，因此完全向后兼容。约定同时写在 `driver.PointScanResult` 与 `vo.PointScanResultVO` 的注释里。

  **One deliberate deviation from the contract, stated plainly**: enumeration is an all-or-nothing operation (`ListTags` returns everything or nothing), so **there are no partial results on budget exhaustion** — at that moment we hold zero tags, and there is no "partial" to hand back. The contract (`specs/point-discovery.md` §7 rule 1) asks for partial results with `Incomplete` set; this finder **returns an error** instead of an empty list plus `incomplete`, because the latter renders as a zero-row table and the user concludes "this device has no points" from "there is not a single tag" — exactly the misreading that document exists to prevent. Note the asymmetry with **truncation**: hitting `MaxPoints` means enumeration actually finished and only the mapping stopped, and *that* case does return partial results. The limitation is stated permanently in the dialog's `Description`.
  **Guarding a third-party library that ignores ctx.** goindustrial's TCP transport never sets a read deadline and `Session.SendRRData` does not look at ctx at all, so a "TCP up, CIP silent" device blocks enumeration forever — left alone, that RPC hangs until the gateway times it out and increments the plugin's stuck counter, and a few in a row restart the entire plugin process along with every protocol and device under it. The finder therefore wraps it in goroutine + select to stay inside the budget, and the orphaned goroutine is reaped when the caller's `defer drv.Close()` closes the socket and the blocked read errors out. **That relies on library internals** (`DirectTransport.Close` takes no lock, `Unregister` writes without waiting), pinned by `client_test.go`'s `TestClientListTagsUnblocksOnClose`: if the library ever makes `Close` wait for an in-flight call, that test goes red instead of a customer site discovering it. The adapter's `connected` became an `atomic.Bool` for the same path (`Close` deliberately takes no lock, making it the only concurrent writer).
  **Two thresholds that are not the same kind of thing**: the **name is the hard gate** — every emitted address must pass `ParseRockwellAddress`, because `buildPlan` fails only there and it computes the plan for the whole device in one pass: an address that does not parse does not fail "that one point", it **stops the entire device from collecting**; the **type is soft** — unmappable tags are **skipped** (every derived type such as TIMER/COUNTER/UDT comes back as `STRUCT`; LINT and BYTE/WORD/DWORD have no entry in the type table), because emitting them would create points that never have a value. Skipped tags are counted in `Unreadable`, which the UI labels **"not listed"** — the reason is type or name, nothing to do with whether an address exists, and that wording is in both the `Description` and the i18n files. Array tags list only element 0 (the device provides no dimensions).
  **This protocol reads no sample values** (enumeration costs one request per tag; reading values on top would double it), so the result-level `AssumedCommonDataType` is **left empty**. That is not "unset" but a **cross-layer contract**: the front end uses its emptiness to hide the "show zero values" toggle and the zero statistic (that column is entirely empty; turning the toggle off would clear the whole table, and "N zero-valued" would report the full row count), and to switch to "device reports N tags / listed / not listed" wording — "readable/unreadable" and "narrow the range and rescan" are both wrong for enumeration. Each point's type moves to the new optional `DiscoveredPoint.CommonDataType` (DINT and REAL sit in the same table, and one result-level value cannot express that); the front end falls back three levels: `per-point → result-level → spec default`, so older protocols that leave it empty are fully backward compatible. The convention is documented on both `driver.PointScanResult` and `vo.PointScanResultVO`.

  **FINS 的点位扫描按「内存区（DM/CIO/WR/HR）+ 起始字 + 粒度（位/字/双字）」扫一段**，生成 `D100` / `CIO100.05` / `W100` / `H100` 这类写法，与前端 `addressSyntax.js` 的示例一致。两处关键取舍：① **位模式下的字区间只能按 `start/16` 与 `(start+n-1)/16` 算**——对半降级会把起点切到字中间，用「下标 × 每点位字数」会落到别的字上，读到的是**别处**的数据而值看着完全合理；② **地址空间连续 ⇒ 读到第一个读不到的点就收工**，后面的地址一律直接记为读不到。FINS 的内存区是连续的一整片，「某个字不存在」只可能是「已越过该区末尾」；逐个去问会让一次 `count` 填大了的扫描在末尾之后发出几百个必然失败的请求，最后撞上请求数上限、给用户一份标着「未扫完」的结果——而它其实早就扫完了。这条推断成立的前提是错误分类**按主码排除**（`0x01` 本机节点 / `0x02` 目标节点含**忙** / `0x03` 控制器错误一律中止），少了它，一次「目标节点忙」就会把清单从中间截断。

  **Omron's two plugins gain device scan: `Omron.FINS.UDP` / `Omron.FINS.TCP` and `Omron.CIP`** (plugin versions 1.1.0 → 1.2.0 and 1.0.0 → 1.1.0 respectively); the two FINS protocols also gain point range scan.
  **The FINS criterion is "a memory-area read came back", not "port 9600 is open"** — serial servers, SCADA gateways and other vendors' protocols all sit on 9600, and none of them answer with a command-consistent FINS frame. Probing **reuses the driver's own transport** (`newTransport` + `client.Read`) rather than hand-rolling frames, so probe and collection share one address parser, one node-number derivation and one framing path: anything the probe reaches, collection reaches too. To that end both Ethernet clients had their `Read` folded into a shared `exchange`, plus an optional `finsCommander` interface (implemented by UDP/TCP only) so the scan can read **controller data 0x0501** for the model — failing to read it does not affect "device found", the same trade-off as Modbus without FC43. A new rule: **a device answering with an end-code error is still reported as a device** (it replied, it merely refused that read); treating it as "not found" makes a real PLC vanish. **The node-number candidates are optional**: empty means "derive from the device IP's last octet" (byte-for-byte what collection does), and only when the user supplies candidates explicitly is the hit written back into `ProtocolJSON` — writing back means "recording a fact only probing could answer"; a derived value is not a fact, and freezing it just kills a default that would otherwise follow an IP change.
  **FINS point scan** sweeps memory area (DM/CIO/WR/HR) × start word × width (bit/word/dword), emitting `D100` / `CIO100.05` / `W100` / `H100`, matching the examples in the frontend's `addressSyntax.js`. Two key trade-offs: ① **under bit width the word span must be computed as `start/16` and `(start+n-1)/16`** — the binary split can cut the start to mid-word, and "index × words-per-point" then lands on a different word, reading *someone else's* data with entirely plausible values; ② **a contiguous address space means "stop at the first unreadable point"**, with everything after it marked unreadable outright. FINS memory areas are one contiguous block, so "this word does not exist" can only mean "we walked off the end of the area"; probing each remaining address would turn one over-large `count` into hundreds of doomed requests that hit the request quota and hand the user a result labelled "incomplete" — when the scan had actually finished long before. That inference holds only because errors are classified by **excluding main codes** (`0x01` local node / `0x02` destination node, **busy** included / `0x03` controller error all abort); without that, one transient "destination node busy" truncates the list mid-way.
  **`Omron.CIP` takes an entirely different shape: broadcast discovery.** The EtherNet/IP standard **ListIdentity** (encapsulation command 0x0063) is sent as an empty-payload request to 44818/UDP, and each device replies with a self-described identity (vendor, device type, product name, revision, serial, socket address) — **one datagram returns the whole subnet**, unlike the one-target-one-device shape of FINS/S7/Modbus. It declares `TargetMode=both`: broadcast is fast, per-host unicast is the fallback (managed switches and ACLs block broadcasts; declaring broadcast only yields a scan that "finishes normally with zero devices", leaving the user unable to tell network from configuration). The vendor filter **reports Omron only (vendor ID 47)** — other vendors' EtherNet/IP devices cannot be collected over `Omron.CIP`, and reporting them only produces devices that never read a value. The vendor-neutral frame builder/parser lives in `cipcore/listidentity.go` (Rockwell can reuse it later), with the **socket address's port and IP being network order while every other field in the same item is little-endian** pinned byte-for-byte by tests. Two real cases surfaced during implementation: a broadcast reply can exceed the read buffer, and trusting a self-reported `0.0.0.0` builds an unreachable device (now falls back to the datagram source address).
  **`Omron.CIP` deliberately does not implement point scan**: CIP points are symbolic names (`MotorSpeed`, `Recipe.Setpoint`), not an enumerable address space, so "sweep N words from a word address" has nowhere to land. Enumerating tags for real means calling the Symbol Object (class 0x6B), whose layout has no second source of truth in this repo — **not doing it beats guessing**, because a wrong implementation returns an empty list and the user concludes "this device has no points" from "there is not a single tag". By the same reasoning FINS declares point scan only on UDP/TCP; the serial and Host Link over TCP session-reuse paths have not been verified against real hardware, and adding one line is all it takes once they are.
  `APIVersion` is unchanged — scan capability is an optional field; the frontend needs zero changes (it renders purely data-driven, with no allowlist of scannable protocols anywhere). Acceptance: `finsdrv/probe_test.go` drives real sockets against the new UDP fake PLC (`testutil/fake.NewFINSUDP`) and the TCP one, covering end-code-still-a-device, candidate fallthrough, silent targets bounded by timeout, and budgets surviving an oversized user timeout; `finsdrv/pointscan_test.go` covers address round-tripping, exact word spans, stopping at the area end, the request quota and main-code aborts; `cipcore/listidentity_test.go` cross-checks byte order and malformed frames against an **independently implemented** response builder; `omroncipdrv/probe_test.go` covers broadcast multi-device discovery, vendor filtering, the quiet window, the device cap, and non-ListIdentity services not being misreported. **`pluginhost/scanplugin_test.go` adds the end-to-end layer**: it starts the real plugin processes and asserts both capabilities actually cross `pluginwire` into the gateway (including `TargetMode=both` and "ethernet protocols only"), and that probing works on a *real plugin process* all the way to "device and model both come back correctly" — the driver-package tests call `ProbeUDP`/`Probe` directly, skipping payload shape, budget units and the options string/RawMessage conversion, which are exactly where things silently fail to line up.

- **西门子 S7 插件新增局域网设备扫描与点位范围扫描两项能力**（`Siemens.S7`，插件版本 1.0.0 → 1.1.0）。至此西门子 PLC 与 Modbus 一样，可以在「局域网扫描发现」页被扫出来、在设备地址页用「自动发现点位」按钮列出一段范围里读得到的地址。**网关侧与前端零改动**：扫描能力本来就由插件在 `Meta` 里声明、由 `pluginhost` 每次遍历 `m.plugins` 现算（不建缓存表），前端一律数据驱动渲染，代码里没有任何「哪些协议可扫」的白名单；`APIVersion` 不变，老网关 + 新插件忽略未知字段即可，黄金基线（`pluginhost/testdata/parity/typemap/s7.json` 只含 scope + 协议名 + 类型表）也不需要重新生成。
  **设备扫描的判据是「S7 会话协商成功」，不是「102 端口开着」**——HMI 触摸屏、Comfort Panel、各类 S7 网关都监听 102，只有 PLC 会完成 TPKT/COTP 连接与 S7 PDU 协商。没有复用 Modbus 那种「裸发帧 + 自洽性校验」的写法，而是直接复用驱动自己的 `handler.Connect()`：S7 的握手是 TPKT/COTP + PDU 协商两轮，再手写一遍只会多出一份会与采集路径漂移的实现。**机架/槽位做成候选列表**（表单项 `rackSlots`，默认 `0/1,0/2`，最多 4 组）——它是 PLC 上连接资源的地址而不是可选参数，填错的表现是「端口开着却连不上」，从错误信息里完全看不出来；连上的那一组会**写回 `ProtocolJSON`**，否则一键建出来的设备连不上。TCP 层失败（`net.OpError.Op == "dial"`）直接放弃该目标：可达性与机架/槽位无关，而一个 /24 里绝大多数地址都走这条分支，不跳出会让整次扫描的耗时乘以候选数。识别到 CPU 时用 SZL 0x001C 补上型号与序列号；**认不出型号不影响「发现了设备」**，与 Modbus 不支持 FC43 时同一条取舍。102 有服务但协商不出 S7 会话的主机**刻意不上报**——否则同样监听 102 的 HMI 面板会被报成 PLC。
  **两个 gos7 的坑写进了注释**：① **绝不能调 `GetOrderCode()`** —— 它内部 `readSzl` 的命名返回值 `size` 从未被赋值（恒为 0），而它做的是 `szl.Data[size-3]`，也就是 `Data[-3]`，**只要 `readSzl` 成功就必然 panic**；② **`GetCPUInfo()` 必须包 `recover`** —— 它直接切片 `szl.Data[172:204]` 等五处，设备回的 SZL 记录短于 204 字节就是越界，而 panic 会被 `driversdk` 兜成一次 RPC 错误，把「这台设备标识读不出来」升级成「整次探测失败」。
  **点位扫描**按「区域（DB/M/I/Q）+ 起始字节偏移 + 粒度（位/字节/字/双字）」扫一段地址，生成的地址是 `DB1.DBW100` / `DB1.DBX0.1` / `M0.1` / `MW100` 这类写法，与前端 `addressSyntax.js` 里 s7 规格的示例一致，并由 `TestPointNameRoundTrip` 逐组合钉住「能过 `ParseS7Address` 往返」——一个解析不出来的地址写进 `device_address` 之后，这个点位会永远采不到值（规划期就被摘出计划、只报 `QualityBadAddress`；此处当时还是 `CalcS7Ranges` 直接报错、整台设备采集全挂，见下面 `### Fixed` 那条修复）。三处与 Modbus 实现刻意不同：① S7 **没有**「地址含义由配置决定」的形态（`StringLen`/`MaxGap` 只影响采集侧的区间规划），所以**没有**照抄 Modbus 那条 `errConfigModeNotScannable` 守卫——它是为 Modbus 的具体形态写的；② 错误分类只能靠**字符串匹配**（gos7 把 PLC 回的项级错误码经 `CPUError`/`ErrorText` 翻译成一句人话，没有可 `errors.As` 的类型，这点与 goburrow 给结构化 `ModbusError` 不同），白名单只收「明确表示地址/对象不存在」的那几句，**连接类错误一律中止而不是记成「地址不存在」**；③ 除了 `deadline` 再加一条**请求数上限**——对一段整段都读不到的地址，对半降级会退化成一棵满二叉树，光靠 deadline 止损会让耗时随网络延迟漂移。零值过滤仍然留给前端（插件侧过滤会在「所有地址都是 0」的设备上返回空列表，用户据此得出「这里没有点位」）。
  **探测预算按「一次握手包含几次 socket 等待」反推着花**：S7 一次探测要顺序做 TCP 拨号 → ISO-on-TCP 连接 → PDU 协商 → 读 CPU 标识（SZL 首帧 + 续帧）共 5 次带超时的网络操作，所以每个候选的时间上限取 `min(connectTimeout, 剩余预算 / 5)`。不这么做，用户把连接超时填大一点（表单允许）就能让单目标探测花掉 `候选数 × 5 × 超时`，撞上网关侧的 probe RPC 超时并在插件卡死计数上累加——**连续几次会把整个插件进程连同它下面所有协议、所有设备一起重启**。回归见 `s7drv/probe_test.go` 的 `TestProbeTCPRespectsBudget`（断言耗时落在预算内，用一个「收下连接就不说话」的监听器驱动）。S7 **未实现 `ConnectionMatcher`**，因此点扫走的是**临时实例**路径（另开一条 102 连接），与 Modbus TCP 现状一致。
  验收：`driversrc/s7/s7drv/pointscan_test.go` 覆盖地址往返、跨块的点位落点不越界、位号/字偏移取值、对半降级把空洞逐点摘出、连接错误中止而非记成读不到、错误分类的白名单与黑名单、选项解析，并对着 `fake.NewS7()` 跑通「装驱动 → Connect → ScanPoints」整条链路；`probe_test.go` 覆盖候选解析、`ProtocolJSON` 必须能被 `ParseS7Config` 解析出正确的机架/槽位（**字符串形态**，写成数字会被静默丢弃）、对着假 PLC 发现设备、目标不可达与非 S7 服务都返回 `(nil, nil)`、预算与候选表达式非法时的报错；`main_test.go` 钉住「声明与实现一一对应」。
  **Siemens S7 now declares both LAN device scan and point range scan** (`Siemens.S7`, plugin version 1.0.0 → 1.1.0), so a Siemens PLC can be discovered from the "LAN device scan" page and have a range of readable addresses listed from the "Discover points" button on the device-address page, exactly like Modbus. **No gateway or front-end change was needed**: scan capability is declared by the plugin in `Meta` and computed on the fly by `pluginhost` (which walks `m.plugins` every time rather than caching), the UI renders purely from that data, and nothing in the tree hardcodes which protocols are scannable. `APIVersion` is unchanged (old gateway + new plugin ignores the unknown fields) and no golden fixture needs regenerating (`pluginhost/testdata/parity/typemap/s7.json` holds only scope, protocol names and the type table).
  **The device-scan criterion is "the S7 session negotiated", not "port 102 is open"** — HMI panels, Comfort Panels and S7 gateways all listen on 102; only a PLC completes the TPKT/COTP connect and the S7 PDU negotiation. It does not copy Modbus's "speak raw frames and self-check" approach but reuses the driver's own `handler.Connect()`: S7's handshake is two rounds (ISO-on-TCP + PDU negotiation), and hand-rolling it again would only produce a second implementation that drifts from the collection path. **Rack/slot is a candidate list** (form field `rackSlots`, default `0/1,0/2`, up to four entries) — it is the address of a connection resource on the PLC, not an optional parameter, and getting it wrong looks like "the port is open but nothing connects" with no hint in the error text; the group that connected is **written back into `ProtocolJSON`**, without which the one-click device would not connect. A TCP-layer failure (`net.OpError.Op == "dial"`) abandons that target immediately: reachability has nothing to do with rack/slot, and since most addresses in a /24 take that branch, not breaking out would multiply the whole scan's duration by the number of candidates. When the CPU is identified, SZL 0x001C supplies model and serial number; **failing to identify it does not stop the device from being reported**, the same trade-off Modbus makes when FC43 is unsupported. Hosts that answer on 102 but never negotiate an S7 session are **deliberately not reported** — otherwise HMI panels listening on 102 would show up as PLCs.
  **Two gos7 landmines are documented in the code**: ① **never call `GetOrderCode()`** — inside it, `readSzl`'s named return `size` is never assigned (always 0) while the function indexes `szl.Data[size-3]`, i.e. `Data[-3]`, so it **panics whenever `readSzl` succeeds**; ② **`GetCPUInfo()` must be wrapped in `recover`** — it slices `szl.Data[172:204]` and four other ranges directly, so an SZL record shorter than 204 bytes is an out-of-range access, and a panic would be swallowed by `driversdk` into an RPC error, escalating "this device's identification is unreadable" into "the whole probe failed".
  **Point scan** sweeps a range defined by area (DB/M/I/Q), a starting byte offset and a width (bit/byte/word/dword), emitting addresses like `DB1.DBW100` / `DB1.DBX0.1` / `M0.1` / `MW100` — matching the s7 spec examples in the front end's `addressSyntax.js`, and pinned per combination by `TestPointNameRoundTrip` as round-tripping through `ParseS7Address`. An address that fails to parse does not merely fail "that one point": `CalcS7Ranges` parses the whole batch and errors out, so **the entire device stops collecting**. Three places differ deliberately from the Modbus implementation: ① S7 has **no** "address meaning fixed by config" mode (`StringLen`/`MaxGap` only affect the collector's range planning), so the Modbus-only `errConfigModeNotScannable` guard is **not** copied — it was written for Modbus's specific shape; ② error classification can only be **string matching** (gos7 translates the PLC's item-level error codes into a human sentence via `CPUError`/`ErrorText`, with nothing to `errors.As` — unlike goburrow's structured `ModbusError`), so the allowlist admits only the messages that clearly mean "this address/object does not exist", and **connection errors always abort instead of being recorded as "address does not exist"**; ③ besides `deadline` there is a **request-count cap** — for a range that is entirely unreadable, bisection degenerates into a full binary tree, and a deadline alone would let the duration drift with network latency. Zero filtering is still left to the front end (filtering in the plugin would return an empty list on a device whose addresses are all zero, and the user would conclude there are no points).
  **The probe budget is derived from how many socket waits one handshake contains**: an S7 probe performs five timed network operations in sequence (TCP dial → ISO-on-TCP connect → PDU negotiation → read CPU identity, whose SZL read uses a first and a continuation frame), so each candidate's time limit is `min(connectTimeout, remaining budget / 5)`. Without that, a user raising the connect timeout (which the form allows) would make a single-target probe cost `candidates × 5 × timeout`, breaking the gateway-side probe RPC deadline and accumulating the plugin's stuck counter — **several in a row restart the entire plugin process, taking every protocol and device under it down**. Regression: `TestProbeTCPRespectsBudget` in `s7drv/probe_test.go` (asserts the elapsed time stays inside the budget, driven by a listener that accepts and then says nothing). S7 **does not implement `ConnectionMatcher`**, so point scan takes the **throwaway instance** path (a second connection on 102), the same as Modbus TCP today.
  Acceptance: `driversrc/s7/s7drv/pointscan_test.go` covers address round-tripping, every point landing inside its chunk's read buffer, bit-index and word-offset decoding, bisection extracting interior holes point by point, connection errors aborting rather than being counted as unreadable, the allowlist and denylist of the error classifier, and option parsing — plus the full "install driver → Connect → ScanPoints" chain against `fake.NewS7()`; `probe_test.go` covers candidate parsing, `ProtocolJSON` being parseable by `ParseS7Config` with the right rack/slot (**as strings** — writing numbers gets them silently dropped), device discovery against the fake PLC, `(nil, nil)` for both an unreachable target and a non-S7 service, and errors for an over-budget or malformed candidate expression; `main_test.go` pins "declaration and implementation correspond one-to-one".

  **Deleting a device now also deletes the device addresses under it** — the only behaviour change here, and **single delete was changed to match**: there are no foreign keys between the tables (see `migrations/002_device.sql`), so without an explicit delete the address rows survive as unreachable orphans — the collector loads addresses via `device` and the UI lists them by `deviceId`, so they never appear anywhere and can only be found by reading the database. Two deletion paths with different semantics would be worse still: users would assume "single delete is safer" when it merely leaves the garbage behind silently. The single-delete confirmation text therefore also states that **the addresses under the device go with it**.
  It shares the reasoning of the device-address batch delete: **one `DELETE ... WHERE id IN (...)`** (addresses first by the same batch of `device_id`, then the devices, in one transaction), no per-id existence check, and no failure when an individual id is gone — looping over the single-delete endpoint would error and roll back whenever "someone else just deleted that device", making **the whole batch fail**; the response reports the **actual deleted row count** `deleted` (which may be less than `requested`) so the UI can say "fewer were deleted" instead of always claiming success. - **新增设备点位范围扫描：在设备地址页一键列出「这个范围里读得到的地址」，勾选后批量建成点位**。设备扫描解决了「网段里有哪些 PLC」，但设备建成后运维仍要逐条录入点位：翻图纸、查寄存器表、填地址/类型/标签。现在设备地址页多了一个「自动发现点位」按钮：选功能区与地址范围、扫描、勾选、批量建 `device_address`（逐条失败不中断整批，复用 Excel 导入那套结果契约）。
  **必须把它的性质说在前面**：设备**不会告诉你**它有哪些点位。除 OPC UA（Browse）、ABB RWS（信号表）、DLT645（数据标识字典）外，Modbus / S7 / 三菱 / FINS / CIP 都没有任何标准枚举手段。所以本功能产出的是「**该范围内读得到的地址清单**」，是**候选清单而不是点位表**——非零不一定有意义，读得到 0 的也可能是有效值。插件因此**不做零值过滤**（过滤是前端的一枚开关：在插件里过滤会在「所有寄存器都是 0」的设备上返回空列表，用户据此得出「这里没有点位」）。
  与设备扫描是**相反的两件事**，代码与文档都成对安排（`driver/pointDiscovery.go` ↔ `discovery.go`、`pluginhost/pointdiscovery.go` ↔ `discovery.go`、`service/devicePointScanService.go` ↔ `deviceScanService.go`）：设备扫描问「网段里谁在」（目标由网关规划、无会话、可取消），点位扫描问「**这台已存在的设备**上有哪些点位」（目标由 `deviceId` 指定、**复用那台设备的采集会话**、一次 RPC 覆盖整段、**不可取消**）。完整契约见 [backend/specs/point-discovery.md](backend/specs/point-discovery.md)，与 [device-scan.md](backend/specs/device-scan.md) **必须成对修改**。
  线协议是新的 `discoverPoints` 方法。**扫描不走驱动自己的 `Read`**：那条路读设备的 cfg 做区间规划，配置模式下会静默给出错位的值，而照它建出来的点位会**永远取到别处的数据**（在时序库里表现为一条完全合理的曲线）。正确形态是给 finder 一个 `SessionAccess`，让它取驱动自己的客户端直接读，并且**块与块之间重新取一次会话锁**（一次 `Do` 覆盖整段扫描 = 把采集卡死几十秒，与 `pingSessionBudget` 同一条理由）。串口回退规则也**刻意与 ping 相反**：ping 拿不到会话锁就跳过并回落临时实例是对的（不能让「测 COM2 时因为 COM1 在忙」变成假失败），但一次长扫描回落成临时实例会**抢占串口长时句柄**，采集侧下次重连报 `Access is denied` 并进入退避——「点一次扫描把设备打成离线」。因此串口上「有会话但复用不到」一律**报错不回退**，只有「该协议一个会话都没有」才回落（那时端口按定义是空的）。
  **地址写法用 IEC 61131-3 的 `%MW` / `%IW` / `%MX` / `%IX`（0-based）**，不是传统的 `40001` 风格：传统写法在满量程（`465536` 解析不出来）、差一（1-based）、功能区丢失（`10000` 落进纯数字分支）三处都会坏，而一个解析不出来的地址写进 `device_address` 之后，这个点位会永远采不到值（当时是整台设备采集全挂，见下面 `### Fixed` 那条修复）。因此结果里的**地址列在前端只读**。往返由 `TestPointNameRoundTrip` 钉住（0/9999/10000/65534/65535 × 四个功能区）。
  结果是三个计数（`Scanned` / `Readable` / `Unreadable`，不变量 `Readable + Unreadable == Scanned`）加**两个必须分开显示**的标志：`Truncated`（达到 `MaxPoints`，后面的地址根本没试）与 `Incomplete`（预算耗尽，范围还没扫完）——它们与「读不到」是三回事，前端合并成一句话会让用户得出错误的结论。`MaxPoints` 是每协议的声明（取 `[1,20000]`），上限存在的意义不是性能而是事故半径：一个 2000 寄存器的范围会产生上百 KB 的应答，而 `pluginwire` 写帧持插件进程的写锁，大帧会头阻塞该进程上所有协议的应答。
  **网关侧还会把插件声明的预算再钳到 7000ms**（`pointScanGatewayBudgetCapMs`），RPC 超时 = 该值 + 2s ⇒ 最坏 9s < `main.go` 里 `srv.Shutdown` 的 10s 宽限期。这一条是**跨文件耦合**：超了不是「报个错」，而是 `Shutdown` 卡满整个宽限期后打一条 `context deadline exceeded`——在服务管理器里表现为**「网关停不掉」**。点扫是**同步 HTTP**（与设备扫描的「登记即返回」不同），所以才需要这道钳制；代价是 RTU 大范围扫描会被截断，因此 `Incomplete` 必须在界面上显式显示。改一个必须同时改另一个，回归见 `TestBudgetWithinGatewayCap`。**不开新的总开关**：点扫复用 `deviceScan.enabled`；错误码只新增 `40027 该协议不支持点位扫描`。
  **一处插件作者可见的源码级破坏性改动**：`driversdk.Main` / `Serve` / `ServeConn` 的第三个参数由裸 `Probers` 改成结构体 `driversdk.Capabilities{Probers, PointFinders}`。**站外插件重编时改一行**（`driversdk.Probers{...}` → `driversdk.Capabilities{Probers: ...}`，不需要扫描的传零值 `driversdk.Capabilities{}`），但 **`APIVersion` 不变、旧二进制在新网关上仍可加载**：`Protocol.PointDiscovery` 是可选字段，元数据与线协议都向后兼容。改成结构体是因为第三种能力（原生枚举）已经可以预见，而每加一种能力就要在三个入口重复一遍并在仓库内 25 处调用点各改一次。
  验收：`driversdk/pointscan_test.go` 用 `net.Pipe` 覆盖块间释放锁、串口绝不回落临时实例（自证：临时实例连同一串口必然失败）、会话中途关闭返回部分结果、finder panic 后锁未泄漏、预算钳制；`driversrc/modbus/modbusdrv/pointscan_test.go` 覆盖空洞处的对半降级、连接错误中止而非记成「地址不存在」、分块不超单帧上限（用请求帧数断言）、拒绝配置模式、地址往返；`pluginhost/modbusplugin_test.go` 编译**真实插件产物**对着假 PLC 跑通整条链路。
  **Device point range scan: from the device-address page, list the addresses that answered inside a range and turn the ticked ones into points in one click.** Device scan answered "which PLCs are on this subnet", but after a device exists an operator still enters every point by hand — reading drawings, looking up register tables, typing address/type/label. There is now a "Discover points" button on the device-address page: pick a function area and an address range, scan, tick, and create `device_address` rows in bulk (per-row failures never abort the batch, reusing the Excel-import result contract).
  **The nature of the feature has to come first**: a device **never tells you** which points it has. Outside OPC UA (Browse), ABB RWS (signal table) and DLT645 (data-identifier dictionary), Modbus / S7 / Mitsubishi / FINS / CIP have no standard enumeration at all. What this produces is therefore "the addresses that answered inside this range" — a **list of candidates, not a point table**: a non-zero value does not imply it means anything, and a readable zero may well be a valid value. The plugin consequently does **no zero filtering** (that is a front-end switch; filtering in the plugin would return an empty list on a device whose registers are all zero, from which the user would conclude "there are no points here").
  It is the **mirror image of device scan**, and code and docs are laid out in pairs (`driver/pointDiscovery.go` ↔ `discovery.go`, `pluginhost/pointdiscovery.go` ↔ `discovery.go`, `service/devicePointScanService.go` ↔ `deviceScanService.go`): device scan asks "who is on this subnet" (gateway plans the targets, no session, cancellable), point scan asks "**this existing device** — which points does it have" (target fixed by `deviceId`, **reuses that device's collector session**, one RPC for the whole range, **not cancellable**). The full contract is [backend/specs/point-discovery.md](backend/specs/point-discovery.md), which **must be changed together with** [device-scan.md](backend/specs/device-scan.md).
  The wire method is `discoverPoints`. **The scan must not go through the driver's own `Read`**: that path reads the device cfg to plan ranges, and in config mode it silently yields misaligned values — addresses that, once saved as points, make **the whole device's collection fail**. One point takes down the device. The correct shape is to hand the finder a `SessionAccess` so it uses the driver's own client directly, and to **re-acquire the session lock between chunks** (a single `Do` covering the whole scan pins collection for tens of seconds — the same reasoning as `pingSessionBudget`). The serial fallback rule is **deliberately the opposite of ping's**: for ping, "skip and fall back to a throwaway instance when the lock is busy" is right (it must not turn "COM2 is busy because COM1 is being read" into a false failure), but a long scan falling back to a throwaway instance would **seize the serial handle**, and the collector's next reconnect would report `Access is denied` and back off — "one scan click takes the device offline". So on serial, "there is a session but it cannot be reused" is **an error, never a fallback**; a fallback happens only when the protocol has no session at all (in which case the port is by definition free).
  **Addresses use IEC 61131-3 `%MW` / `%IW` / `%MX` / `%IX` (0-based)**, not the traditional `40001` style: the traditional form breaks in three places — full scale (`465536` does not parse), off-by-one (it is 1-based), and loss of the function area (`10000` lands in the plain-number branch) — and an unparseable address saved as a point does not fail "just that one point", it makes **the whole device's collection fail**. The address column is therefore **read-only** in the UI. Round-tripping is pinned by `TestPointNameRoundTrip` (0/9999/10000/65534/65535 × all four function areas).
  The result carries three counters (`Scanned` / `Readable` / `Unreadable`, invariant `Readable + Unreadable == Scanned`) plus **two flags that must be displayed separately**: `Truncated` (hit `MaxPoints`; later addresses were never tried) and `Incomplete` (budget exhausted; the range was not fully swept) — both distinct from "unreadable", and collapsing them into one sentence would lead the user to the wrong conclusion. `MaxPoints` is a per-protocol declaration (`[1,20000]`); its purpose is not performance but blast radius: a 2000-register range produces a response of hundreds of KB, and `pluginwire`'s frame write holds the plugin process's write lock, so a large frame head-of-line-blocks every protocol on that process.
  **The gateway additionally clamps the plugin-declared budget to 7000 ms** (`pointScanGatewayBudgetCapMs`); the RPC deadline is that value + 2 s ⇒ at worst 9 s, under the 10 s grace period of `main.go`'s `srv.Shutdown`. This is a **cross-file coupling**: overshooting does not produce an error, it makes `Shutdown` burn the entire grace period and log `context deadline exceeded` — which under a service manager reads as **"the gateway will not stop"**. Point scan is **synchronous HTTP** (unlike device scan's "register and return"), which is exactly why the clamp is needed; the price is that large RTU ranges get truncated, so `Incomplete` must be shown in the UI. Changing one requires changing the other — regression test `TestBudgetWithinGatewayCap`. **No new master switch**: point scan reuses `deviceScan.enabled`; the only new error code is `40027 this protocol does not support point discovery`.
  **One source-level breaking change visible to plugin authors**: the third argument of `driversdk.Main` / `Serve` / `ServeConn` changed from a bare `Probers` to the struct `driversdk.Capabilities{Probers, PointFinders}`. **Out-of-tree plugins change one line when they rebuild** (`driversdk.Probers{...}` → `driversdk.Capabilities{Probers: ...}`; pass the zero value `driversdk.Capabilities{}` if you need no scanning), but **`APIVersion` is unchanged and existing binaries still load** on the new gateway: `Protocol.PointDiscovery` is an optional field, and both metadata and wire protocol stay backward compatible. It became a struct because a third capability (native enumeration) is already foreseeable, and each new capability would otherwise have to be repeated across three entry points and all 25 call sites in the tree.
  Acceptance: `driversdk/pointscan_test.go` uses `net.Pipe` to cover lock release between chunks, serial never falling back to a throwaway instance (self-proving: a throwaway instance on the same port must fail), a session closed mid-scan returning partial results, no lock leak after a finder panic, and budget clamping; `driversrc/modbus/modbusdrv/pointscan_test.go` covers bisection across an interior hole, connection errors aborting instead of being recorded as "address does not exist", chunking within the single-frame limit (asserted by request count), rejection of config mode, and address round-tripping; `pluginhost/modbusplugin_test.go` builds the **real plugin artifact** and runs the whole chain against a fake PLC.

- **新增局域网设备扫描发现：扫描网关所在网段，勾选结果一键建成设备**。此前网关只能被动接设备——运维必须先在图纸/铭牌上查到每台 PLC 的 IP、站号、端口，再手工录入。现在前端多了一个「局域网扫描发现」页面：选协议、选网段（网段来自本机网卡自动枚举，只允许扫网关自己的网段）、点开始，扫描异步跑并实时显示进度与结果（IP、站号、厂商、型号、版本、耗时），勾选后一键建成 `device` 行。扫描结果里的连接配置由插件给出且由服务端持有，客户端不回传；逐条失败不中断整批（复用 Excel 导入那套结果契约）。
  协议驱动全部在进程外，所以扫描是**插件声明 + 插件实现**的新扩展点：`Meta.Protocols[].Discovery` 声明能力（可选字段，因此**不递增 `APIVersion`**，旧插件无需重编），`driversdk.Probers` 给探测实现，声明了却没有实现则插件启动即失败。线协议是新的 `probe` 方法，**无会话、一次一个目标**——网关负责枚举目标、并发、限速、取消与进度，插件只回答「你给我的这个 IP:端口是不是我的设备」；广播型协议（EtherNet/IP ListIdentity、FINS/UDP）由网关把各网段的子网广播地址也加进目标列表即可覆盖，不必各自实现一套网段枚举。完整契约见 [backend/specs/device-scan.md](backend/specs/device-scan.md)。
  示范实现是 **Modbus TCP**：裸发 MBAP 帧读 FC43/14 设备标识（依赖的 goburrow/modbus 没有该功能码），不支持时用一次寄存器读取兜底判定「这是 Modbus 设备」——把「是 Modbus 设备」与「支持读标识」分开是这里的关键，多数 PLC 属于后者不支持的。三菱 / FINS / CIP 等照同一接口各自补即可，本轮不动（**S7 已在后续一轮补上**，见本文件上方那条「西门子 S7 插件新增局域网设备扫描与点位范围扫描两项能力」）。
  任务只在内存里（不落库、重启即丢，超过 `jobTTLMinutes` 惰性清理），同一时刻只允许一个任务。**新增配置段 `deviceScan`**（`enabled` / `maxConcurrentProbes` / `maxTargets` / `jobTTLMinutes`）。探测超时**刻意不是配置项**：它是每协议的属性，由插件声明 `MaxBudgetMs`，网关侧的 RPC 超时按它推导 —— 而一个全局旋钮配小了只会得到「RPC 先超时、插件还在跑、用户看到扫不到设备」这种静默故障。
  **一处必须点明的既有代码修复**：`pluginhost/client.go` 原先把 `ctx.Done` 一律计为「插件卡死」的证据。取消一个扫描会同时掐掉在飞的全部探测，于是**点一次取消就能顶满阈值**；而在「一台还没建设备的新网关」（运维第一件事就是扫描）上，该插件进程除探测外没有任何成功调用，看门狗随即杀掉进程 —— **该插件下所有协议、所有设备一起断**。现在只把真正的超时计入。回归测试 [backend/pluginhost/client_test.go](backend/pluginhost/client_test.go) 的 `TestCancelDoesNotCountAsTimeout`（已实测：改回旧行为它立刻失败）。
  验收：[backend/pluginhost/modbusplugin_test.go](backend/pluginhost/modbusplugin_test.go) 编译真实插件产物、对着假 PLC 跑通探测链路；[backend/devicescan/engine_test.go](backend/devicescan/engine_test.go) 覆盖并发上限、取消保留部分结果、截断上报、惰性过期；另有一次真实的端到端手工验收（假 PLC + 真网关走完 capabilities → start → 轮询进度 → 取消 → 截断 → 批量建设备 → 测试连接，并确认多次取消后插件进程未被重启）。
  **LAN device scan: sweep the gateway own subnets, then turn the results into devices in one click.** Until now the gateway could only accept devices it was handed — an operator had to look up every PLC IP, unit id and port from drawings or nameplates and enter it by hand. There is now a "LAN device scan" page: pick a protocol and subnets (enumerated from the host own interfaces; only the gateway own subnets are scannable), start, and watch progress and results stream in (IP, unit id, vendor, model, version, elapsed). Ticking rows creates `device` rows in one click. The connection config in each result is produced by the plugin and held server-side — the client never sends it back — and per-row failures never abort the batch (reusing the Excel-import result contract). The contract is [backend/specs/device-scan.md](backend/specs/device-scan.md).
  Because every protocol driver is out-of-process, scanning is a new **plugin-declared, plugin-implemented** extension point: `Meta.Protocols[].Discovery` declares the capability (an optional field, so **`APIVersion` is not bumped** and existing plugins need no rebuild), `driversdk.Probers` supplies the probe, and declaring the capability without implementing it fails at plugin startup. The wire method is `probe`: **session-less, one target per call** — the gateway enumerates targets, controls concurrency, rate-limits, cancels and tracks progress, while the plugin answers exactly one question: "is this IP:port one of mine?". Broadcast-based protocols (EtherNet/IP ListIdentity, FINS/UDP) are covered by the gateway adding each subnet broadcast address to the target list, so they need not each reimplement subnet enumeration.
  The reference implementation is **Modbus TCP**: it speaks raw MBAP to read FC43/14 device identification (the goburrow/modbus dependency has no such function code) and falls back to a single register read to decide "this is a Modbus device" — separating "is Modbus" from "supports device identification" is the crux, since most PLCs are the latter without the former. Mitsubishi / FINS / CIP follow the same interface later; they are out of scope here (**S7 was added in a later round** — see the entry above titled "Siemens S7 now declares both LAN device scan and point range scan").
  Jobs live in memory only (never persisted, lost on restart, lazily cleaned up after `jobTTLMinutes`) and only one runs at a time. **New `deviceScan` config section** (`enabled` / `maxConcurrentProbes` / `maxTargets` / `jobTTLMinutes`). The probe timeout is deliberately **not** a config knob: it is a per-protocol property declared by the plugin as `MaxBudgetMs`, from which the gateway derives the RPC deadline — a global knob set too low only ever produces the silent failure "RPC times out first, the plugin keeps running, the user sees no devices found".
  **One pre-existing bug had to be fixed and is worth calling out**: `pluginhost/client.go` used to count every `ctx.Done` as evidence that the plugin was stuck. Cancelling a scan tears down all in-flight probes at once, so **a single cancel could fill the streak**; and on a brand-new gateway with no devices configured yet (exactly when an operator scans) that plugin process has no successful calls other than probes, so the watchdog killed it — **taking every protocol and every device under that plugin down with it**. Only genuine timeouts are counted now. Regression test: `TestCancelDoesNotCountAsTimeout` in [backend/pluginhost/client_test.go](backend/pluginhost/client_test.go) (verified: it fails immediately if the old behaviour is restored).
  Acceptance: [backend/pluginhost/modbusplugin_test.go](backend/pluginhost/modbusplugin_test.go) builds the real plugin artifact and runs the probe chain against a fake PLC; [backend/devicescan/engine_test.go](backend/devicescan/engine_test.go) covers the concurrency cap, cancel-keeps-partial-results, truncation reporting and lazy expiry; plus a real end-to-end manual run (fake PLC + real gateway through capabilities, start, progress polling, cancel, truncation, batch device creation and connection test, confirming the plugin process was not restarted after repeated cancels).

- **新增协议插件 `ABB.RWS`（ABB 机器人 Robot Web Services）**。机器人此前是采集盲区——节拍、程序状态、夹具 IO 只能靠加装额外 PLC 中转，现在直接读控制器：IO 信号、RAPID 变量/常量、控制器面板状态、关节与笛卡尔位姿、系统信息。同一插件**自动识别两代 RWS**：1.0（IRC5 / RobotWare 6，Digest 认证、HTTP:80）与 2.0（OmniCore / RobotWare 7，Basic 认证、HTTPS:443），探测不准时可在表单里显式指定。源码在 `backend/driversrc/abb/`，产物 `iot-driver-abb`，协议名 `ABB.RWS`、scope `abb`（新协议，非搬迁，无既有配置需要迁移；`iot_protocol` 行由插件加载时自动建立，不需要 SQL 迁移）。
  地址用「命名空间前缀 + 路径」写法，也接受直接粘贴 RWS 原生路径：`signal:Local/DRV_1/DI1`（≡ `/rw/iosystem/signals/Local/DRV_1/DI1`）、`rapid:T_ROB1/Mod1/nTest`、`panel:ctrlstate`、`motion:ROB_1/joint/rax_1`、`system:rwversion`；`#字段` 可取出复合值里的具体分量（如 `signal:L/D/DI1#quality`、`rapid:T/M/pHome#x`）。**裸地址（无前缀）一律拒绝**——它与 RAPID 的三段路径语法同形，靠猜会静默读到另一个资源的值，而时序库里看不出任何异常。
  读取策略是**批量优先 + 单点回退**：一轮按资源去重后只发 2~3 个请求即可覆盖上千点位（控制器有 <20 req/s 的硬限流，逐点 GET 必然撞墙），列表未覆盖的点位再走单点 GET 并受条数与时间双重预算约束；确认不存在（4xx）的点位进入负缓存，不再每轮重试。信号被勾了仿真时质量标为 128（不确定）而非 192。RAPID 符号是刻意例外——RWS 的符号搜索端点只返回描述符不含值，所以它永远走单点 GET。
  实现**不新增任何 go.mod 依赖**：Digest 认证（含 RFC 2069 无 qop 分支）与限流令牌桶均自实现，插件保持自包含。**https→http 的静默降级被禁止**：只有端口根本不可达才换下一个候选，握手/证书失败一律硬报错并把用户引导到表单里的「仅HTTP」——否则一个能干扰 TLS 的攻击者就能把 Basic 凭据诱导成明文发出。
  **New protocol plugin `ABB.RWS` (ABB robot Robot Web Services).** Robots were previously a blind spot — cycle time, program state and fixture IO needed an extra PLC in the middle; now the controller is polled directly for IO signals, RAPID variables/constants, panel state, joint and cartesian pose, and system information. One plugin **auto-detects both RWS generations**: 1.0 (IRC5 / RobotWare 6, Digest auth, HTTP:80) and 2.0 (OmniCore / RobotWare 7, Basic auth, HTTPS:443), overridable from the device form. Sources live in `backend/driversrc/abb/`, artifact `iot-driver-abb`, protocol `ABB.RWS`, scope `abb` (a new protocol, not a migration — no existing config to migrate, and the `iot_protocol` row is provisioned automatically on plugin load with no SQL migration).
  Addresses use a `namespace:path` form and also accept pasted native RWS paths: `signal:Local/DRV_1/DI1` (≡ `/rw/iosystem/signals/Local/DRV_1/DI1`), `rapid:T_ROB1/Mod1/nTest`, `panel:ctrlstate`, `motion:ROB_1/joint/rax_1`, `system:rwversion`; a `#field` suffix selects a component of a compound value (e.g. `signal:L/D/DI1#quality`, `rapid:T/M/pHome#x`). **Bare addresses are rejected outright** — they are syntactically identical to RAPID's three-segment paths, and guessing silently reads a different resource's value with nothing anomalous visible in the time-series store.
  Reads are **bulk-first with a single-get fallback**: one round issues 2–3 deduplicated requests to cover thousands of points (controllers hard-limit at <20 req/s, so per-point GETs always hit the wall), uncovered points fall back to individual GETs under both a count and a time budget, and points confirmed missing (4xx) are negatively cached instead of being retried every round. Simulated signals report quality 128 (uncertain) rather than 192. RAPID symbols are a deliberate exception — RWS's symbol-search endpoint returns descriptors without values, so they always go through single GETs.
  It adds **no new go.mod dependency**: Digest auth (including the RFC 2069 no-qop branch) and the rate-limit token bucket are implemented in-plugin. **Silent https→http downgrade is forbidden**: a fallback only happens when the port is unreachable at all; a handshake or certificate failure is a hard error that points the user at the form's "HTTP only" option — otherwise an attacker able to tamper with TLS could steer Basic credentials onto the wire in clear text.
- **新增协议插件 `DLT645.Serial` / `DLT645.TCP`（DL/T 645 多功能电能表）**。协议实现逐文件移植自 [iot-gateway](https://gitee.com/edwin_2025/iot-gateway) 的内置驱动 `backend/driver/dlt645`，改以进程外插件形式分发：源码在 `backend/driversrc/dlt645/`，产物 `iot-driver-dlt645`，协议名 `DLT645.Serial`（RS-485/RS-232 串口）与 `DLT645.TCP`（串口服务器 / DTU 透传），scope `dlt645`。两个协议**沿用 iot-gateway 侧的原值**，因此两个项目之间的 `device.protocol_id`、点位地址与类型名可以直接互相迁移；`iot_protocol` 行由插件加载时自动建立，不需要 SQL 迁移。串口协议声明 `SerialExclusive`（采集引擎整轮持锁，保证 485 总线上的帧不被交错），TCP 不独占（客户端内部已对单次请求-响应持锁）。
  支持 **2007 与 1997 两个方言**（控制码、正常/异常应答码、数据标识长度均不同），点位地址即数据标识：内置字典收录 A相电压 `02010100`、组合有功总电能 `00000000`、电表运行状态字 `04000501`–`04000507` 等常用项，厂商私有标识按 `DI:字节数:小数位[:标志]` 显式声明（如 `12345678:2:0:s`）。**数据的字节数、小数位、符号与编码方式由数据标识本身决定，不由类型下拉决定**——下拉只决定输出形态（工程值 / 原始整数 / 文本 / 时间 / 布尔），这与其它协议「类型决定一切」的语义不同，是 645 的核心设计。电量级数值全程整数定标、不经过浮点，避免 `999999.99` 丢最后一位。
  帧解析对现场报文容错：前导 `FE` 唤醒字节、半双工链路回显的请求帧、总线上其它表的应答、缺失的结束符、任意分片投递都能正确跳过并重新同步；**校验码不符只跳过 1 字节重同步**（不按长度跳过，长度本身也可能被干扰）。协议层问题（电表正常应答但拒绝请求、解码失败、应答含后续帧）只把相关点位标记为异常，**绝不上抛成连接错误**——否则一台能通但拒读某个数据标识的电表会被整台判离线。同一问题只在状态变化时告警一次（现场实测 10 分钟刷了 124 条完全相同的告警），恢复正常打一条 INFO。
  表单在 iot-gateway 播种脚本的基础上补上了每项的默认值（驱动实际会用的值：`parity=E`、`baudRate=2400`、串口 `preambleBytes=4` 而 TCP 为 0），并**去掉了 `maxFollowUpFrames`**：当前实现不支持拼接后续帧，一个填了毫无作用的旋钮只会误导现场（该字段仍被容错解析，从 iot-gateway 搬来的配置不会解析失败）。
  验收见 [pluginhost/dlt645plugin_test.go](backend/pluginhost/dlt645plugin_test.go)：它是全新协议（本仓库从未有过它的第二份实现），**没有黄金基线可对**，因此验插件能否被正确加载/注销，以及能否跑通完整采集链路（含一个最小 DL/T 645-2007 假电能表，按数据标识回放固定字节，断言到采集记录一级）。
  **New protocol plugin `DLT645.Serial` / `DLT645.TCP` (DL/T 645 multifunction electricity meters).** The implementation is ported file-by-file from the built-in `backend/driver/dlt645` driver in [iot-gateway](https://gitee.com/edwin_2025/iot-gateway) and now ships as an out-of-process plugin: sources in `backend/driversrc/dlt645/`, artifact `iot-driver-dlt645`, protocols `DLT645.Serial` (RS-485/RS-232) and `DLT645.TCP` (serial server / DTU), scope `dlt645`. Both **keep the iot-gateway values**, so `device.protocol_id`, point addresses and type names migrate cleanly between the two projects; the `iot_protocol` rows are provisioned automatically on plugin load with no SQL migration. The serial protocol declares `SerialExclusive` (the collector holds the device lock for a whole round so frames never interleave on the bus); TCP does not (its client already locks each request/response pair).
  Both **the 2007 and 1997 dialects** are supported (control codes, normal/abnormal response codes and data-identifier length all differ). A point address *is* the data identifier: the built-in dictionary covers A-phase voltage `02010100`, total combined active energy `00000000`, meter status words `04000501`–`04000507` and more, while vendor-private identifiers are declared explicitly as `DI:bytes:decimals[:flags]` (e.g. `12345678:2:0:s`). **Byte length, decimals, sign and encoding all come from the data identifier, not from the type dropdown** — the dropdown only picks the output form (engineering value / raw integer / text / time / boolean), which is the opposite of every other protocol here and is the core design of 645. Energy-grade values are scaled with integer arithmetic throughout, never through floating point, so `999999.99` never loses its last digit.
  Frame parsing tolerates messy field traffic: leading `FE` wake-up bytes, echoed request frames from half-duplex links, other meters' responses on the shared bus, a missing end byte, and arbitrary fragmentation are all skipped and resynchronised correctly. **A checksum mismatch only skips one byte to resync** (never the length field — that can be corrupted too). Protocol-level problems (a meter that answers but refuses the request, a decode failure, a response with a follow-up frame) mark only the affected points as bad and are **never escalated to a connection error** — otherwise a meter that is reachable but refuses one data identifier would be declared offline entirely. Repeated problems are logged once per state change (a field log showed 124 identical warnings in 10 minutes), and recovery logs a single INFO.
  The form adds per-field defaults on top of iot-gateway's seed script (the values the driver actually uses: `parity=E`, `baudRate=2400`, `preambleBytes=4` on serial but 0 on TCP) and **drops `maxFollowUpFrames`**: follow-up frame reassembly is not implemented, and a knob that does nothing but mislead the field is worse than no knob (the field is still parsed leniently, so configs moved over from iot-gateway do not fail to parse).
  Acceptance lives in [pluginhost/dlt645plugin_test.go](backend/pluginhost/dlt645plugin_test.go): this is a brand-new protocol here (the repo never had a second implementation of it), so **there is no golden baseline to compare against** — instead it checks that the plugin loads/unloads correctly and that the full acquisition chain works end to end, including a minimal DL/T 645-2007 fake meter that replays fixed bytes per data identifier, asserting down to the collected-record level.

### Fixed

- **一个写错的点位地址不再拖垮整台设备、也不再误报「设备断联」**（插件版本 modbus 1.2.0 → 1.2.1、s7 1.2.0 → 1.2.1、fins 1.2.1 → 1.2.2、mitsubishi 1.2.1 → 1.2.2、Omron.CIP 1.1.2 → 1.1.3、Rockwell.CIP 1.1.1 → 1.1.2；`APIVersion` 不变、黄金基线不动）。**六个**区间/标签规划器一起改：modbus / s7 / fins / mitsubishi 覆盖「地址写法」，Omron.CIP / Rockwell.CIP 覆盖「标签名」——后两者的解析器只收可打印 ASCII（`0x21..0x7E`），**一个空格或一个中文就够**，把「Line 1.Temp」或中文说明填进地址栏是常见手误，触发难度比 `%MW1x` 还低。改完这些之后，全仓不再有任何**点位级配置条件**（写错的地址、写错的标签名、放不进单请求的类型/长度、与 `startAddress` 对不上的寄存器）会把设备判成离线。
  **症状**：现场日志里一行 `modbus: calc address ranges failed: modbus: address "%MW1x" (id=…) invalid format`，随后这台设备被判**离线**。
  **追下去是一条完整的误判链**：`%MW1x` 死在 `ParsePLCAddress` 的 `strconv.ParseUint("1x")` 上，**一个字节都没发出去**；错误从 `Read` 返回，而采集侧只看得见一个 `err`，分不清它是「地址写错了」还是「网线被拔了」——于是 `incError()` + `reportState(dev, false)`，连续三轮后 `alarm.Tracker` 落一条**断联**报警并推通知（`设备 X 断联`）。而那个设备**全程在线**：`IsConnected()` 为真，重连/退避逻辑根本不启动。三个后果：① 运维收到一条永不自愈的假报警，第一反应（查网络、重启 PLC）与真实原因完全无关；② `forEachBatch` 遇错立即返回，**坏地址之后的批次全部被跳过**，整台设备的点位一起停止采集；③ 这个配置错误本身没有任何指向自己的信号。
  **修法不是改报警措辞，而是把这个点位级配置故障送回它本来就该去的桶**：规划前先用**该协议自己的解析器**把地址拆成两半（`partitionBadAddrs` / `partitionBadTags`），解析不出的从区间计划里摘出去并随计划带走；`Read` 不再报错，该点位单独返回一条 `Quality=QualityBadAddress`、`Value=""`、`DataType`/`Kind` 照填的记录，由既有的**点位质量报警**报出「地址无效」并**指名到点位**。设备保持在线，其余点位照常采集。
  **一套形状做了六遍，其中两处各有自己的看点**：`Omron.CIP` 没有计划缓存（每轮现算，改动最小）；`Rockwell.CIP` 的计划在**进程级 `sync.Map`（`arrCache`）、按内容指纹、刻意不设 TTL**，所以 `bad` 必须挂在缓存里的 `*tagPlan` 上 —— 它是**计划输入的纯函数**，与 `tags`/`arrs` 一样由指纹决定，因此不需要 TTL，也就没有碰上那条「别把带 TTL 的每驱动状态混进进程级缓存」的取舍（标签名改对 ⇒ 指纹变 ⇒ 重新算）。回归 `TestPlan_BadRidesTheProcessCacheWithoutTTL` 把这两条都钉住（缓存命中后 `bad` 仍在；改对名字后该标签回到计划里、`bad` 清空）。
  **这不是新发明，是移植仓库里已有的形态**：`dlt645drv/plan.go` 的 `planEntry.err`（「单个点位地址非法…不会使整批失败」）与 `abbdrv/driver.go` 的 `slot.err` 早就这么做，`alarm/point.go` 的 `causeTextAddress = "地址无效"` 也是为这个场景写的；六个规划器本来也都已有 per-point 载体（`markQuality`/`markBadPoint`/`markTagZero` + 计划缓存上的 `bad map`），改动是把「解析失败」接进那条既有的路。
  **四处刻意的取舍**：① **判据只用协议自己的解析器**，不新建正则或校验器 —— 那正是「两条路径不可能漂移」的支点；② **`CalcXRanges` 的签名与错误契约不动**（它那条 `invalid format` 与 `no addresses to read` 仍有测试钉着，只是现在永远收不到非法输入）：拆在它上游；③ **质量码复用 `QualityBadAddress` 而不是 `QualityBadParse`** —— 后者的报警文案是「解析失败」，会把运维引向设备/解码；`driver/types.go` 与 `alarm/point.go` 里该码的注释一并扩写为「**本地就解析不出来**或设备已确认不存在」；④ **原先「刻意保留批次致命」的两处，这一轮也收掉了** —— 配置模式的 `addr < startAddress`（Modbus）与「单点位跨度超过 `maxReadWords`」（FINS/MC）。第一轮留它们的理由是"改成逐点得在 `CalcXRanges` 之外重算一遍跨度与钳制，那正是各包注释里警告过的「同一个问题两条路径两种答案」漂移"，但正解不是复制判据而是**把判据本身提出来共享**：新增 `modbusExcluded`、`finsSpanWords` + `finsMaxReadWords`、`mcParseAddr` + `mcSpanTooLarge` + `mcMaxReadWords` + `mcStringLen`，`CalcXRanges` 与 `partitionBadAddrs` 调的是同一份 —— 漂移这个反对理由随之消失，`CalcXRanges` 自己那条错误退化成给直接调用方（契约测试）的兜底。回归：fins/mc 两包各自把原来那条「跨度超限必须报错」的用例翻成「超限点位只坏它自己、同批好点位照常取值且位模式点位不被字跨度上限误伤」（`TestRead_SpanTooLargeExcluded`），并新增 Modbus 的 `TestPlanFor_BelowStartAddressGoesToBad`（其中断言日志那句话里写的是 `startAddress` 而不是 `invalid format`，即两种排除在日志里可分辨），三包的「一批全不可用」用例也各扩成混合三种成因。**仍**留在那一侧的只剩点位保存层的地址校验，那**不加是刻意的**：驱动全在插件进程里，主二进制不含任何协议解析器，后端要校验就得走插件 RPC；前端加一份正则则必然与插件解析器漂移（前端只校验长度，服务层只校验非空/长度/唯一）。
  **一处提醒**：Modbus 那半个来源（`addr < startAddress`）**今天配不出来** —— `ParseModbusTcpConfig` 不读 `protocol_json` 的 `startAddress`（`modbusConfigRaw` 里没有这个字段，表单也只有 `host`/`port`/`unitId`/`byteOrder`/`wordOrder`），所以 `cfg.StartAddress` 恒为 0。它防的是"将来有人把 `startAddress` 加回表单"（与 point-discovery spec 里那条「配置模式被拒」的守卫同源），现在只有 `TestPlanFor_BelowStartAddressGoesToBad` 直接调 `planFor` 覆盖；**现场能触发的那一半只有地址写法**。
  **未新增 parity 黄金用例**：黄金编码的是「被移除的内置实现产出过什么」，而内置实现对这种输入是**报错**，没有可对照的等价性；新行为由各包新增的 `badaddr_test.go` 钉住（不报错、记录数与输入地址数相等且按索引对齐、坏点位 `QualityBadAddress` 且 `DataType`/`Kind` 非空、同批好点位照常取值且**确实上了线**、一批全坏时零次上线请求）。`pluginhost/testdata/parity/**` 一个字未动（四份 `addresses.json` 里的地址全部可解析，拆分对它们是无操作）。
  **一处只有 Modbus 才会踩的坑**：它的结果骨架是**按功能码组**预填的（`readRanges`），被摘出的地址不在任何组里，若不带过来，末尾「按 addrs 重组」会产出一条**零值记录**（连 `DeviceAddressID` 都为空，`toRecords` 的名称回退会走到空键）——违反「addrs 里每个点位都恰好有一条记录」这条写死的契约，且下游 MQTT 负载与时序库表结构正靠 `DataType` 决定怎么写。所以 `modbusPlan` 多了个 `bad` 字段、`readBatch` 多了一段播种循环。另有一处：配置模式下 `groupAddrsByFC` 对空输入也会写出一个 **nil 值的键**，喂给 `CalcReadRanges` 会撞上它的 `no addresses to read` —— 加了空组守卫。
  **A mistyped point address no longer takes the whole device down, and no longer raises a false offline alarm** (plugin versions modbus 1.2.0 → 1.2.1, s7 1.2.0 → 1.2.1, fins 1.2.1 → 1.2.2, mitsubishi 1.2.1 → 1.2.2, Omron.CIP 1.1.2 → 1.1.3, Rockwell.CIP 1.1.1 → 1.1.2; `APIVersion` unchanged, golden fixtures untouched). **Six** range/tag planners change together: modbus / s7 / fins / mitsubishi cover address syntax, Omron.CIP / Rockwell.CIP cover tag names — those two parsers accept only printable ASCII (`0x21..0x7E`), so **a single space or one Chinese character is enough**, and typing `Line 1.Temp` or a Chinese description into the address field is an ordinary slip — easier to hit than `%MW1x`. With all of these done, no point-level configuration condition in this repo — a mistyped address, a mistyped tag name, a type/length too wide for a single request, or a register below `startAddress` — makes a device look offline any more.
  **Symptom**: one log line — `modbus: calc address ranges failed: modbus: address "%MW1x" (id=…) invalid format` — after which the device is reported **offline**.
  **The chain is a complete misdiagnosis**: `%MW1x` dies inside `ParsePLCAddress`'s `strconv.ParseUint("1x")` — **not a single byte ever reaches the wire**; the error comes back from `Read`, and the collector can only see an `err`, unable to tell "the address is a typo" from "the cable is unplugged" — so it does `incError()` + `reportState(dev, false)`, and after three rounds `alarm.Tracker` writes an **offline alarm** and pushes a notification (`设备 X 断联`). The device was **online the whole time**: `IsConnected()` is true, so the reconnect/backoff path never even engages. Three consequences: ① operations gets a false alarm that never clears, and its first move (check the network, power-cycle the PLC) has nothing to do with the real cause; ② `forEachBatch` returns on the first error, so **every batch after the bad one is skipped** and the whole device stops collecting; ③ the configuration error itself raises no signal pointing at itself.
  **The fix is not a rewording of the alarm but sending this point-level configuration fault back to the bucket it belongs in**: before planning, the addresses are split in two by **the protocol's own parser** (`partitionBadAddrs` / `partitionBadTags`); the unparseable ones are excluded from the range plan and carried on the plan; `Read` no longer errors and returns exactly one record for that point with `Quality=QualityBadAddress`, `Value=""` and `DataType`/`Kind` intact, which the existing **point-quality alarm** reports as 「地址无效」 **naming the point**. The device stays online and the other points keep collecting.
  **Not a new invention — a port of a shape already in this repo**: `dlt645drv/plan.go`'s `planEntry.err` ("a single illegal point address … does not fail the batch") and `abbdrv/driver.go`'s `slot.err` have done exactly this all along, and `alarm/point.go`'s `causeTextAddress = "地址无效"` was written for it; all four range planners already carried the per-point machinery (`markQuality`/`markBadPoint` plus a `bad map` on the plan cache), so the change is wiring "parse failure" into that existing path.
  **Four deliberate trade-offs**: ① **the criterion is only the protocol's own parser**, no new regex or validator — that is what makes the two paths incapable of drifting; ② **`CalcXRanges`' signature and error contract are untouched** (its `invalid format` and `no addresses to read` branches are still pinned by tests — they simply can no longer receive invalid input): the split happens upstream of it; ③ **the quality code is `QualityBadAddress`, not `QualityBadParse`** — the latter's alarm text is 「解析失败」, which points the operator at the device/decoding rather than the address; the doc comments for that code in `driver/types.go` and `alarm/point.go` were widened to "**unparseable locally** or the device confirmed it does not exist"; ④ **the two cases first left "deliberately batch-fatal" were taken down in this same round** — config mode's `addr < startAddress` (Modbus) and FINS/MC's "span exceeds `maxReadWords`". The first round's reason for leaving them was "making them per-point would mean re-deriving span and clamping outside `CalcXRanges`, exactly the 'one question, two answers' drift those packages' comments warn about" — but the fix is not to duplicate the criterion, it is to **extract the criterion itself and share it**: new helpers `modbusExcluded`, `finsSpanWords` + `finsMaxReadWords`, and `mcParseAddr` + `mcSpanTooLarge` + `mcMaxReadWords` + `mcStringLen`, called by both `CalcXRanges` and `partitionBadAddrs`. That removes the drift objection entirely, and `CalcXRanges`' own error degrades to a backstop for callers that invoke it directly (the contract tests). Regressions: fins and mc each flipped their old "span over the limit must error" case into "the over-limit point breaks only itself, the good points in the same batch still read, and bit-mode points are not caught by the word-span cap" (`TestRead_SpanTooLargeExcluded`); Modbus gained `TestPlanFor_BelowStartAddressGoesToBad` (which asserts the log line says `startAddress` rather than `invalid format` — the two exclusion causes stay distinguishable in the log); and each package's "whole batch unusable" case now mixes all three causes. **The only thing still left on the fatal side** is address validation at the point-save boundary, and leaving it out **is deliberate**: the drivers live in plugin processes and the main binary contains no protocol parser, so backend validation would need a plugin RPC, while a front-end regex would inevitably drift from the plugin parsers (the front end checks length only; the service layer checks non-empty/length/uniqueness).
  **No new parity golden was added**: the goldens encode "what the removed built-in implementation produced", and the built-in implementation *errored* on this input, so there is no equivalence to preserve; the new behaviour is pinned by a new `badaddr_test.go` in each package (no error; record count equal to input count and index-aligned; the bad point is `QualityBadAddress` with non-empty `DataType`/`Kind`; the good points in the same batch still read and genuinely reached the wire; an all-bad batch issues zero requests). `pluginhost/testdata/parity/**` is unchanged by a single character (every address in the four `addresses.json` files parses, so the split is a no-op for them).
  **One trap only Modbus has**: its result skeleton is prefilled **per function-code group** (`readRanges`), and an excluded address is in no group — without carrying it on the plan, the final "rebuild in `addrs` order" emits a **zero-value record** (with an empty `DeviceAddressID`, sending `toRecords`' name fallback to an empty key), violating the hard-written contract "exactly one record per point in `addrs`" and breaking downstream MQTT payloads and time-series schemas that depend on `DataType`. Hence the new `bad` field on `modbusPlan` and the seeding loop in `readBatch`. One more: in config mode `groupAddrsByFC` writes a **nil-valued key** even for empty input, which would trip `CalcReadRanges`' `no addresses to read` — a guard was added for empty groups.

- **`Rockwell.CIP` / `Omron.CIP`：两处「一个坏元素 / 一次协议拒绝，殃及其余」的修复**（Rockwell 1.1.0 → 1.1.1、Omron 1.1.1 → 1.1.2）。与上面两条同属一族，但两处的**症状各不相同**，其中 Rockwell 那处比 `quality=0` 更糟。
  **Rockwell ①：数组区间分块读会静默读到别的元素的值。** 数组区间按 `maxTagElements`（125）切成多块、每块一次 `Read Tag Elements`（0x4C）—— 而 0x4C 的**请求体里只有元素个数、没有偏移字段**（CIP 规范如此，库的 `NewReadTagRequest` 也只写两字节元素数），偏移只能写在**标签路径**里（`Big[125]`）。驱动发的是裸基础名 `Big`，等于每次都从元素 0 读，而响应解析是按 `(下标-offset)` 切片解码的 —— 于是**第二块起的点位读到的是别的元素的值**：值看着完全合理，曲线平滑，只是不是它自己的。300 个点的数组切成 3 块时实测**后 175 个点全错**。修法是让请求路径带上起始下标（`rangeRequestName`）。**这条 bug 此前被测试掩护着**：原来的用例假设备按"设备记得上一次读到哪"应答（`offsetBase` 自增），而真实设备不可能是这个语义；假设备现在会拒绝不带下标的路径，用例则逐请求断言 `Big[0] x125` / `Big[125] x1`。
  **Rockwell ②：一块数组（最多 125 个元素）被设备整块拒绝时，按元素下标对半降级。** 只摘掉真正不存在的那个元素，同块其余元素照常取值。判据只认三个**明确表示"不存在"**的状态码（0x04 路径段错误 / 0x05 路径目标未知 / 0x16 对象不存在）；0x02 资源不可用、0x06 部分传输、0x13/0x15 长度不符这类**可恢复的设备状态**说明不了"哪个元素不存在"，因此既不降级也不确认任何元素 —— 整块保持 `quality=0` 并在下一轮重试（与修复前一致，不会更糟）。应答本身不可用（类型码头缺失/数据不足）同样不确认任何元素。
  **这里刻意不做降级计划缓存**（其它五个协议都做了）：块上限只有 125、把一个坏元素摘出来要十几次请求，而 Rockwell 的读取计划来自**进程级、无 TTL 的指纹缓存**（`arrCache`）—— 在它上面混挂一份带 TTL 的每驱动状态，两者的生命周期会互相矛盾（计划命中时旧指纹的降级结论会跨设备生效）。代价是每轮重付这十几次请求，换来的是**每轮自愈**，不必等 TTL。
  **Omron：整批（0x0A 多服务）请求被设备拒绝时，不再把整台设备判离线。** 设备不认 0x0A 时回的不是多服务应答，而是一个单服务的错误回显；`parseMultipleDataTableRead` 报普通错误 → `driver.Read` 上抛 → 采集引擎据此把设备判离线并反复重连 —— 而 PLC 一直好好地应答着，它只是不认批量。现在多服务应答的**解析失败统一带上 `errBatchUnusable` 哨兵**（与"设备以通用状态码整体拒绝本批"走同一条路），`flush` 据此**当场退回逐标签单读**把本轮的值救回来（不是整批置 0 等下轮），并记下"这台设备不吃批量"：**5 分钟静默期内直接单读**（不再每轮先赔一次注定失败的批量往返），到期**自动重试一次**批量 —— 现场把设备修好或换台支持 0x0A 的机器之后不必重启网关即可恢复，`Connect` 时静默期作废。
  **判据是"错误的来源"，不是"错误有多严重"**：只有"设备回了话、但应答不成其为多服务应答"才回退；写失败 / 读超时 / 封装层状态非 0 / CPF 解析失败照旧上抛（**回退救的是协议级拒绝，不是断连** —— 少了这条区分，"回退"就成了掩盖断连）。应答**截断**也归入回退，因为猜错的代价不对称：当成"批量不可用"最多白跑 5 分钟逐标签单读（值照样读到），当成链路错误则整台设备判离线。逐标签单读的语义（设备拒绝某个标签只让该标签的点位 `quality=0`、链路错误才上抛）与常规单读**合并为同一处实现**（`readIndividually`）—— 回退路径若自己复制一份，两份迟早分叉成"同样的失败在回退下和单读下表现不同"，而这类分叉在界面上只表现为"偶尔有一批点位没值"。
  回归：Rockwell 三条（单元素隔离并逐请求断言路径、非地址类状态不降级、设备补上元素后恢复）+ 重写的数组用例；Omron 八条（含一条**纯字节**用例把"设备用单服务错误回显应答 0x0A"这条线协议事实钉到哨兵上、静默期跳过批量、TTL 到期重试、链路错误仍上抛、回退中单个标签被拒不上抛、回退途中链路错误上抛）。其中 Rockwell 的重写数组用例与 Omron 的五条**都实测过"修复前必挂"**。
  **`Rockwell.CIP` / `Omron.CIP`: two fixes for "one bad element / one protocol-level refusal dragging everything else down"** (Rockwell 1.1.0 → 1.1.1, Omron 1.1.1 → 1.1.2). Same family as the two entries above, but the **symptoms differ** — and the Rockwell one is worse than `quality=0`.
  **Rockwell ①: chunked array reads silently returned other elements' values.** An array range is split into chunks of `maxTagElements` (125), one `Read Tag Elements` (0x4C) per chunk — and a 0x4C request body **carries only an element count, no offset** (per the CIP spec; the library's `NewReadTagRequest` writes two count bytes and nothing else). The offset can only live in the **tag path** (`Big[125]`). The driver sent the bare base name `Big`, i.e. read from element 0 every time, while the response is decoded by slicing at `(index-offset)` — so **points in the second chunk onwards were given other elements' values**: entirely plausible numbers, smooth curves, just not their own. Measured on a 300-point array split into three chunks: **175 points wrong**. The fix puts the start index in the request path (`rangeRequestName`). **The old test shielded this**: its fake device answered on a "the device remembers where it last read" model (`offsetBase` incrementing), which no real device implements; fakes now reject a path with no index and the case asserts `Big[0] x125` / `Big[125] x1` request by request.
  **Rockwell ②: a rejected array chunk (up to 125 elements) now degrades by element index bisection.** Only the element that genuinely does not exist is dropped; the rest of the chunk reads normally. The predicate accepts only the three statuses that unambiguously mean "not here" (0x04 path segment error / 0x05 path destination unknown / 0x16 object does not exist); 0x02 resource unavailable, 0x06 partial transfer and 0x13/0x15 length mismatches are **recoverable device states that say nothing about which element is missing**, so they neither degrade nor confirm anything — the whole chunk stays at `quality=0` and is retried next round (same as before the fix, never worse). An unusable response (missing type-code header, short data) likewise confirms nothing.
  **Deliberately no degraded-plan cache here** (the other five protocols have one): a chunk tops out at 125 elements, isolating one bad element costs a dozen or so requests, and Rockwell's read plan comes from a **process-wide, TTL-less fingerprint cache** (`arrCache`) — hanging a TTL'd per-driver state off it would put the two lifetimes at odds (a hit on an old fingerprint would apply another device's conclusions). The cost is re-paying those dozen requests each round; the return is **self-healing every round**, with no TTL to wait out.
  **Omron: a rejected whole batch (0x0A multiple-service) no longer takes the device offline.** When a device does not understand 0x0A it answers with a single-service error echo rather than a multiple-service response; `parseMultipleDataTableRead` returned a plain error, `driver.Read` propagated it, and the collector marked the device offline and reconnected in a loop — while the PLC was answering perfectly well and simply did not understand batching. Now every parse failure of a multiple-service response carries an **`errBatchUnusable` sentinel** (sharing one path with "the device rejects the batch wholesale with a general status code"), and `flush` uses it to **fall back to per-tag reads immediately**, recovering this round's values (rather than zeroing the batch and waiting), and records "this device will not batch": a **five-minute quiet period of direct single reads** (no longer paying for a doomed batch every round), after which batching is **retried once automatically** — fixing the device or swapping in one that supports 0x0A recovers without a gateway restart, and `Connect` discards the hint.
  **The predicate is the error's source, not its severity**: only "the device answered, but not with a multiple-service response" falls back; write failures, read timeouts, non-zero encapsulation status and CPF parse failures still propagate (**the fallback rescues a protocol-level refusal, not a lost link** — without that distinction, "fall back" becomes a way to hide disconnects). A **truncated** response also falls back, because guessing wrong is asymmetric: treating it as "batching unusable" costs at most five minutes of per-tag reads (the values still arrive), while treating it as a link error takes the whole device offline. The per-tag read semantics (a device refusal zeroes only that tag's points; link errors propagate) are now **one shared implementation** (`readIndividually`) with the ordinary single-read path — a fallback that copied its own loop would drift into "the same failure behaves differently under fallback and under single reads", and that kind of drift only shows up in the field as "sometimes a batch of points has no value".
  Regressions: three for Rockwell (single-element isolation with the request path asserted per call, non-address statuses not degrading, recovery once the device gains the element) plus the rewritten array case; eight for Omron (including a **pure-bytes** case tying the wire fact "the device answers 0x0A with a single-service error echo" to the sentinel, the quiet period skipping batching, retry after TTL expiry, link errors still propagating, a single rejected tag not propagating during fallback, and a link error mid-fallback propagating). Rockwell's rewritten array case and five of Omron's were **verified to fail against the pre-fix shape**.
- **`ModBus.TCP` / `ModBus.RTU` / `Siemens.S7`：一个点位读不到，不再把同区间的其它点位一起标成 `quality=0`**（两个插件 1.1.0 → 1.2.0）。与上一条 `Omron.FINS` / `Mitsubishi.MC` 是同一件事搬到另外两个协议上：它们同样把地址间隙在窗口内的点位合并成**一次请求**（Modbus `mergeWindow` 默认 125 个寄存器、S7 `maxGap` 默认 8 字节），设备对含"不存在地址"的整个请求**整段拒绝**，于是区间里那一个越界地址就把整段点位一起标成 0。三个插件各持一份实现（插件之间不共享代码是硬规则），形状一致。
  **Modbus 顺带修掉旧降级路径的两个缺陷**，它们正是"这个 bug 修过一半"的来源：① 旧的降级只在**含空洞**的区间上触发（`len(AddressMap) < Quantity`），而坏地址落在**连续块**里才是最常见的形态 —— 那条路一次都进不去，只能整段标 0；② `readRegisterRangesStrict` 在任一子段失败时 `return nil, err`，父区间随即被整段标 0，**把前面已经读到的兄弟子段一起丢掉**。现在两者都并入统一的对半降级。**位区间与寄存器区间是两套单位**（位按位、寄存器按寄存器，多寄存器类型按字节数折算），混用不会报错，只会把读取头落到别的寄存器上、读到别处的数据而值看着合理 —— 位路径因此单独钉一条用例，请求序列逐条断言。
  **两个协议"什么算地址问题"的判据各不相同，且都刻意窄于点扫那条路**：Modbus 只认 `0x02 IllegalDataAddress` / `0x03 IllegalDataValue`；`0x06 ServerDeviceBusy`（从站忙）、`0x05 Acknowledge`、`0x04` / `0x08` / `0x0A` / `0x0B` 一律**不算**。S7 只能靠字符串匹配（gos7 没有结构化错误码），用的是点扫那套 `unreadableMarkers` 的**真子集**，去掉了 `"CLI : function refused by CPU"` 这个兜底桶 —— S7-1500 的项级错误码恰好都落到它。两条路问的是两个不同的问题：**点扫**问"要不要停止扫描 / 记成读不到"（判错最多让候选清单多一条）；**采集**问"要不要**确认**这个地址永久不可读、摘出计划并缓存 5 分钟"（判错是把一个本来好用的点位静默丢掉）。所以兜底桶与"从站忙"在采集侧一律当瞬时状态：整段原样留在计划里，下一轮重试 —— 与修复前的行为一致（一轮 `quality=0`、下轮重试），不会更糟。
  **同一次改动里还有两处顺带**：① S7 的链路错误判据由 `errors.As(err, &netErr)` 换成点扫同款的 `isConnErr`（多覆盖 EOF / 连接被关）—— 此前一次 EOF 会被当成"区间读取失败"，整段标 0 且**不触发重连**；② Modbus 的 TCP 与 RTU 两个 `Read` 原本是逐句重复的两份，现在只有一份 `readBatch`，两个驱动各传自己的客户端与错误前缀。
  **验收：四个插件的核心用例都实测过"修复前必挂"**。Modbus 与 S7 各六条（单点坏 → 仅该点 0；坏地址夹在中间；**降级后按新起点重算偏移**由"值里写着自己的地址"的假设备钉住；非地址类错误 → 整段原样重试、不缓存降级计划、设备恢复后一轮取到值；链路错误上抛并标记断开；预算逐轮有界且全部确认后计划里不再留着它们；`TestReadRanges_DegradeConvergesAcrossRounds` —— 80 点一个区间、前 40 个不存在，摘完要 79 次请求 > 64 的预算，退回父区间的写法下 6 轮之后那 40 个**好点位**仍是 0）。为了能真正跑到生产代码，Modbus 把批次循环抽成 `readBatch`、S7 抽成 `readOnce`，测试传假客户端 —— 原先在测试里照抄一遍循环的写法量到的是测试自己那版，给错的实现背书。两处测试夹具同时订正：Modbus 那条空洞用例原先是拿 `errors.New("illegal data address")` 当设备拒绝（普通错误在新判据里是链路问题、应当上抛），改成真正的 `ModbusError{ExceptionCode: 0x02}`；S7 的点位类型由不存在的 `uint8` 改成它自己的 `byte`。七个协议的黄金基线与 `go test ./...` 全量通过。
  **`ModBus.TCP` / `ModBus.RTU` / `Siemens.S7`: one unreadable point no longer drags every other point in its read range down to `quality=0`** (both plugins 1.1.0 → 1.2.0). This is the preceding `Omron.FINS` / `Mitsubishi.MC` fix carried to the other two protocols: they likewise merge points whose address gap is within a window into **a single request** (Modbus `mergeWindow`, default 125 registers; S7 `maxGap`, default 8 bytes), and the device **rejects the whole request** when it covers a non-existent address — so one out-of-range address zeroed every point in the range. Each plugin keeps its own copy (plugins must not share code); the shape is the same.
  **The Modbus change also removes the two defects of the old half-fix**, which is exactly why this bug had been "fixed halfway" before: ① the old degradation only triggered on ranges **with holes** (`len(AddressMap) < Quantity`), yet a bad register sitting inside a **contiguous block** is the most common shape — that path could never be entered, leaving only "zero the whole range"; ② `readRegisterRangesStrict` returned `nil, err` as soon as any sub-range failed, so the parent was zeroed wholesale, **discarding sibling sub-ranges that had already read successfully**. Both are now folded into the unified bisection. **Bit ranges and register ranges are two different units** (bits for coils, registers for holdings, multi-register types converted from their byte size), and mixing them raises no error — it merely puts the read head on a different register and returns data from elsewhere that looks plausible — so the bit path gets its own case with the request sequence asserted one by one.
  **What counts as an "address problem" differs per protocol, and both predicates are deliberately narrower than the scan path's**: Modbus accepts only `0x02 IllegalDataAddress` / `0x03 IllegalDataValue`; `0x06 ServerDeviceBusy`, `0x05 Acknowledge`, `0x04`, `0x08`, `0x0A` and `0x0B` do **not** count. S7 has only string matching (gos7 exposes no structured item-level codes) and uses a **strict subset** of the scan path's `unreadableMarkers`, dropping the `"CLI : function refused by CPU"` catch-all — which is precisely where every S7-1500 item-level code lands. The two paths ask different questions: the **scan** asks "stop sweeping, or record this as unreadable?" (a wrong answer adds one bogus entry to a candidate list); the **read** path asks "**confirm** this address is permanently unreadable, drop it from the plan and cache that for five minutes?" (a wrong answer silently loses a working point). So on the read side both the catch-all and "slave busy" are treated as transient: the range stays in the plan untouched and is retried next round — the pre-fix behaviour (one round of `quality=0`, retried next poll), never worse.
  **Two things came along in the same change**: ① S7's link-error test moved from `errors.As(err, &netErr)` to the scan path's `isConnErr` (which also covers EOF and a closed connection) — previously a single EOF was treated as "range read failed", zeroing the whole range **and never triggering a reconnect**; ② Modbus's TCP and RTU `Read` were two line-for-line copies and are now one `readBatch`, with each driver passing its own client and error prefix.
  **Acceptance: the core cases for all four plugins were measured against the pre-fix shape and fail without the fix.** Six cases each for Modbus and S7 (one bad point → only that point is 0; a bad address in the middle; **offsets recomputed from the new sub-range start**, pinned by a fake device that writes its own address into each value; a non-address error → the range is retried untouched, no degraded plan is cached, and recovery reads every point within one round; link errors propagate and mark the connection down; the per-round budget stays bounded and an all-confirmed range leaves nothing in the plan; and `TestReadRanges_DegradeConvergesAcrossRounds` — 80 points in one range with the first 40 missing, which needs 79 requests against a budget of 64, leaves those 40 **healthy** points at 0 after six rounds under the restore-the-parent shape). To actually exercise production code, Modbus extracted its batch loop into `readBatch` and S7 into `readOnce`, with tests passing a fake client — the previous arrangement copied the loop into the test, so it measured the test's own version and would have vouched for a wrong implementation. Two test fixtures were corrected along the way: Modbus's gap case used to model a device refusal with `errors.New("illegal data address")` (a plain error, which the new predicate classifies as a link error and propagates), now a real `ModbusError{ExceptionCode: 0x02}`; and the S7 case used the non-existent type `uint8` instead of S7's own `byte`. All seven plugins' golden baselines and the full `go test ./...` pass.

- **`Omron.FINS` / `Mitsubishi.MC`：一个点位读不到，不再把同区间的其它点位一起标成 `quality=0`**（FINS 1.2.0 → 1.2.1、MC 1.2.1 → 1.2.2）。两个驱动都把地址间隙 ≤ 合并窗口的点位合并成**一次请求**（FINS `mergeWindow` 默认 100 字、MC `maxGap` 默认 8 字），而设备对**含「不存在地址」的整个请求**是**整段拒绝**（FINS 结束码非 0；MC 结束码 `0xC051` / `0xC056` / `0x4031`）—— 于是区间里那个"越界 / 未配置"的地址一出现，`markRangeZero` 就把**整段所有点位**一起标成 `quality=0`：一个 `D32768`（`D` 只到 `D32767`）、一个没启用文件寄存器区的 `ZR`，足以让合并窗口里几十个本来好好的点位同时失去数据，而日志只有一行 `unreadable, mark N points quality=0`。现在改为**有界对半降级**：整段被拒时按点位一分为二各自重读，读得通的一半正常取值，读不通且只剩单点才确认该地址不存在（`quality=0` 并从计划里摘掉）—— 与点位扫描那条路早就有的对半降级同一形状，此前只有采集这条路做不到（三个点扫文件里都写着「驱动的 Read 那条路做不到这件事」）。
  **四个边界是承重的，缺任何一个都会从「少几个点位」变成「更糟」**：① **只对「地址类」结束码降级**（复用点扫那条路已经有的 `isAddressEndCode`，不另立判据）。`IsEndCodeError` 是全部非零结束码，其中"节点忙 / 通信错误 / 程序运行中"这类**可恢复的设备状态说明不了任何一个地址是否存在** —— 拿它去降级，一次「PLC 忙」会把整段点位逐个"确认"成地址不存在、把这份误判缓存住，比修复前（一轮 `quality=0`、下轮重试）还糟。这类错误现在整段原样留着下轮重试，一个点位都不确认。② 网络 / 超时错误照旧上抛 —— 否则一次断连会被静默成「点位质量 0」，沉进本轮数据里且永不触发重连。③ **预算在整次 `Read` 内共享**（请求数 64 + 时间 15s 双上限），且**时间窗口在首个降级请求时才锚定**，不是在 `Read` 开头：串口链路上一个批次的常规读取本身就可能花掉十几秒，从 `Read` 开头锚定的话预算一出生就过期，恰好是最需要降级的那些设备上一次都不会发生。上限本身必须远小于网关侧 `Read` 的 60s RPC 超时（连续 3 次超时会把整个插件进程判死），而对一整段全读不到的地址，对半降级会退化成一棵满二叉树。④ **预算耗尽时，留在计划里的是"停在哪一段"（`pending`）而不是原区间** —— 这一条最容易写错，也最关键：退回原区间的话，下一轮的排序、分点、每轮全新的预算都与上一轮完全相同，遍历每次都停在同一个节点，**落在未访问子树里的好点位会永远停在 `quality=0`**，"下轮接着摘"一次也不会真的发生。
  **降级结果进区间缓存（`degradedPlanTTL` 5 分钟，且不刷新已有时间戳）**：不回写的话每轮都要为同一个坏地址重付一遍「整段失败 + 对半降级」的往返，1s 周期下几十个坏地址就把采集周期拖垮；带 TTL 则是为了**能自愈** —— 现场把软元件补上、把文件寄存器区启用之后，最迟 5 分钟采集自己就恢复了。**但每轮刷新时间戳会把 TTL 变成"永不过期"**：批次里只要有另一个区间每轮都在降级，被摘出的地址就会被无限推迟，自愈永远不会发生（这正是"已有降级计划时保留原时间戳"那条的要害）。去重日志带 10 分钟 TTL 而不是一次性的：坏地址被摘出计划后就不再被读取、自然也不再打日志，后来才翻日志的人会找不到任何线索（修复前那条日志反倒是每轮都打的）。`Connect` 时计划与去重表一并清空。**MC 另有一处单位陷阱**：降级重切必须沿用区间**自己的**单位 —— 位模式按位（`Number`）、字模式按字（`Word`），位设备的字访问用 16 对齐后的位地址（`M100` 配 `int16` 时请求里的读头是 `96`）。拿位地址去算字模式的点数不会报任何错，只会把读头落到**别的字**上，读到的是别处的数据而值看着完全合理。
  回归：`finsdrv/degrade_test.go` 与 `mitsubishidrv/degrade_test.go` 各六条。核心两条**都验证过"修复前必挂"**：`TestDriverReadDegradeConvergesAcrossRounds`（80 点合并成一个区间，前 40 个设备上不存在、后 40 个是好的；摘完前 40 个要 79 次请求 > 64 的预算，所以第一轮必然在中途停下 —— 退回原区间的写法下，6 轮之后那 40 个**好点位**仍取不到值）与 `TestDriverReadNonAddressEndCodeKeepsWholeRange`（"先忙后好"的假设备：忙时只发一次请求、不降级、不留降级计划，恢复后一轮内全部取到值）。其余四条：单点坏 → 仅该点 0；坏地址夹在中间 → 前后照常取值；**降级后按新起点重算偏移**由「字里写着自己的地址」的假设备钉住（MC 的位模式与位设备字访问两条单位路径另逐请求断言）；网络错误仍上抛；预算上限逐轮有界、且全部确认读不到之后计划里不再留着它们；降级计划命中后第二轮不再发那个必然失败的区间；TTL 到期 + 设备侧补上地址 → 自愈。既有用例（`TestDriverReadEndCodeError`、`TestDriverReadPipeline`、`TestDriverReadBitMode`）与七个协议的黄金基线一字未改地继续通过 —— 基线里没有区间被拒的场景。
  **`Omron.FINS` / `Mitsubishi.MC`: one unreadable point no longer drags every other point in its read range down to `quality=0`** (FINS 1.2.0 → 1.2.1, MC 1.2.1 → 1.2.2). Both drivers merge points whose address gap is within a merge window into **a single request** (FINS `mergeWindow`, default 100 words; MC `maxGap`, default 8 words), and the device **rejects the whole request** when it covers a non-existent address (a non-zero FINS end code; MC end code `0xC051` / `0xC056` / `0x4031`). So the moment one out-of-range or unconfigured address landed in a range, `markRangeZero` marked **every point in that range** `quality=0`: a single `D32768` (where `D` stops at `D32767`) or a `ZR` with no file-register area enabled was enough to strip data from dozens of healthy points inside the merge window, with nothing in the log but `unreadable, mark N points quality=0`. The read path now does a **bounded bisection**: on rejection it splits the range's points in half and re-reads each half — a half that reads is decoded normally, and only a single point that still draws a rejection is confirmed non-existent (`quality=0`, dropped from the plan). This is the same shape the point-scan path has had all along; all three point-scan files say outright that "the driver's Read path cannot do this," and it now can.
  **Four bounds are load-bearing — omit any one and "a few missing points" becomes something worse**: ① **degrade only on "address-class" end codes** (reusing the scan path's existing `isAddressEndCode`, not a second predicate). `IsEndCodeError` is every non-zero end code, and recoverable device states such as "node busy / communication error / program running" **say nothing about whether any address exists** — degrading on those would confirm every point in the range as non-existent one by one and cache that misjudgement, which is worse than the behaviour being fixed (one round of `quality=0`, retried next poll). Such errors now leave the range intact for a retry and confirm nothing. ② Network and timeout errors still propagate, or a lost link gets silently downgraded to "point quality 0", sinks into the round's data and never triggers a reconnect. ③ **One budget shared across the whole `Read`** (64 requests and 15 s, both capped), with the **time window anchored at the first degrade request** rather than at the start of `Read`: on a serial link a batch's ordinary reads alone can take more than fifteen seconds, and anchoring early means the budget is born expired — on exactly the devices that need degradation most, it would never once happen. The caps themselves must stay far below the gateway's 60 s `Read` RPC timeout (three consecutive timeouts kill the entire plugin process), because bisecting a span where *nothing* is readable degenerates into a full binary tree. ④ **When the budget runs out, what stays in the plan is "where the traversal stopped" (`pending`), not the original range** — the easiest of the four to get wrong and the most important: restoring the parent range makes every subsequent round repeat an identical traversal (same sort, same half-split, a fresh budget each time) that halts at the same node, so **healthy points sitting in never-visited subtrees stay at `quality=0` forever** and "continues next round" never actually happens.
  **The isolation result goes into the range cache (`degradedPlanTTL`, 5 minutes, with an existing timestamp never refreshed)**: without writing it back, every poll cycle re-pays "range rejected + bisection" for the same bad address, and a few dozen bad addresses sink a 1 s cycle. The TTL is what makes it **self-healing**: once the address exists on the device side (or the file-register area is enabled), collection recovers within 5 minutes. **Refreshing the timestamp every round would turn that TTL into "never expires"**: as long as any other range in the batch keeps degrading, the excluded address is pushed back indefinitely and the self-heal never fires — which is precisely what "keep the original timestamp when a degraded plan already exists" is for. Dedup logs carry a 10-minute TTL rather than being one-shot: once an address is dropped from the plan it is no longer read and therefore no longer logged, so someone reading the log later would find no trace at all (the line being replaced was printed every cycle). `Connect` clears both the plan cache and the dedup table. **MC carries one extra unit trap**: the re-split must use the range's **own** unit — bit mode counts bits (`Number`), word mode counts words (`Word`), and a bit device's word access uses the 16-aligned bit address (for `M100` typed `int16` the request head is `96`). Computing word-mode point counts from bit addresses raises no error at all; it merely puts the read head on a **different word**, returning data from elsewhere that looks entirely plausible.
  Regressions: six cases each in `finsdrv/degrade_test.go` and `mitsubishidrv/degrade_test.go`. The two central ones were **both verified to fail against the pre-fix shape**: `TestDriverReadDegradeConvergesAcrossRounds` (80 points merged into one range, the first 40 of which do not exist on the device and the last 40 of which are healthy; finishing the bad half needs 79 requests against a budget of 64, so round one necessarily stops midway — under the restore-the-parent shape those 40 **healthy** points are still unread after six rounds) and `TestDriverReadNonAddressEndCodeKeepsWholeRange` (a "busy then healthy" fake device: while busy exactly one request is sent, nothing degrades and no degraded plan is cached; after recovery every point reads within one round). The other four: one bad point → only that point is 0; a bad address in the middle → its neighbours still read; **offsets recomputed from the new sub-range start**, pinned by a fake device that writes its own address into each word (with MC's bit-mode and bit-device-word-access unit paths asserted request by request); network errors still propagate; the per-round budget stays bounded and an all-bad range leaves nothing behind in the plan; a cached degraded plan never re-sends the doomed range; and TTL expiry plus a fixed device → recovery. Existing cases (`TestDriverReadEndCodeError`, `TestDriverReadPipeline`, `TestDriverReadBitMode`) and all seven plugins' golden baselines pass unchanged — no baseline covers a rejected range.

- **「测试连接」失败时会说明这个地址当前正被哪台设备采着，不再只甩一句 `i/o timeout`**。真机 2026-09-29 现场：`10.62.100.22:10000`（三菱 MC TCP）**采集一切正常，测试连接必报** `mc: ping connect failed: mc tcp: dial 10.62.100.22:10000 failed: dial tcp 10.62.100.22:10000: i/o timeout`。根因既不在网关也不在超时值：**那台 PLC 一次只服务一条 MC 连接**（内置以太网的「开放式设置」按连接槽分配，现场只开了一条），采集会话占着那一条 —— 用**与驱动逐字节相同**的 3E 帧从网关机器另开连接去读 `D0`，第一次 TCP 握手成功但 5 秒无应答，连续重试之后连握手都不再被接受，而同一时刻采集侧照读不误。而「测试连接」按既有设计**不复用** TCP 连接（`mcDriver.MatchConnection` 只让串口参与复用），于是它开出的第二条连接必然撞上那个拒绝，报出来的却是一句与真相毫无关系的网络超时。**复用策略本次刻意未改**（TCP 复用会让这次 ping 排在一次可能很长的批量读取后面，见 [docs/driver-plugins.md](docs/driver-plugins.md) §3.5 —— 那条已知代价现在写在了明处），改的是**错误提示**：新增跨协议约定 `host` / `port`（`driver.HostField` / `PortField` / `ExtractEndpoint`，返回 `host:port`，数字与字符串端口都认；端口非法或不填时只给 host，**不拿协议默认端口去猜**）、`collector.EndpointHolder` / `Engine.EndpointHolders()`（与串口那个 holder 共用 `eachLiveDevice` 这一份筛选规则：没有驱动实例的设备一律排除）、`service.endpointBusyHint`，并把三个入口（测试连接 / 点位扫描失败 / 点位扫描中断）的说明块拼装统一到 `service.busyHint` **一处** —— 同一件事在两个入口给出不同说法，是这套提示最怕的漂移。**判据与串口相同（"这个目标配给了谁"），只是分档依据不同**：TCP 目标不是独占资源（网关自己就是开连接的那一方），故 `Connected` 只用来分档措辞（"该设备正在采集" / "当前未连接"）。初版按 `Connected` **过滤**，当天就被真机打回：设备侧那个唯一的连接槽被一条**已死**的连接占住后（对端断开它不会立刻察觉），PLC 一律拒绝新连接，此时网关侧没有任何"正在采集"的设备，而未连接的这台才是那个地址唯一的历史持有者 —— 过滤恰好让提示在最需要它的时刻一声不吭。措辞沿用串口那条纪律：只说事实（这个地址配给了谁、那台设备正在采集）加一句可被证伪的推测（"若被测设备只允许一条连接"），不匹配 OS/驱动的错误文本，也不断言因果。**点扫路径同样受益**：设备开始采集之后再对它做「自动发现点位」，走的也是"回落临时实例"那条路（`driversdk.selectSession` 的 TCP 一列），原先会以同样的方式超时失败。回归：`driver/endpoint_test.go` 的 `TestExtractEndpoint`、`collector/endpointholder_test.go` 的 `TestEndpointHolders`、`service/devicePingHint_test.go` 的 `TestEndpointBusyHint` 与 `TestBusyHint`；既有的 `TestSerialBusyHint` / `TestSerialPortHolders` 一字未改地继续通过 —— 串口那条路只搬了拼装位置，判据没动。
  **A failed "test connection" now says which device is currently collecting that address, instead of a bare `i/o timeout`.** Real hardware, 2026-09-29: on `10.62.100.22:10000` (Mitsubishi MC over TCP) **collection was perfectly healthy while every connection test failed** with `mc: ping connect failed: mc tcp: dial 10.62.100.22:10000 failed: dial tcp 10.62.100.22:10000: i/o timeout`. The cause was neither the gateway nor the timeout value: **that PLC serves only one MC connection at a time** (a built-in Ethernet "Open Setting" allocates connection slots and only one was configured), and the collection session holds it. Sending a **byte-for-byte identical 3E frame** over a fresh connection from the gateway host to read `D0`: the first attempt completed the TCP handshake but drew no answer for 5 seconds, and after a couple of retries even the handshake stopped being accepted — while collection kept reading normally throughout. The connection test, by existing design, **does not reuse** a TCP connection (`mcDriver.MatchConnection` only lets serial participate), so its second connection lands on exactly that refusal and reports a network timeout that has nothing to do with reality. **The reuse policy was deliberately left alone** (reusing over TCP would make this ping queue behind a potentially long batch read — see §3.5 of [docs/driver-plugins.md](docs/driver-plugins.md), where that known cost is now stated outright); what changed is the **message**: a new cross-protocol convention for `host` / `port` (`driver.HostField` / `PortField` / `ExtractEndpoint`, returning `host:port`, accepting both numeric and string ports and returning the host alone rather than **guessing** a protocol's default port), `collector.EndpointHolder` / `Engine.EndpointHolders()` (sharing the single `eachLiveDevice` filter with the serial holder: any device without a driver instance is excluded), and `service.endpointBusyHint` — with the hint block now assembled in **one** place, `service.busyHint`, for all three entry points (test connection, point-scan failure, point-scan interrupt), because the failure mode this family of hints fears most is the same situation being described two different ways. **The predicate matches the serial one (who the target is configured for); only the wording tiers differ**: a TCP target is not an exclusive resource (the gateway is the one opening connections), so `Connected` decides between "the device is collecting" and "currently disconnected" rather than acting as a filter. The first cut *did* filter on `Connected` and real hardware overruled it the same day: once the device's single connection slot is held by a **dead** connection (the peer's disconnect is not noticed immediately), the PLC refuses every new connection, the gateway then has no "currently collecting" device at all, and the disconnected holder is the only historical one for that address — filtering made the hint go silent exactly when it was needed most. The wording keeps the serial discipline: state facts (who the address is configured for, that the device is collecting) plus one falsifiable guess ("if the device under test allows only one connection"), never matching OS/driver error text and never asserting causation. **The point-scan path benefits too**: running "auto-discover points" on a device that has already started collecting takes the same temp-instance fallback (`driversdk.selectSession`'s TCP column) and used to time out the same way.   **同一次排查还带回第二个 bug：结束码错误的应答体没读干净，会把这条 TCP 连接上的后续请求全部读错位。** 那台 PLC 回结束码错误时**不是**「数据长度 2、只有结束码」，而是「数据长度 11 = 结束码(2) + 出错站信息 9 字节（网络/PC/I-O/站 + 命令回显）」；`mcTCPClient.Read` 只看 11 字节头、一发现结束码非 0 就返回，那 9 字节留在流里 —— 下一条请求读到的是**错位的窗口**（子头不再是 `0xD0`），报出来的是 `unexpected response subheader`，与真正的故障毫无关系，而且这条连接此后再也读不到一次成功。现在结束码分支先把数据段读走再返回（读不干净就标记断连让采集侧重连：留一条永远错位的连接比断掉更糟，它不会自愈）。**采集路径同样受益**：这台 PLC 上任何一个越界点位，原先都会让后续每一轮都报子头错误。

  **Mitsubishi point scan: end code `0x4031` (specified device number out of range) is no longer treated as "scan failed"** (plugin version 1.2.0 → 1.2.1). Real hardware, 2026-09-29: scanning `ZR` on `10.62.100.22:10000` (the form's default 64 points at bit width, i.e. `ZR0.0 … ZR3.15`) aborted the whole sweep with "scan failed: reading ZR0.0 … ZR3.15: mc: end code 0x4031" — which points the user at a dead device or an incompatible protocol, while **that PLC was reachable throughout** (`D`/`M`/`W`/`SD`/`X`/`B` all read fine). The cause is that the allowlist is a list of **values** and only carried the QnA-compatible ones: the same "address out of range" is `0x4031` in the iQ family (`endCodeDeviceRange`, added to `frame.go`). Measured on that PLC: `D32768` (its `D` only reaches `D32767`), `W9999999`, and **any `ZR`/`R` address while the file-register area is empty** all answer with it, whereas overrunning a component's **number space** (`M9999999`/`B9999999`/`SD999999`) answers the already-known `0xC056`. So `0x4031` carries two duties: **"past the end of this area"** (without it, **sweeping `D` across `D32767` aborts too**, instead of the intended "stop at the end") and **"this entire component has no readable address"** (the same reasoning as `0xC051`). With it allowlisted, the scan reports what is actually true: 64 scanned, 0 readable — that CPU has no file register configured (`PLC Parameter → PLC File Settings` in GX Works, "Not used" by default), so `ZR`/`R` genuinely have no readable address on the device side.
  **The same investigation turned up a second bug: the body of an end-code error reply was not drained, which misaligns every later request on that TCP connection.** That PLC's error replies are **not** "data length 2, end code only" but "data length 11 = end code (2) + 9 bytes of error station information (network / PC / I-O / station + command echo)"; `mcTCPClient.Read` read the 11-byte header, saw a non-zero end code and returned, leaving those 9 bytes in the stream — the next request then read a **shifted window** (its sub-header is no longer `0xD0`) and reported `unexpected response subheader`, which has nothing to do with the real fault, and that connection never succeeded again. The end-code branch now drains the body before returning (marking the connection down if the drain fails — a permanently misaligned connection is worse than a dropped one, since it does not self-heal). **The collection path benefits too**: on this PLC any single out-of-range point used to make every later cycle report a sub-header error.
  Regressions: `TestIsAddressEndCode` (one more allowlisted value) and `TestScanPointsTreatsDeviceRangeEndCodeAsAddressEnd` in `mitsubishidrv/pointscan_test.go` (ZR, start 0, bit width, 64 points, every reply shaped like the real device's — without the fix it reports the user's exact sentence), plus `TestTCPClientEndCodeWithBody` in `mitsubishidrv/client_test.go` (an error reply carrying a 9-byte body, followed by a second request that must still succeed; the existing `TestTCPClientEndCode` uses the "data length 2, no body" shape and therefore cannot catch this — both shapes need a case). The spec and the plugin-author guide had their now-untenable "every MC end code lives in `0xC0xx`" wording corrected as well.

- **`Omron.CIP`：设备拒绝读某个标签，不再被当成「整台设备读取失败」**（插件版本 1.1.0 → 1.1.1）。真机 2026-09-29 现场：`10.62.100.16`（NX1P2-1140DT）上一个点位名写成 `Recipe.Setpoint`，设备回通用状态 `0x05 (path destination unknown)`，于是采集引擎每轮都判这台设备读取失败 —— **设备被反复置为离线并触发断联报警，而 PLC 一直是通的**（同一时刻 `ping` 正常、会话句柄照常注册）。根因不在协议层：`cipClient.ReadTags` 在 `len(specs) == 1` 时退化为单读，却把设备拒绝（通用状态错误）直接 `return nil, err` 当成函数级错误上抛 —— 这与它自己在 `cipTransport` 接口上写明的语义（「结果 `Err` 非 nil 表示该标签被设备拒绝（连接仍通）」）相反，也让**同一个点位**因类型/配置不同得到两种结局：走批量路径（定长类型 + 默认 `maxTagsPerRequest=64`）时整台设备离线，走单读路径（`string` 类型或 `maxTagsPerRequest=1`）时只是该点 `quality=0`。也就是说，一个名字写错的点位足以让整台设备的**所有**点位一起失去数据。现在单标签分支经 `singleTagResult` 分类：设备拒绝 → 逐标签 `Err`（`driver.Read` 的 `flush` 早已会把它落成该点 `quality=0` 并继续读其它标签），只有网络/协议错误才上抛。**同时补上 `flush` 里整批被拒的分支**：整批回通用状态错误（如 `0x08` 多服务报文不受支持）时把该批点位一并置 `quality=0` 而不是判设备失败 —— 否则一个协议层拒绝会让设备永久离线，日志里只有一句 `read device failed`，看不出「设备不支持批量、把 `maxTagsPerRequest` 调成 1 即可」这种可配置规避的原因。**成员路径（`Recipe.Setpoint`）与数组下标（`Array[3]`）仍未经真机验证**：驱动把整串名字编进**单个** ANSI 扩展符号段，而欧姆龙变量访问的成员/下标本应由多个路径段拼出；设备对扁平名回 `0x04`、对带点名回 `0x05`，只能说明它按两种方式解析了路径，**不能**说明这种单段写法能被解析。要结掉这条，得在 PLC 上真建一个已公开的结构体变量再逐字节核对。回归：`omroncipdrv/client_test.go` 的 `TestReadTagsSingleTagDeviceDenied`（走**真实 TCP 回环**的假 PLC —— mock 传输层恰好绕开了出问题的那一行，此前 mock 测试全绿而真机整台设备离线）与反面对照 `TestReadTagsSingleTagNetworkError`（网络错误必须仍然上抛，否则断连会被静默成「点位质量 0」、永不触发重连），以及 `driver_test.go` 的 `TestDriverReadSingleTagBatchDenied`、`TestDriverReadWholeBatchRejected`。
  **`Omron.CIP`: a device refusing to read one tag is no longer treated as "the whole device failed to read"** (plugin version 1.1.0 → 1.1.1). Real hardware, 2026-09-29: on `10.62.100.16` (NX1P2-1140DT) one point was named `Recipe.Setpoint`, the device answered general status `0x05 (path destination unknown)`, and the collector consequently failed the device every single cycle — **the device was repeatedly marked offline and raised disconnect alarms while the PLC was reachable the whole time** (ping succeeded and the session handle registered normally in the same seconds). The root cause is not in the protocol layer: when `len(specs) == 1`, `cipClient.ReadTags` degenerates to a single read but returned the device's refusal (a general status error) as `nil, err`, a function-level failure — the opposite of the semantics it documents on its own `cipTransport` interface ("a non-nil `Err` means the tag was refused by the device, the connection is still up"). That also gave **one and the same point** two different outcomes depending on type and configuration: via the batch path (fixed-size type with the default `maxTagsPerRequest=64`) the entire device went offline, while via the single-read path (`string` type or `maxTagsPerRequest=1`) only that point reported `quality=0`. A single misspelled point name was therefore enough to strip data from **every** point on the device. The single-tag branch now classifies through `singleTagResult`: a device refusal becomes a per-tag `Err` (which `driver.Read`'s `flush` already turns into `quality=0` for that point and then continues with the other tags), and only network/protocol errors propagate. **A branch for a wholly rejected batch was added to `flush` as well**: when the entire batch draws a general status error (e.g. `0x08`, multi-service packets unsupported) those points are marked `quality=0` instead of failing the device — otherwise a protocol-level refusal takes the device permanently offline with nothing in the log but `read device failed`, concealing the configurable workaround (`maxTagsPerRequest=1`). **Structure member paths (`Recipe.Setpoint`) and array indices (`Array[3]`) remain unverified against real hardware**: the driver packs the whole dotted name into a **single** ANSI extended symbol segment, whereas Omron variable access is supposed to build members and indices from multiple path segments; the device answering `0x04` to a flat name and `0x05` to a dotted one only shows that it parsed the path two different ways, **not** that this single-segment form is accepted. Settling it requires a published structure variable on a real PLC and a byte-level check. Regressions: `TestReadTagsSingleTagDeviceDenied` in `omroncipdrv/client_test.go` (against a fake PLC over a **real TCP loopback** — the mock transport bypasses exactly the line that was broken, which is why the mock tests were all green while the real device was offline) plus its counter-case `TestReadTagsSingleTagNetworkError` (network errors must still propagate, or a lost link would be silently downgraded to "point quality 0" and never trigger a reconnect), and `TestDriverReadSingleTagBatchDenied` / `TestDriverReadWholeBatchRejected` in `driver_test.go`.

- **设备扫描真的按插件声明的 `TargetMode` 生成目标了；同一台设备不再重复上报**。`TargetMode` 写在契约里、由 `driversdk.Meta.Validate` 校验，**但引擎侧的目标展开从来没有读它** —— 一律逐主机展开，于是「声明了广播的插件」拿到的仍是两百多个主机地址，而两边都不报错。症状是广播型协议（EtherNet/IP 的 ListIdentity、FINS/UDP 的节点查询）**扫得又慢、在部分网络上还扫不到**，日志里没有任何线索。现在 `expandTargets` 按 `unicast` / `broadcast` / `both` 三种模式产出目标，广播目标是各网段的**子网广播地址**（`ip | ^mask`，不是 `255.255.255.255`）并带 `LocalIP` 供源地址绑定，且**排在逐主机目标之前** —— 它一个就覆盖整个网段，排在两百多个目标之后就会在大网段触顶时永远轮不到它。掩码不在 `[1,30]` 的网段（`/31`、`/32`）没有广播地址的概念，跳过。同时引擎按 `host:port:unitId` 对结果**去重**：`TargetMode=both` 下同一台设备会被广播与它自己的单播目标各报一次，不去重的话用户看到两份一模一样的设备行，而他无从判断这是「两台设备」还是「重复」。键里带 `unitId` 是必须的 —— 同一 IP:端口上的不同站号是协议定义的真实区分，合并它们会把本该建成多台设备的发现压成一台。回归：`devicescan/targets_test.go`（三种模式的展开、广播目标优先、`requested` 与目标数恒等、`/31` `/32` 跳过）与 `devicescan/engine_test.go` 的 `TestBroadcastSpecPlansBroadcastTarget`、`TestDedupDropsSameDeviceFromTwoTargets`、`TestDedupKeepsDistinctUnits`。一处测试夹具随之修正：`service` 里"重名逐条报错"那个用例原先给三条设备填了**相同的站号**，而夹具会把 Host 统一覆写成探测目标地址 —— 三条记录逐字段相同，在新去重下会合成一条，那个用例考的就不再是重名了（真实探测器的形态是一个目标产出多台设备时靠站号区分）。
  **Device scan now honours the plugin's declared `TargetMode`, and the same device is no longer reported twice.** `TargetMode` lived in the contract and was validated by `driversdk.Meta.Validate`, **but the engine's target expansion never read it** — everything was expanded per-host, so a plugin declaring broadcast still received 254 host addresses, with no error on either side. Broadcast-shaped protocols (EtherNet/IP ListIdentity, FINS/UDP node queries) were therefore **slow, and on some networks found nothing at all**, with no hint in the logs. `expandTargets` now produces targets per `unicast` / `broadcast` / `both`, emitting **subnet broadcast addresses** (`ip | ^mask`, never `255.255.255.255`) carrying `LocalIP` for source binding, and **placing them ahead of per-host targets** — one broadcast covers the whole subnet, and anywhere behind 254 hosts it would never be reached once a large subnet hits the cap. Masks outside `[1,30]` (`/31`, `/32`) have no broadcast address and are skipped. The engine also **deduplicates results by `host:port:unitId`**: under `TargetMode=both` the same device is reported once by the broadcast target and once by its own unicast target, and without dedup the user sees two identical device rows while being unable to tell "two devices" from "a duplicate". `unitId` must be part of the key — different station numbers on one IP:port are a protocol-defined distinction, and merging them would collapse a multi-device discovery into one. Regressions: `devicescan/targets_test.go` (all three modes, broadcast-first ordering, `requested` matching the target count, `/31` and `/32` skipped) and `TestBroadcastSpecPlansBroadcastTarget`, `TestDedupDropsSameDeviceFromTwoTargets`, `TestDedupKeepsDistinctUnits` in `devicescan/engine_test.go`. One test fixture was corrected along the way: the "duplicate names are rejected row by row" case in `service` gave all three devices the **same station number** while the fixture overwrites Host with the probe target's address — the three records were field-for-field identical and would collapse into one under the new dedup, so the case was no longer testing duplicate names at all (a real prober distinguishes multiple devices from one target by station number).

- **点位扫描中途断链时，已经读到的点位不再被丢掉**。插件（`ScanPoints` 在连接类错误上 `return sc.finish(), chunkErr`）、宿主（`pluginhost.DiscoverPoints` 判了「reply 非空就一并返回」）、契约（`FindPointsFunc` 第 3 条）三方都刻意保下了这份结果，服务层却在 `if err != nil` 处把它扔了 —— 于是一次「串口扫到第 800 个地址掉线」只给用户一句「扫描失败」，前 800 个候选点位全部作废，得从头再扫十几秒。现在改为：结果非空（`Scanned > 0 || len(Points) > 0`，与宿主的过滤口径一致）时照常返回 VO，并把根因放进新增的 `warning` 字段（前端在结果区顶部以告警条显示）；同时**补置 `Incomplete`** —— 插件侧的该标志只在预算耗尽时置位，链路中断不经过那条分支，不补的话用户会把一份截断的清单当成全量。扫描根本没开始的失败（选项解析失败、设备正忙、配置模式）结果为空，照旧走业务错误码。回归见 `service/devicePointScanService_test.go` 的 `TestDiscoverPointsKeepsPartialResultOnFailure` 与 `TestDiscoverPointsNoPartialResultStillFails`。
  **A point scan that loses the link mid-sweep no longer discards what it already read.** The plugin (`ScanPoints` returns `sc.finish(), chunkErr` on connection-class errors), the host (`pluginhost.DiscoverPoints` deliberately returns a non-empty reply alongside the error) and the contract (`FindPointsFunc` rule 3) all preserve that partial result — and the service layer then threw it away at `if err != nil`. A serial scan that died at address 800 gave the user a bare "scan failed" and voided the first 800 candidates. Now a non-empty result (`Scanned > 0 || len(Points) > 0`, the same filter the host uses) is returned as a normal VO with the root cause in a new `warning` field (rendered as an alert above the results); `Incomplete` is **also forced on**, because the plugin only sets that flag when the budget runs out and a broken link never goes through that branch — without it the user would read a truncated list as the complete one. Failures where the scan never started (bad options, device busy, config mode) carry an empty result and still return a business error. Regressions: `TestDiscoverPointsKeepsPartialResultOnFailure` and `TestDiscoverPointsNoPartialResultStillFails` in `service/devicePointScanService_test.go`.
- **点位扫描弹窗显示的是实际生效的预算**。原来显示插件声明的 `maxBudgetMs`（Modbus 是 20000ms），而网关会把同步 HTTP 这条链路钳到 7000ms —— 用户按 20 秒预估，实际 7 秒就停了并看到「未扫完」，于是去怀疑设备与链路。响应里新增 `effectiveBudgetMs`（= `pluginhost.BudgetWithinGatewayCapMs`，钳制逻辑仍只有那一处实现），前端显示它，声明值照样返回供排查。回归见 `TestPointCapabilityExposesEffectiveBudget`。
  **The point-scan dialog now shows the budget that actually applies.** It used to show the plugin-declared `maxBudgetMs` (20000 ms for Modbus) while the gateway clamps this synchronous-HTTP path to 7000 ms — the user budgeted 20 seconds, the scan stopped at 7 and reported "incomplete", and they went off to blame the device and the link. The response now carries `effectiveBudgetMs` (= `pluginhost.BudgetWithinGatewayCapMs`, still the single implementation of that clamp); the declared value is still returned for troubleshooting. Regression: `TestPointCapabilityExposesEffectiveBudget`.
- **两项前端修复**：① 局域网扫描页**首次进入时「扫描参数」表单不渲染** —— `fetchCapabilities` 设了默认协议却没调 `renderScanForm`（它只挂在 `el-select` 的 `@change` 上，而程序赋值不触发该事件），于是 form-create 从不挂载，用户看不到「站号 / 拨号超时 / 单帧超时」，必须把协议切走再切回来才出现；② 批量建设备 / 批量建点位时**失败的行被一并从结果表里摘掉**，用户连改名重试的入口都没有，只能重扫。现在只摘掉真正入库的行，失败的行留在表里并保持勾选，改完即可再提交（`errors[].row` 是提交数组里的 1-based 下标）。
  **Two front-end fixes**: (1) the LAN scan page **did not render the plugin scan-options form on first load** — `fetchCapabilities` set the default protocol but never called `renderScanForm`, which is wired only to the `el-select`'s `@change` event and is not fired by a programmatic assignment; form-create never mounted, so the unit-id / dial-timeout / frame-timeout inputs were invisible until the protocol was toggled away and back. (2) When creating devices or points in bulk, **failed rows were removed from the result table along with the successful ones**, leaving no way to retry a duplicate name short of rescanning. Now only rows that were actually inserted are removed; failed rows stay in the table and stay selected so the user can fix and resubmit (`errors[].row` is the 1-based index into the submitted array).

### Added

- **压测框架新增 `-serial-baud`：无需串口硬件即可压测串口链路容量**。串口容量里唯一需要「测」的量是表处理时间，其余全是算术（帧数 = ⌈点数/`maxDIsPerRead`⌉、线路时间 = 帧字节数 ÷ 波特率），而现有假表的 `-latency` 是**逐帧**注入的，与「一帧占一段线路时间」同构 —— 于是只要把线路时间折算出来喂进去即可。新开关按协议帧布局自动折算并**叠加**到 `-latency`（后者留给表处理时间），折算过程打印出来供复核：
  ```
  serial modeled: 2400bps 8E1 (11 bits/byte) × 168 bytes/frame = 770ms line time (+ -latency 50ms = 820ms per frame)
  ```
  帧字节数随打包数变化（645 的 2007 读命令为 `12+4N` 请求 / `12+N×(4+每标识数据字节)` 应答），故 `-dlt645-dis` 会连带改变线路时间。按 8E1（11 位/字节）折算，与 645 电表出厂默认一致。`serialFrameBytes` 是协议适配器上的**可选钩子**，目前只有 dlt645 实现 —— 其余协议带该开关运行会**直接报错退出**，而不是静默按 0 处理：一个「配了却不生效」的开关会让人以为测的是串口容量，实际测的还是 loopback，比没有这个开关糟得多。验收：`cmd/loadtest/harness_test.go` 钉住折算算术，并把 README 里举例的「168 字节 / 770ms」钉在代码上（文档与代码任何一侧改动都会立刻暴露）。
  同时订正一处方向的误导：**不要**用虚拟串口对（com0com / socat）压测串口 —— 它们按内存速度传数据、不模拟波特率时序，每帧时间接近 0，会给出严重乐观的容量数字，比不测更危险。该结论已写入 README 的「串口容量」小节。
  首轮实测结果已落进 README 的同名小节：每帧往返 2400bps **823.5ms** / 9600bps **243.8ms** / 115200bps **68.0ms**（与「线路时间 + 表处理」模型偏差均 <3%）；单表点数上限 scan=10s 下约 96 / 336 / 1220 点。**最值得注意的结论是提波特率收益递减**：线路时间占每帧的比例从 2400bps 的 94% 降到 115200bps 的 24%，交叉点在约 38400bps —— 超过它之后瓶颈变成电表自身的应答速度。表处理时间按 50ms 假设，是该组数字里唯一需要真表校准的输入。
  **New `-serial-baud` flag in the load-test harness: serial link capacity can now be measured without serial hardware.** The only quantity in serial capacity that must be *measured* is the meter's processing time — everything else is arithmetic (frames = ⌈points / `maxDIsPerRead`⌉, line time = frame bytes ÷ baud), and the existing fake's `-latency` is injected **per frame**, which is structurally identical to "one frame occupies one stretch of line time". So the line time just has to be derived and fed in. The new flag derives it from the protocol frame layout and **adds** it to `-latency` (which is left for meter processing time), printing the derivation for review:
  ```
  serial modeled: 2400bps 8E1 (11 bits/byte) × 168 bytes/frame = 770ms line time (+ -latency 50ms = 820ms per frame)
  ```
  The frame size varies with the packing count (for DL/T 645-2007 reads: `12+4N` request / `12+N×(4+data bytes per identifier)` response), so `-dlt645-dis` changes the line time too. Framing is fixed at 8E1 (11 bits/byte), matching the 645 meter default. `serialFrameBytes` is an **optional hook** on the protocol adapter and only dlt645 implements it — other protocols given this flag **fail loudly** rather than silently treating it as 0: a flag that is set but has no effect makes you think you are measuring serial capacity while you are still measuring loopback, which is worse than not having the flag. Acceptance: `cmd/loadtest/harness_test.go` pins the derivation arithmetic and pins the README's "168 bytes / 770ms" example to the code, so a change on either side surfaces immediately.
  One piece of misleading guidance was corrected at the same time: **do not** use a virtual port pair (com0com / socat) to load-test serial — those move bytes at memory speed and do not model baud-rate timing, so the per-frame time comes out near zero and the capacity is wildly optimistic, which is worse than not testing. This is documented in the README's "Serial capacity" section.
  The first round of measurements is now in that same README section: per-frame round trip of **823.5ms** at 2400bps / **243.8ms** at 9600bps / **68.0ms** at 115200bps (all within 3% of the "line time + meter processing" model), and a per-meter point ceiling at scan=10s of roughly 96 / 336 / 1220 points. **The most notable finding is the diminishing return on baud rate**: the line's share of each frame falls from 94% at 2400bps to 24% at 115200bps, with the crossover around 38400bps — above which the meter's own response speed becomes the bottleneck. Meter processing time is assumed at 50ms, the one input in that set that needs calibrating against a real meter.

### Changed

- **`driversdk.Main` / `Serve` / `ServeConn` 新增第三个参数 `driversdk.Probers`（插件作者可见的签名变更）**。不提供局域网扫描发现的插件传 `nil` 即可，仓库内 8 个插件各自只加了一个 `nil`。**注意这不是一次全量重编的要求**：`Protocol.Discovery` 是可选字段，插件的元数据与线协议都向后兼容 —— 只要你不需要扫描能力，旧二进制在新网关上照常工作；只有要实现扫描能力的插件才必须用新套件重编。
  另有两处行为变更：`client.call` 的 `ctx.Done` 分支现在只在 `DeadlineExceeded` 时计入卡死计数（主动取消不计入，理由见上面的 Added），对既有调用方零影响 —— `Connect`/`Read`/`Ping`/`Close` 的超时全部由 `context.WithTimeout(context.Background(), …)` 派生，`ctx.Err()` 只可能是 `DeadlineExceeded`。`Meta.Validate` 新增了表单 JSON 合法性检查，并把判定排在序列化检查**之前** —— 此前一份写坏的 `FormJSON` 会先撞上「DataType 的 Decode/Encode/Format 必须带 json:"-" 标签」那条错误，把作者引向与表单毫无关系的地方。
  **`driversdk.Main` / `Serve` / `ServeConn` take a third argument, `driversdk.Probers` (a signature change visible to plugin authors).** Plugins that do not offer LAN scan discovery pass `nil`; the eight in-tree plugins each gained exactly one `nil`. **Note this is not a wholesale rebuild requirement**: `Protocol.Discovery` is an optional field and both the metadata and the wire protocol are backward compatible — if you do not need scanning, your existing binaries keep working against the new gateway, and only a plugin that wants to implement scanning must be rebuilt with the new SDK.
  Two behavioural changes besides: `client.call` now counts a `ctx.Done` toward the stuck-detection streak only when it is a `DeadlineExceeded` (a deliberate cancel does not — see Added above), with no impact on existing callers, since `Connect`/`Read`/`Ping`/`Close` all derive their deadlines from `context.WithTimeout(context.Background(), …)` and can therefore only ever see `DeadlineExceeded`. And `Meta.Validate` gained a form-JSON validity check that runs **before** the serialisability check — previously a malformed `FormJSON` tripped the DataType `json:"-"` tag error first, pointing the author at something entirely unrelated to the form.

- **DL/T 645 性能修复与出厂默认值调整：单帧成本降到 1/73，默认配置从「2000 点档起 100% 掉点」变为可直接使用**。压测报告此前把该协议的问题归因为两个可调参数（`maxDIsPerRead` 出厂 1 = 一点一帧、`interFrameDelayMs` 出厂 30ms），但按报告调到最优后仍不达标（50 设备 × 5000 点 @1s 掉 1.6%，同矩阵其它协议 0%）。用 benchmark 把驱动从采集引擎里隔离出来定位到真因：**`exchange()` 每帧开头的 `t.Drain()` 占了每帧成本的 98.7%**（1,537,655 ns/帧）。它用「设 1ms 截止时间再读」清残留字节，而干净链路的接收缓冲本就是空的，那次读必然空等到截止时间——**每帧白等 1ms**，且帧数随点位数线性增长（帧数 = ⌈点数/`maxDIsPerRead`⌉），直接变成单设备轮询周期的下限。
  修法是先用一次零成本探测（Windows `WSAIoctl(FIONREAD)` / 类 unix `ioctl(TIOCINQ)`，实测 676ns，新增 `driversrc/dlt645/dlt645drv/sockbuf_{windows,unix}.go`）问「缓冲里有没有待读字节」，没有就立即返回，有残留才进入原来的定时读循环——**Drain 的语义完全不变**，已到达的残留照样被清掉。串口拿不到裸 fd（`serial.Port` 只有 `io.ReadWriteCloser`），改用记账：`dlt645Transport` 接口新增 `MarkDirty()`，只在写失败 / 读超时 / I/O 错误 / 跳过噪声帧时置位，干净轮次整段跳过 Drain（串口空口读一次要空等 `serialReadTimeout` 20ms）。迟到的应答只可能在某轮没按时收到应答时才在途，而那正是置位的轮次；同仓库 ModBus.RTU（goburrow/modbus）从不 pre-drain，本策略比它更保守。
  实测：单帧 1,537,655 ns → **21,061 ns（73 倍）**；50 设备 × 5000 点 @1000ms 从 1.6% 掉点 → **0.0%**（约 30 万记录/秒）。**出厂默认值同步调整**：`maxDIsPerRead` 1 → **12（协议上限）**，`interFrameDelayMs` 按传输层分叉 —— TCP **0**（30ms 是 RS-485 收发器换向预留，透传链路由串口服务器 / DTU 自己处理）、串口**保持 30**（`DefaultDLT645Config` 本就按传输层分叉 `PreambleBytes`，此处照此扩展）。旧默认值「一个数据标识一个请求」的顾虑（异常应答不回显失败项）已有兜底：批量请求遇异常应答会自动降级为逐个重读（`readGroupPerDI`），代价只是失败时多发一轮。**默认值只在 `protocol_json` 缺该键时生效，不会追溯改动已存库的设备**（表单历来都写显式值）。
  验收：新增 `driversrc/dlt645/dlt645drv/perf_bench_test.go`（`BenchmarkReadTCP`，直接打印 `ns/frame` 与 `frames/s`，是本次定位瓶颈的仪器，留作回归资产）与 `drain_test.go`（串口干净轮次不读 / TCP 空缓冲不等待 / 有残留仍清干净 / 探测如实报数）。压测报告 `backend/cmd/loadtest/README.md` 的 DLT645 专节已按新默认重测并重写。
  **DL/T 645 performance fix and new factory defaults: per-frame cost cut to 1/73, and the default configuration goes from "100% drop from the 2000-point tier up" to usable as shipped.** The load-test report attributed this protocol's problems to two tunable parameters (`maxDIsPerRead` defaulting to 1 = one frame per point, and `interFrameDelayMs` to 30ms), but even tuned to the report's optimum it fell short (1.6% drop at 50 devices × 5000 points @1s, where other protocols in the same matrix showed 0%). Isolating the driver from the collector with a benchmark found the real cause: **`t.Drain()` at the head of every `exchange()` accounted for 98.7% of the per-frame cost** (1,537,655 ns/frame). It clears residual bytes by "set a 1ms deadline, then read", but on a clean link the receive buffer is empty, so that read necessarily blocks until the deadline — **1ms of dead time per frame** — and frame count grows linearly with point count (frames = ⌈points / `maxDIsPerRead`⌉), making it the floor on a device's poll period.
  The fix asks first, with a zero-cost probe (Windows `WSAIoctl(FIONREAD)` / unix `ioctl(TIOCINQ)`, measured at 676ns, added in `driversrc/dlt645/dlt645drv/sockbuf_{windows,unix}.go`), whether anything is pending; if not it returns immediately, and only enters the original timed-read loop when there is residue — **Drain's semantics are unchanged**, already-arrived residue is still discarded. Serial has no raw fd to probe (`serial.Port` is only `io.ReadWriteCloser`), so it uses bookkeeping instead: a new `MarkDirty()` on the `dlt645Transport` interface, set only on write failure / read timeout / I/O error / skipped noise frame, lets clean rounds skip Drain entirely (an empty serial read blocks for `serialReadTimeout`, 20ms). A late reply can only be in flight if some round failed to get its reply in time — exactly the rounds that set the flag; this repo's ModBus.RTU (goburrow/modbus) never pre-drains at all, so this strategy is more conservative.
  Measured: 1,537,655 ns → **21,061 ns per frame (73×)**; 50 devices × 5000 points @1000ms went from 1.6% drop to **0.0%** (~300k records/s). **Factory defaults changed accordingly**: `maxDIsPerRead` 1 → **12 (the protocol ceiling)**, and `interFrameDelayMs` now forks by transport — **0 on TCP** (the 30ms is an RS-485 transceiver-turnaround allowance, handled by the serial server / DTU on a pass-through link) and **30 on serial** (`DefaultDLT645Config` already forked `PreambleBytes` by transport; this extends the same pattern). The concern behind the old default (a 645 abnormal response does not echo which data identifier failed) now has a fallback: a batched request that gets an abnormal response degrades to per-identifier reads (`readGroupPerDI`), costing one extra round on failure. **Defaults apply only when the key is absent from `protocol_json`, so already-stored devices are not retroactively changed** (the forms have always written explicit values).
  Acceptance: new `driversrc/dlt645/dlt645drv/perf_bench_test.go` (`BenchmarkReadTCP`, which prints `ns/frame` and `frames/s` directly — the instrument that found this, kept as a regression asset) and `drain_test.go` (serial skips clean rounds / TCP does not wait on an empty buffer / residue is still cleared / the probe reports pending bytes faithfully). The DLT645 section of `backend/cmd/loadtest/README.md` has been re-measured against the new defaults and rewritten.
- **破坏性变更（非滚动升级）：全部协议驱动搬为进程外插件**。`backend/driver/` 只剩契约与基建（`driver.go` / `types.go` / `typeRegistry.go` / `dataTypeMap.go` / `rangeSig.go`），插件开发套件移到同级的 `backend/driversdk/`，主二进制不再包含任何协议实现；7 个插件源码位于 `backend/driversrc/`（`modbus` / `mitsubishi` / `s7` / `opcua` / `rockwellcip` / `omroncip` / `fins`），各编译为 `iot-driver-<目录名>`，放入可执行文件同级的 `plugins/` 目录即被加载。**升级必须成对替换主二进制与 `plugins/` 目录**——旧网关 + 新插件、新网关 + 旧插件两种混搭都会让对应协议不可用；回滚同样成对换回即可（数据库未改动，`migrations/` 未新增或修改）。12 个协议名与类型 scope 沿用原值，既有设备配置、`iot_protocol` 行与前端表单**无需迁移**。
  **Breaking change (not a rolling upgrade): every protocol driver moved out of process.** `backend/driver/` now holds only the contract and infrastructure (`driver.go` / `types.go` / `typeRegistry.go` / `dataTypeMap.go` / `rangeSig.go`), the plugin SDK moved to the sibling `backend/driversdk/`, and the binary contains no protocol implementation; the 7 plugin sources live in `backend/driversrc/` (`modbus` / `mitsubishi` / `s7` / `opcua` / `rockwellcip` / `omroncip` / `fins`), each building to `iot-driver-<dir>` and loaded from the `plugins/` directory beside the executable. **Upgrades must replace the binary and `plugins/` as a pair** — old gateway + new plugins and new gateway + old plugins both leave the corresponding protocols unusable; rollback is symmetric (no database change, `migrations/` untouched). The 12 protocol names and type scopes keep their previous values, so existing device configs, `iot_protocol` rows and frontend forms **need no migration**.
- 插件相关目录改为**按「种类 + 角色」命名**，并把传输层从驱动套件里拆出来：新增 `backend/pluginwire/`（帧编解码 / 方法名 / `RemoteError`，**只依赖标准库**，与插件种类无关），`pluginhost/` 只依赖它、不再依赖驱动套件；识别「驱动」的代码收敛到同包的 `pluginhost/adapter_driver.go`（连同原有的 `provision.go` / `remote.go`）。**纯结构调整**：产物名（`iot-driver-*`）、`plugin.dir` / `glob` 配置、`iot_protocol` 表与 `device.protocol_id` 全部不变，无需迁移。目的是为将来把推送通道也做成进程外插件留出位置（套件 `pushsdk/` + 源码 `pushsrc/` + 适配器 `pluginhost/adapter_push.go`），**避免届时复制 `process.go` / `upgrade.go` 另起一个宿主**。
  Plugin directories are now named by **kind + role**, and the wire layer is split out of the driver SDK: new `backend/pluginwire/` (frame codec / method names / `RemoteError`, **stdlib-only**, kind-agnostic), which `pluginhost/` now depends on instead of the driver SDK; everything that knows about "drivers" is confined to `pluginhost/adapter_driver.go` (alongside the pre-existing `provision.go` / `remote.go`). **Pure restructuring**: artifact names (`iot-driver-*`), the `plugin.dir` / `glob` config, the `iot_protocol` table and `device.protocol_id` are all unchanged — no migration. The point is to leave room for making push channels out-of-process later (SDK `pushsdk/` + sources `pushsrc/` + adapter `pluginhost/adapter_push.go`) **without duplicating `process.go` / `upgrade.go` into a second host**.
- `plugin.enabled` 出厂值改为 `true`：协议全部来自插件，关掉它网关就不支持任何协议。加载插件等于**以网关自身的 OS 权限执行 `plugins/` 下的程序**——插件是可信代码而非沙箱内容，`plugins/` 目录因此是一条**可执行代码的信任边界**：Unix 下网关拒绝世界可写目录（除非显式 `plugin.allowInsecureDir: true`），Windows 的权限位无意义、只记警告，需部署方自行保证仅管理员可写。详见 [SECURITY.md](SECURITY.md)。
  `plugin.enabled` now ships as `true`: all protocols come from plugins, so disabling it leaves the gateway with no protocol support. Loading plugins means **executing the programs under `plugins/` with the gateway's own OS privileges** — plugins are trusted code, not sandboxed — which makes the `plugins/` directory a **trust boundary for executable code**: on Unix the gateway refuses world-writable directories (unless `plugin.allowInsecureDir: true`), while Windows permission bits are meaningless and only produce a warning, so keeping it administrator-writable is the deployer's responsibility. See [SECURITY.md](SECURITY.md).
- 主二进制不再链接 `goburrow/modbus`、`robinson/gos7`、`gopcua/opcua`、`iceisfun/goindustrial`、`goburrow/serial` 等协议库——它们现在只被 `backend/driversrc/` 下的插件链接，**协议库随插件分发**，主二进制依赖面显著收窄。
  The main binary no longer links protocol libraries such as `goburrow/modbus`, `robinson/gos7`, `gopcua/opcua`, `iceisfun/goindustrial` and `goburrow/serial` — they are linked only by the plugins under `backend/driversrc/`. **Protocol libraries now ship with the plugins**, sharply shrinking the binary's dependency surface.
- `docker-compose.yml` 中 `./plugins:/app/plugins:ro` 绑定挂载改为注释：该挂载会**遮蔽镜像内已构建的插件**（宿主目录为空即无任何协议）。确需运行期挂载时，必须先把发行包 `plugins/` 的内容拷进宿主目录。
  The `./plugins:/app/plugins:ro` bind mount in `docker-compose.yml` is now commented out: it would **mask the plugins built into the image** (an empty host directory means no protocols). For runtime mounting, copy the release archive's `plugins/` contents into the host directory first.
- `backend/specs/capacity-testing.md` / `.en.md`：修正失效的驱动源码路径（`driver/rockwell/cip/range.go` → `backend/driversrc/rockwellcip/rockwellcipdrv/range.go`），并声明其历史实测数据采集于进程内驱动时期——插件版每次读写多一次 RPC 往返，**绝对吞吐基线不再可比**。
  `backend/specs/capacity-testing.md` / `.en.md`: stale driver source paths corrected (`driver/rockwell/cip/range.go` → `backend/driversrc/rockwellcip/rockwellcipdrv/range.go`), and the document now states that its measurements were taken with in-process drivers — the plugin build adds one RPC round-trip per read/write, so **the absolute throughput baselines are no longer comparable**.
- `omroncipdrv/config.go` 中 `maxTagsPerRequest` 的注释订正：原注释写「0/负值回退默认关闭」，但 `DefaultCIPConfig` 实际把默认值设为 **64（批量读默认开启）**。**驱动行为未改动**，只把注释改成与实际一致（压测实测 5000 点 = 80 帧，印证默认值是 64）。若本意是「默认逐标签单读」，需另行把 `DefaultCIPConfig` 的值改回 0——那会变更出厂行为，本次未做。
  Corrected the `maxTagsPerRequest` comment in `omroncipdrv/config.go`: it claimed "0/negative falls back to the default of OFF", but `DefaultCIPConfig` actually defaults it to **64 (batch reads ON)**. **Driver behaviour is unchanged** — only the comment was made accurate (the benchmark measured 80 frames for 5000 points, confirming the default is 64). If "one tag per round-trip by default" was the intent, `DefaultCIPConfig` must be changed to 0 separately, which alters out-of-box behaviour and was deliberately not done here.
- `backend/specs/push-payload.md` / `.en.md`：示例中的不存在的协议名 `Siemens.Net.S7` 更正为真实注册名 `Siemens.S7`。
  `backend/specs/push-payload.md` / `.en.md`: the nonexistent protocol name `Siemens.Net.S7` in an example corrected to the real registered name `Siemens.S7`.
- JWT 签名密钥不再使用内置固定值：未配置时每次启动随机生成临时密钥；生产环境建议通过 `IOT_GATEWAY_JWT_SECRET` 环境变量或 `jwt.secret` 配置固定密钥。
  The JWT signing secret no longer ships with a built-in fixed value: an ephemeral random secret is generated per start when unset; set `IOT_GATEWAY_JWT_SECRET` or `jwt.secret` in production to keep sessions across restarts.
- 推送通道的通用逻辑收敛到 `push` 包（新增 [push/outbox.go](backend/push/outbox.go)、[push/drain.go](backend/push/drain.go)、[push/writer.go](backend/push/writer.go)）：mqtt / tdengine / influxdb 此前各自复制了一份「有界出站队列 + 落盘 + 补发唤醒 + 状态统计」，含三份逐字相同的容量常量、补发循环与攒批写循环；现统一为**一个共享骨架（`Outbox`）+ 通用循环（`AggregateWriter` 攒批下发 / `DrainLoop` 补发 / `ReconnectLoop` 重连），各通道只实现「负载构造与下发」**。聚合类通道的补发算法（分组/切分/窄化/删除）收敛为 `GroupedDrainer`，实时写入与补发共用同一个 `push.Aggregator` 负载构造器。**对外行为与配置不变**：`push.Channel` 接口、`push_channel` / `push_outbox` 表结构、前端表单与开放接口均未改动。
  顺带修掉两处**停服丢数据窗口**：worker 组停服前会把 outbox 中写失败的批次转投缓存，而落盘协程在 `quit` 后立即收工返回，这些批次会留在内存通道里随进程退出丢失。现在收尾顺序是 `Close`（关 quit）→ 等 worker 组退出 → `Wait`（落盘协程排空在途批次后才收工），mqtt 与 tdengine 此前有此问题（influxdb 已单独修过）。另外 mqtt 的补发循环此前在队头发布失败且连接仍在时会**紧循环重试**（空转刷 CPU），现与另外两个通道一致地在失败后等待补发事件或兜底间隔再重试。
  Push-channel common logic is consolidated into the `push` package (new [push/outbox.go](backend/push/outbox.go), [push/drain.go](backend/push/drain.go), [push/writer.go](backend/push/writer.go)): mqtt / tdengine / influxdb each carried a copy of the same "bounded outbound queue + spooling + drain wakeup + status counters", including three verbatim-identical sets of capacity constants, drain loops and batched write loops. They now share **one skeleton (`Outbox`) plus generic loops (`AggregateWriter` for batched delivery / `DrainLoop` for replay / `ReconnectLoop`), with each channel implementing only payload construction and delivery**. The aggregated channels' replay algorithm (grouping / splitting / narrowing / deletion) collapses into a single `GroupedDrainer`, and real-time writes and replay now share one `push.Aggregator` payload builder. **External behaviour and configuration are unchanged**: the `push.Channel` interface, the `push_channel` / `push_outbox` schemas, the frontend forms and the Open API are all untouched.
  This also closes two **data-loss windows on shutdown**: on the way down, a channel's workers offload batches that failed to deliver into the spool, but the spool writer returned as soon as `quit` closed, leaving those batches in an in-memory channel to die with the process. The teardown order is now `Close` (closes quit) → wait for the worker group → `Wait` (the spool writer only exits after draining in-flight batches), which fixes mqtt and tdengine (influxdb had been fixed separately). Separately, mqtt's drain loop used to **retry in a tight loop** (burning CPU) when the head batch failed while still connected; it now waits for a drain event or the backstop interval like the other two channels.

- **破坏性变更（管理接口）：移除「新增协议」与「删除协议」，改为「恢复默认表单」**。协议行全部由插件供给（`iot_protocol` 由 `pluginhost` 在插件加载时按 `driversdk.Meta.Protocols` 自动维护），两条路径因此在插件模型下都是坏的：**手工建的行没有任何驱动与之对应**——设备选了它，采集时 `driver.Create` 失败并**静默跳过该设备**（前端只在设备列表里显示一个空协议名），可它却会出现在设备的协议选择器里；**删除则是无效操作**——`provisionProtocols` 只在插件加载/热升级时按名字补行，删掉的行在网关下次重启后会被原样插回，而用户重新上传同一个插件文件又会被 `InstallPlugin` 的同内容短路判为"已跳过写入"，看着成功实则什么都没变。两个入口一并移除（路由 `POST /protocol/createProtocol`、`GET /protocol/deleteProtocol/:id`，及对应的 controller / service / `CreateProtocolDTO`）。
  取而代之的是 **`POST /protocol/resetProtocolForm/:id`**：把 `iot_protocol.form_json` 换回插件当前声明的那一份。这正是运维真正需要的动作（表单改坏了、或插件更新了表单要采纳），且**不触碰 `description`**——它同样是运维数据，`provision` 也只在它为空时才补。`pluginhost.Manager` 为此新增只读入口 `PluginProtocolForm(name)`：返回副本（改写不会污染已加载插件的 meta），无插件提供该协议时返回 `ErrProtocolNotProvisioned`，插件未声明表单时返回 `(nil, nil)`——两者对应两个新错误码 `50004` / `50005`，好让用户知道该去找什么。新增的 `service.ProtocolFormSource` 接口与 `pluginhost.Reloader` 同理，是为了让 service 的测试不必拉起真实插件子进程。
- **协议名改为不可修改**：`UpdateProtocolDTO.name` 只剩"校验它没被改动"这一个用途，一改即返回新错误码 `50003`（前端编辑弹窗的名称输入框相应改为只读）。协议名是 `iot_protocol.name` 与 `driver.Register` 名的唯一纽带，也是 `device.protocol_id` 的解析目标；改名后插件下次加载时 `provision` 按名字找不到这一行、会再插一条正确的，改名后的旧行沦为孤儿，而引用它的设备全部静默停采。选择硬拒绝而非静默忽略——静默忽略会让调用方以为改成功了。
- **移除协议行的 status（启用/禁用）**：该字段只写不读，`collector` 加载协议时是无过滤的 `db.Find(&protocols)`，设备的协议选择器也不看它，所以"禁用协议"从未生效过——留着只会让人以为它有用，实际却是一条隐蔽的停采路径。`iot_protocol.status` 列仍留在库中（迁移 004 建的），Go 侧不再映射它（删除该列需重建 SQLite 表，不值得）；要停采请禁用设备或移走插件文件，两者都已覆盖。
  **Breaking change (admin API): "add protocol" and "delete protocol" are gone, replaced by "restore default form".** Protocol rows are supplied entirely by plugins (`iot_protocol` is maintained by `pluginhost` from `driversdk.Meta.Protocols` on plugin load), which makes both paths broken under that model. **A hand-created row has no driver behind it** — a device that selects it fails `driver.Create` at collection time and is **silently skipped** (the UI just shows an empty protocol name), yet the row still appears in the device protocol picker. **Deletion is a no-op** — `provisionProtocols` re-inserts a missing row by name on the next plugin load, so a deleted row comes back on the next gateway restart, while re-uploading the identical plugin file is short-circuited by `InstallPlugin`'s same-content check and reported as "skipped" — success on screen, nothing actually changed. Both entry points are removed (routes `POST /protocol/createProtocol` and `GET /protocol/deleteProtocol/:id`, plus their controller / service code and `CreateProtocolDTO`).
  They are replaced by **`POST /protocol/resetProtocolForm/:id`**, which swaps `iot_protocol.form_json` back to the form the plugin currently declares. That is the action operators actually need (a form they broke, or a plugin that shipped a new form) and it **leaves `description` alone** — that is operator data too, and `provision` likewise only fills it when empty. `pluginhost.Manager` gained a read-only `PluginProtocolForm(name)`: it returns a copy (mutating it cannot pollute the loaded plugin's meta), `ErrProtocolNotProvisioned` when no plugin provides the protocol, and `(nil, nil)` when the plugin declares no form — two new error codes `50004` / `50005` so the user can tell which it is. The new `service.ProtocolFormSource` interface exists for the same reason as `pluginhost.Reloader`: so service tests need not spawn a real plugin subprocess.
- **The protocol name is now immutable**: `UpdateProtocolDTO.name` survives only to verify it was not changed, and changing it returns the new error code `50003` (the edit dialog's name field is now read-only). The name is the sole link between `iot_protocol.name` and the `driver.Register` name, and the resolution target of `device.protocol_id`; after a rename, `provision` finds no row under that name on the next plugin load and inserts a correct one, leaving the renamed row an orphan while every device referencing it stops collecting silently. It hard-rejects rather than silently ignoring, because silent ignoring lets the caller believe the rename went through.
- **The protocol row's `status` (enable/disable) is removed**: the field was write-only — `collector` loads protocols with an unfiltered `db.Find(&protocols)` and the device protocol picker ignores it, so "disabled protocol" never took effect. Keeping it only suggested it did something while actually being a hidden way to stop collection. The `iot_protocol.status` column remains in the database (created by migration 004) but is no longer mapped in Go (dropping it would require rebuilding the SQLite table, which is not worth it); to stop collection, disable the device or move the plugin file away — both are already covered.

### Fixed

- **SQLite 启动写探针：确认库真的可读可写，而不是"能打开"就算数**。此前「可读不可写」的库**能启动成功** —— SQLite 是懒打开的，迁移在已有库上会全部跳过、admin 播种也只在用户表为空时才写，于是网关照常起来，直到运行期某次写入才报 `attempt to write a readonly database`，对外表现为登录失败、outbox 落盘失败等一串与根因对不上的错误（Windows 服务账号不是 LocalSystem、容器里数据目录以只读方式挂载都长这样）。现在 `InitDB` 在迁移前建一张 `iot_gateway_rw_probe` 表、插入、回读、删除，任一步失败即 Fatal 并打印**绝对路径**与排查提示；目录可写性一并验证（WAL 的 `-wal` / `-shm` 是运行时才创建的伴生文件，目录不可写则库整体不可写，仅靠文件模式位判断会漏掉这一整类）。同时 `PRAGMA journal_mode=WAL` 由静默改为回读确认，切不过去时记一条带路径的 WARN；`os.MkdirAll` 失败由 WARN 升为 Fatal（随后的 `gorm.Open` 必然也失败，就地报错才能带上路径）。
  **SQLite startup write probe: prove the database is actually readable and writable rather than merely openable.** A read-only database used to **start successfully** — SQLite opens lazily, migrations are all skipped on an existing database, and admin seeding only writes when the user table is empty — so the gateway came up normally and only failed at some later write with `attempt to write a readonly database`, surfacing as failed logins and dead outbox spooling rather than anything pointing at the cause (a Windows service account that is not LocalSystem, or a container volume mounted read-only, both look like this). `InitDB` now creates an `iot_gateway_rw_probe` table, inserts, reads back and drops it before running migrations; any failure is fatal and prints the **absolute path** plus what to check. Directory writability is covered by the same probe (the WAL `-wal` / `-shm` sidecars are created at runtime, so a read-only directory makes the whole database unwritable — a check that file mode bits alone would miss entirely). `PRAGMA journal_mode=WAL` now confirms the resulting mode instead of ignoring it, warning with the path when it did not take effect, and a failed `os.MkdirAll` is fatal instead of a warning (the subsequent `gorm.Open` would fail anyway; erroring here is what gets the path into the log).
- 启动日志中的 SQLite 路径改为**绝对路径**：Windows 服务由 SCM 拉起、工作目录是 System32，相对路径报出来对不上运维在磁盘上看到的东西。
  The SQLite path in the startup log is now **absolute**: a Windows service is launched by the SCM with System32 as its working directory, so a relative path in the log does not match what operators see on disk.

  **Quality cause dimension added to collection results: "address does not exist" is now distinguishable from "this round's comms failed"**. `ReadResult.Quality` used to be only `192=good / 0=bad` (`128=uncertain` from ABB), and `0` collapsed two **opposite** failures into one value: an **address-level** failure (the address itself is bad/absent, the device is fine, and the bisecting degrade path already confirmed it by narrowing to a single point — it **never self-recovers**) and a **comms-level** one (the whole range was refused with a recoverable status — slave busy, node busy, gateway error — retried next round). The previous round's bisecting degrade (the entries above) **already computed that distinction internally** (`isAddressException` / `isAddressNotFoundErr` / `isAddressEndCode` / `isAddressStatusError`) but threw it away, leaving only a `0`. This adds `driver.ReadResult.QualityCause` (`driver.QualityCauseAddress` = `"address"` / `QualityCauseComms` = `"comms"` / `QualityCauseParse` = `"parse"`; **invariant: always empty when `Quality==192`**). The boundaries are documented on the const block: `comms` **does not cover link timeouts** — a transport timeout/EOF makes the whole `Read` return an error and produces no `ReadResult` at all; it means specifically "the device answered in-band with a recoverable rejection". **All nine protocols are covered.** The first five (Modbus / S7 / FINS / Mitsubishi / Rockwell) use the verdicts their own **bisecting degrade** already computed; the other four (OPC UA / Omron.CIP / DLT645 / ABB) have no bisecting degrade, but **each one's read path already has a fork between "permanent config error" and "transient failure"** and simply discarded the verdict — so this classifies, it does not change behaviour: OPC UA maps a local `parseError` and a browse-path resolution failure (`BadNoMatch`, etc.) to address-level, classifies the per-node `Status` by semantics (`BadNodeIDUnknown` / `BadNodeIDInvalid` / `BadNotFound` / `BadNoMatch` / `BadAttributeIDInvalid` → address, `BadTimeout` / `BadCommunicationError` / `BadServerNotConnected` / `BadConnectionClosed` → comms, other Bad codes and Uncertain stay empty), and marks a wholly rejected sub-batch (`BadTooManyOperations`, where the server answered for no node at all so there is no way to tell which point is at fault) comms for the whole range; Omron.CIP maps general status 0x04/0x05/0x16 (path segment error / path destination unknown / object does not exist) to address and every other general status (resource unavailable, partial transfer…) to comms (a new `IsAddressStatusError` in `cipcore`, word-for-word the same criterion as rockwellcip's — the two plugins' `cipcore` copies were always separate, per the "plugins must not import each other" rule), an unsupported local type code to address, and a decode failure to parse; DLT645 maps an address-parse failure (data identifier not in the dictionary / malformed) and abnormal response code 0x02 "no requested data" to address, and a DI echo mismatch / truncated data / decode failure / an unsupported follow-up frame to parse; ABB maps an address-parse failure, a service-level 4xx (the controller saying the thing is not there — deliberately the **same** status range as its negative-cache test), a missing field in the response, and a negative-cache hit to address, and a service-level 5xx to comms. **Two things stay deliberately empty and one is deliberately left unattributed**: DLT645's abnormal code 0x01 "other error" is not attributed (the driver's own comment states it carries no locating information — wrong meter address, unimplemented data identifier and a non-reading meter all report 01, so guessing one cause is worse than none); unrecognised status/error codes in OPC UA and DLT645 stay empty; and in ABB the points held back by the fallback budget, like the ones OPC UA hands to the single-point path because the list did not cover them, stay empty (that is a deferral, not a device verdict). The cause is written **at the branch where the classification verdict is already made**, never in the prefill skeleton — none of the three is a pure function of the error, it is a function of *which branch the code is on*. **Points deferred because the degrade budget ran out deliberately stay empty**: that is a deferral, not a device verdict, and the tests pin it (the only thing that catches a naive "stamp the whole prefill skeleton with `comms`" implementation). **Cross-round persistence is what makes or breaks this**: the four drivers with a plan cache remove a confirmed-bad address from the plan, so the classification code runs only in the confirming round — hence the cause is cached alongside the degraded plan (a `bad` map in `storeDegradedPlan`, replayed into the next round's prefill). Without it, "this address does not exist" would be visible in only 1/N rounds, and a point-level alarm keyed on N consecutive rounds would never fire. Rockwell and Omron.CIP are unaffected (the former's `degradeChunk` is deliberately not cached and re-confirms every round; the latter has no point-level negative cache and re-judges every round). ABB's and DLT645's own cross-round caches (the `hintMissing` negative cache and `planEntry.err` riding along in the cached plan) are themselves the carrier of "this point does not exist", and the cause is replayed through them each round. **One asymmetry was fixed along the way**: Rockwell scalar tags went through `markTagZero` with no classification at all; they now use `isAddressStatusError` to pick `address` vs `comms` (a scalar tag group is keyed by one full tag name, so a general-status rejection means "this tag does not exist"). The path is end-to-end: `driver.ReadResult` → plugin wire → `collector.CollectedRecord` → `realtime.Point` → MQTT / TDengine / InfluxDB / realtime page. **MQTT and InfluxDB are byte-for-byte compatible for good points** (`omitempty` and "only emit when non-empty" respectively), so existing subscribers and queries need no changes; **TDengine cannot be**, because its INSERT is positional `VALUES(...)`, so every row changes.
  ⚠️ **Two things must ship together or they are hard failures**: (1) **plugin `APIVersion` 2 → 3** (the payload is positional binary and the decoder enforces exact byte consumption via `Done()`, so the two versions cannot read each other) — **every plugin must be rebuilt after upgrading the gateway**, otherwise the handshake rejects it with "APIVersion mismatch"; note the frame magic stays `IGP2`, only the payload changed. (2) **The TDengine super table on existing deployments needs a manual column add**: the schema statement is `CREATE STABLE IF NOT EXISTS`, which skips entirely when the table exists, while the positional INSERT keeps failing on a column-count mismatch (**not** a silent misalignment). Run this once before upgrading (fresh installs need nothing — the table is created with the column):
  `ALTER STABLE {db}.{stable} ADD COLUMN quality_cause NCHAR(16);`
  `ensureSchemaSQL` **deliberately creates and never alters**: it runs on startup and after every reconnect, so an unconditional `ALTER` erroring on an existing column would fail `ensureSchema` and the channel would never come up (a hard outage) — that reasoning is in the function comment. The realtime page no longer prints a bare `0/192`: good points get a green "Good" tag, `quality==0` gets a red tag showing the **cause** (`Bad address` / `Comm failed` / `Decode failed`) instead of the raw number — a misconfigured address needs a config change while a transient comms blip needs waiting a round, and the remedies differ; when the cause is absent — which can mean "this branch cannot attribute it", e.g. an unrecognised device status code or a budget-deferred point — it falls back to the raw code rather than disguising "unknown" as a specific reason, and other non-192 values (ABB's `128`) render as before. Regressions: all nine drivers are covered — the first five extended their `degrade_test.go` assertions with causes (`address` / `comms` / `""` at the budget boundary, plus the cross-round guard that **every** bad point carries `address` once the loop converges), and Rockwell gained `TestReadScalarTagStatusCause` covering the previously unexercised scalar-tag branch; the other four gained cause assertions in their own read tests (a shared `assertCause` helper that also enforces the `Quality==192 ⇒ cause empty` invariant) plus a **criterion-table** test pinning the code-to-cause mapping itself (`TestDriverReadCauseClassification` / `TestStatusCause` / `TestAbnormalCodeCause` / `TestServiceErrorCause`), and ABB's `TestReadNegativeCache` was widened to assert across three rounds — the two rounds served entirely from the negative cache with no request issued must **also** carry the cause, which is the only guard on the cross-round replay. Every new assertion was falsified by flipping the criterion to the other bucket and confirming the test turns red, so no assertion is vacuously true. `driversdk/binary_test.go`'s `sampleReply` now deliberately carries non-empty causes (otherwise both sides of the round-trip comparison are zero values and a forgotten field in the encoder would go unnoticed) with a new `TestBinaryPreservesQualityCause` that also pins "an old-format payload with the cause bytes chopped off must fail loudly". On the push side, `TestMarshalBatchQualityCause` / `TestBuildLineQualityCause` assert on **raw bytes** that good points omit the field, and TDengine's two pinned tests (`TestBuildInsertSQL*` / `TestEnsureSchemaSQL`) were updated with the column order.


### Added

- **新增「点位报警」：某个采集点位本身坏掉时，现在会单独报出来并推给值班群**。此前报警只有设备断联与推送通道断联两种，而一个点位采不到值（地址写错、数据类型不对）时**设备是好好的** —— 设备在线、轮询一轮不落、报警页面一片安静，只有翻实时页才看得出那个测点的值一直是空的。现在第三类目标 `target_type='point'` 补上了这一维：连续 3 轮确认后落一条 `alarm_type='quality'` 的报警，文案是「点位 1#炉.温度 采集质量异常（地址无效）」，恢复时写一条「点位 1#炉.温度 恢复采集」。
  **这一维完全建立在上一版已打通的质量成因 `QualityCause` 之上，因此不需要动任何驱动、也不需要重编插件**（`APIVersion` 不变，黄金基线不动）：采集侧只把每轮读到的 `quality`/`cause` 原样转发，判定全在报警这一侧。
  **只认能归咎于点位自身的成因**，这是本功能唯一需要小心的地方。`address`（地址不存在，驱动已单独确认过，永不自我恢复）与 `parse`（设备答了但本地解码失败）计入失败；其余一律**中性** —— 既不报成功也不报失败，状态机原地保持：
  - `comms`（整段被设备以可恢复状态拒绝）按定义是瞬时的，且**成组出现**：整段被拒时该段每个点位一起拿到 comms，计入失败会让一次区间拒绝同时点亮上百个点位报警；
  - `""`（认不出来的设备状态码，以及**预算耗尽被延迟**的点位）—— **这一条最容易被写错**：驱动契约保证 `addrs` 里每个点位都恰好有一条结果（`Quality=0` 的预填骨架），而预算耗尽被延迟的点位既不解析也不摘除，于是恒为 `quality=0` + `cause=""`，且每轮都在同一处被延迟。按最直觉的「`quality != 192` 就报」写，这些点位会**恒定**挂着一条假报警；
  - `128`（ABB 的"不确定"：信号被勾了仿真，值可用但标注质量）不是故障。
  中性还有一处必须守住：它**不能顺手恢复**已有报警。一个已确认地址不存在的点位，这一轮只是因为整段被拒而拿不到值，没有任何证据说明那个地址回来了 —— 所以实现是"不调用状态机"而不是"报成功"。两条边界各有专门的回归测试（`alarm/point_test.go` 的 `TestPointAlarmIgnoresNonAttributableCauses` 与 `TestPointAlarmNeutralDoesNotRecover`），并各自用反向改动验证过会变红。
  **「与设备离线去重」是免费得到的**：设备读失败时 `driver.Read` 直接返 error、一条记录都不产生，点位压根不会被上报，状态机原地冻结 —— 既不新报也不误恢复，不需要任何额外代码。另有一条**必须一起做**的清理：设备停用/删除时，`ClearDeviceAlarm` 现在一条语句清掉**设备自身的断联报警 + 该设备名下全部点位的质量报警**。不做这一步，采集停掉之后再没有信号来恢复那些点位报警，它们会永久挂在"未恢复"上。点位报警的 `target_id` 是点位自身、看不回设备，故靠新增的 `alarm.device_id` 列反查（**建在基础迁移 `007_alarm.sql` 里，随网关启动自动执行，无需手工 ALTER**）；单删点位也走 `ClearPointAlarm`。
  状态机**没有复制第二份**：`alarm.Tracker`（边沿判定 / 去抖 / 节流 / 落库 / 通知）对三类目标一视同仁，差异收敛到新的 `alarm.Spec`（`DeviceSpec` / `ChannelSpec` / `PointSpec`：落库类型 + 文案措辞）。`notify.BuildTestEvent` 的「测试发送」预览也读同一份 Spec —— 它此前把文案硬编码在 `notify` 里、与 `Tracker` 各写一份，现在两边不可能说法不一致。Webhook 通知复用既有 `notify.Dispatcher`（钉钉/企微/飞书/自定义），只在边沿发消息；断联专用的 `GET /alarm/listActive` **只取 `alarm_type='offline'`**，故点位质量报警不会混进"离线目标列表"，`DeviceVO.online` 也不受影响。前端复用同一个报警页组件，新增 `alarm/point` 路由与菜单项。
  验收：`alarm/point_test.go`（成因取舍 / 中性不恢复 / 恢复文案 / 同批隔离 / 不重复报警）、`collector/pointreport_test.go`（点位名优先取中文说明；**每条记录都原样转发** —— 采集侧若替报警侧过滤，中性语义会静默失效）、`service/alarmService_test.go`（清设备连带清其点位报警且不误伤其它设备、清通道不波及点位、点位报警不进离线列表）、`notify/formatter_test.go`（五组文案逐项钉住）。全量 `go test -p 1 ./...` 通过。
  **Point-level alarms: a broken measurement point is now reported on its own and pushed to the on-call group.** Alarms previously covered only device and push-channel disconnection, but a point that cannot be read (wrong address, wrong data type) leaves **the device perfectly healthy** — it stays online, polls on schedule, and the alarm page stays silent; only the realtime page shows the value has been empty all along. A third target kind, `target_type='point'`, closes that gap: after 3 consecutive confirmations a `alarm_type='quality'` row is written with content `点位 1#炉.温度 采集质量异常（地址无效）`, and recovery writes `点位 1#炉.温度 恢复采集`.
  **The whole feature is built on the `QualityCause` dimension shipped in the previous release, so no driver changes and no plugin rebuilds are needed** (`APIVersion` unchanged, golden baselines untouched): the collector forwards each round's `quality`/`cause` verbatim and the decision lives entirely on the alarm side.
  **Only causes attributable to the point itself count as failures**, and that is the one thing here worth being careful about. `address` (the address does not exist; the driver confirmed it individually, so it never self-recovers) and `parse` (the device answered but local decoding failed) count; everything else is **neutral** — neither success nor failure, leaving the state machine untouched:
  - `comms` (the whole range was refused with a recoverable status) is transient by definition and arrives **in groups**: when a range is refused, every point in it gets `comms` at once, so counting it would light up hundreds of point alarms from a single refusal;
  - `""` (an unrecognised device status code, and points **deferred because the degrade budget ran out**) — **this is the easiest one to get wrong**: the driver contract guarantees exactly one result per address (a `Quality=0` prefill skeleton), and a budget-deferred point is neither parsed nor removed from the plan, so it is permanently `quality=0` + `cause=""`, deferred at the same place every round. The intuitive "`quality != 192` means failure" implementation leaves these points with a **permanent** false alarm;
  - `128` (ABB "uncertain": the signal is flagged simulated, the value is usable but annotated) is not a fault.
  Neutrality has one more rule to respect: it must **not** opportunistically recover an existing alarm. A point already confirmed to have a missing address merely failed to yield a value this round because the range was refused — nothing there is evidence the address came back — so the implementation is "do not call the state machine", not "report success". Each boundary has a dedicated regression test (`TestPointAlarmIgnoresNonAttributableCauses` and `TestPointAlarmNeutralDoesNotRecover` in `alarm/point_test.go`), each falsified by mutating the policy to confirm it goes red.
  **De-duplication against device-offline comes for free**: when a device read fails, `driver.Read` returns an error and no records are produced at all, so points are never reported and the state machine freezes in place — no new alarms, no false recoveries, and no extra code. One piece of cleanup **must** ship with it: on device disable/delete, `ClearDeviceAlarm` now clears **the device's own offline alarm plus every quality alarm of its points** in one statement. Without that, collection stops and no signal will ever recover those point alarms, leaving them stuck on "unrecovered" forever. A point alarm's `target_id` is the point itself and cannot be traced back to its device, so this uses the new `alarm.device_id` column (**built into the base migration `007_alarm.sql`, applied automatically on gateway startup — no manual `ALTER` needed**); deleting a single point goes through `ClearPointAlarm`.
  The state machine was **not duplicated**: `alarm.Tracker` (edge detection / debounce / throttling / persistence / notification) treats all three target kinds alike, with the differences confined to the new `alarm.Spec` (`DeviceSpec` / `ChannelSpec` / `PointSpec`: storage type + wording). `notify.BuildTestEvent`'s "test send" preview reads the same Spec — it previously hardcoded the wording in `notify` in parallel with `Tracker`, and the two can no longer disagree. Webhook notification reuses the existing `notify.Dispatcher` (DingTalk / WeCom / Feishu / custom) and only fires on edges; the disconnection-only `GET /alarm/listActive` **filters on `alarm_type='offline'`**, so point quality alarms never leak into the "offline targets" list and `DeviceVO.online` is unaffected. The frontend reuses the same alarm page component with a new `alarm/point` route and menu item.
  Acceptance: `alarm/point_test.go` (cause policy / neutrality does not recover / recovery wording / per-point isolation / no duplicate alarms), `collector/pointreport_test.go` (point name prefers the Chinese label; **every record is forwarded verbatim** — if the collector filtered on the alarm layer's behalf the neutrality semantics would silently break), `service/alarmService_test.go` (clearing a device also clears its points without touching other devices, clearing a channel does not touch points, point alarms stay out of the offline list), and `notify/formatter_test.go` (five wording cases pinned item by item). The full `go test -p 1 ./...` suite passes.

### Changed

- **采集质量成因并入 `Quality` 一个字段：`ReadResult.QualityCause` 被删掉**。上一版为把「地址不存在」与「这轮通信失败」分开而新增了一维字符串 `QualityCause`（`address`/`comms`/`parse`，不变量 `Quality==192` 时恒为空串），它与 `Quality` 合起来只表达 6 个状态，却要各自穿过驱动 → 线协议 → 采集记录 → 实时快照 → VO → MQTT/TDengine/InfluxDB → 前端共 8 层，而那条非法组合（`192` 配一个非空成因）只能靠九个驱动各自的测试去守。现在成因并进 `Quality` 的低 6 位，**非法组合从"要靠测试守"变成"构造不出来"**。
  编码沿袭既有的 192/128/0：高 2 位是类别、低 6 位是子码（因此子码必须 < 64）——`QualityGood=192` 正常、`QualityUncertain=128` 不确定但值可用（ABB 的仿真信号）、`QualityBad=0` 坏但未归类（认不出来的设备状态码、预算耗尽被延迟的点位，**0 的原义完整保留**，驱动预填骨架仍是它）、`QualityBadAddress=1` 坏·地址级、`QualityBadComms=2` 坏·通信级、`QualityBadParse=3` 坏·解析级。新增谓词 `driver.QualityUsable(q)` 供"这个值可不可用"的判定使用。
  **`Quality==0` 不再等于"坏"** —— 这是本次唯一需要下游改代码的地方：MQTT 订阅方、InfluxDB 查询里凡是用 `quality == 0` 判坏的全部要改判为 `quality < 128`（`0/1/2/3` 都是坏，`128/192` 可用），不改的症状是**静默漏掉全部坏点位**（不是报错）。**好点位的报文字节不变**：MQTT 的 `qualityCause` 本来就靠 `omitempty` 省掉、InfluxDB 只在非空时写出，两处的正常点位行与引入成因那一维之前逐字节一致（回归测试用原始字节钉住）。
  ⚠️ **两处必须同批发布的破坏性变更**：① **插件 `APIVersion` 3 → 4**（载荷是位置式二进制、解码端 `Done()` 强制精确消费字节，新旧两版无法互相解读），**升级网关后必须重新编译全部 9 个插件**，否则握手期就以「APIVersion 不匹配」拒绝加载 —— 帧魔数仍为 `IGP2`；② **已部署实例的 TDengine 超级表必须手工删列**（新装实例无需，建表即不带该列）：`ALTER STABLE {db}.{stable} DROP COLUMN quality_cause;`。不执行的话 `CREATE STABLE IF NOT EXISTS` 不会自动删列，位置式 INSERT 便与旧表列数不符 → 写入持续失败，而 SQL 报错在 `push/drain.go` 里被判为**毒批次**（删除并记 dropped）——**静默、永久的数据丢失**，不是响亮停摆。**新增一道护栏**：`ensureSchema` 跑完会 `DESCRIBE` 一次超级表，`quality_cause` 还在就打一条带 ALTER 语句的 ERROR（探测失败只记 WARN、绝不阻断建连 —— 与"只建不改、绝不让通道起不来"同一条理由）；判据收在纯函数 `hasQualityCauseColumn` 里单测，**按列名找 Field 列而不认下标**（DESCRIBE 的列形状因 TDengine 版本而异，认下标会把探测变成一句恒真的空话）。
  **两处隐藏的静默破坏点**，都随本次一起修：① `alarm/threshold.go` 那道「读失败就不判定」的闸写的是 `quality == 0`，坏点位不再恒为 0 之后它不再触发 —— 目前只是"侥幸没事"（坏点位的 `Value` 是空串，会被 `evaluateCondition` 当解析不出来挡下），但那道二次防线会让写错的守卫看起来完全正常，故改为 `!driver.QualityUsable(quality)` 并补 `TestThresholdBadQualityNeverRaises`（四种坏码各配一个**合法的越限值**，让唯一的拦截点只剩那道闸）；② 九个驱动里散落的 `192`/`128` 字面量换成 `driver.QualityGood`/`QualityUncertain`（顺带把 OPC UA 里按 `r.Quality != 0` 判断"值可不可信"的那处改成 `QualityUsable`）。
  驱动侧是机械替换 + 四处守卫逐个核对（形状各不相同，一律替换会改行为）：`markCause`/`markPointsCause`/`setCause`/`setGroupCause` 与 `badCauses`/`planCache.bad` 一并改名换类型（`map[string]string` → `map[string]int`），让词面与事实一致；modbus 的两处「只在仍是未归类时才回填」由 `Quality != 192 && QualityCause == ""` 改写为 `Quality == QualityBad`（副产品：不再会去动 128，属修正）；dlt645 的 `setGroupCause` **保留它无条件覆盖的不对称**；OPC UA 的 `statusCause`→`statusQuality` 对认不出的码返回 `QualityBad`（不猜）；ABB 的三个本地常量删掉、直接用 `driver.Quality*`。**跨轮保持仍是成败处**：四个带计划缓存的驱动把 `bad` 映射一起改成存质量码、逐轮回填，否则"地址不存在"只在 1/N 的轮次可见。
  **一处黄金基线的手工编辑**：`opcua.golden.json` 的 `missing` 条目由 `quality: 0` 改为 `1`。那一点（`ns=1;i=777`）服务器回 `BadNodeIdUnknown`，内置实现在阶段 0 记的是裸 `Quality=0`；同一个事实现在由 `QualityBadAddress=1` 表达 —— **信息相同、编码不同**，故改的是编码而非放宽断言（这是整批黄金里唯一被动过的一条，其余 47 处仍是 192）。基线设计说明里补了一句留痕，免得后来人以为它从未被改过。
  测试：九个驱动的 `degrade_test`/`driver_test` 断言全部改用质量码（含那几张"错误码 → 质量码"的判据表，测试名里的 `Cause` 一并改成 `Quality`）；`driversdk/binary_test.go` 的 `TestBinaryPreservesQualityCause` 换成 `TestBinaryRejectsLegacyPayloadWithCause`（往合法载荷末尾补一个 `0x00` 即得"旧版写出的、成因全为空"的字节流，它必须被 `Done()` 有声地拒绝 —— 这是 `APIVersion 3→4` 在源码层面的守卫）；新增 `TestHasQualityCauseColumn`（8 例，覆盖 TDengine 各版本的 DESCRIBE 形状）、`TestThresholdBadQualityNeverRaises`；`alarm/point_test.go` 的判据表、`collector/pointreport_test.go` 的 `PointStateSink` 测试替身（接口少了一个参数）、`realtime/store_test.go`、mqtt/influxdb/tdengine 三处字节级 pin 全部同步。每个新断言都做过反证（把 `point.go` 的 `QualityBadAddress` 改成 `QualityBadComms`、把阈值守卫改回 `quality == 0`、把 TDengine 探测改成认下标、把线协议的成因字段加回去，逐一确认测试变红）。前端实时页的质量列改由质量码映射文案（1/2/3 出「地址无效」/「通信失败」/「解析失败」，`0` 与 `128` 仍回落显示原始数字 —— 不把"未知"伪装成某个具体原因），i18n key 由 `qualityCause*` 改名 `qualityBad*`，`npm run build` 后按变化文件同步进 `backend/web/dist`。
  **Merge the quality cause into the single `Quality` field: `ReadResult.QualityCause` is gone.** The previous release added a string dimension, `QualityCause` (`address`/`comms`/`parse`, with the invariant "always empty when `Quality==192`"), to tell "this address does not exist" apart from "this round's comms failed". Together the two fields expressed only six states, yet each had to travel through eight layers (driver → plugin wire → collected record → realtime snapshot → VO → MQTT/TDengine/InfluxDB → frontend), and the illegal combination (a `192` carrying a non-empty cause) could only be held in place by nine drivers' tests. The cause now lives in the low six bits of `Quality`, so **the illegal combination goes from "guarded by tests" to "not constructible"**.
  The encoding follows the existing 192/128/0: the top two bits are the class and the low six the sub-code (hence sub-codes must stay under 64). `QualityGood=192` good, `QualityUncertain=128` uncertain but usable (ABB's simulated signal), `QualityBad=0` bad/unclassified (unrecognised device status codes, and points deferred because the degrade budget ran out — **0 keeps its original meaning**, and it is still what the drivers' prefill skeleton carries), `QualityBadAddress=1` bad·address, `QualityBadComms=2` bad·comms, `QualityBadParse=3` bad·decode. A new predicate `driver.QualityUsable(q)` serves "is this value usable" checks.
  **`Quality==0` no longer means "bad"** — that is the one place downstream code has to change: any MQTT subscriber or InfluxDB query testing `quality == 0` must switch to `quality < 128` (`0/1/2/3` are all bad, `128/192` are usable). Not changing it means **silently missing every bad point** — not an error. **Good points are byte-for-byte unchanged**: MQTT's `qualityCause` was already dropped by `omitempty` and InfluxDB only emitted it when non-empty, so a good point's line is identical to before that dimension existed (the regression tests pin this on the raw bytes).
  ⚠️ **Two things must ship together or they are hard failures**: (1) **plugin `APIVersion` 3 → 4** (the payload is positional binary and the decoder enforces exact byte consumption via `Done()`, so the two versions cannot read each other) — **every one of the 9 plugins must be rebuilt after upgrading the gateway**, otherwise the handshake rejects it with "APIVersion mismatch"; the frame magic stays `IGP2`. (2) **The TDengine super table on existing deployments needs a manual column drop** (fresh installs need nothing — the table is created without it): `ALTER STABLE {db}.{stable} DROP COLUMN quality_cause;`. Without it, `CREATE STABLE IF NOT EXISTS` will not drop the column, the positional INSERT no longer matches the column count, and the write keeps failing — while a SQL error is classified as a **poison batch** by `push/drain.go` (deleted and counted as dropped), i.e. **silent, permanent data loss** rather than a loud outage. **A new guard** covers this: after `ensureSchema`, the channel runs one `DESCRIBE` and logs an ERROR carrying the ALTER statement when `quality_cause` is still present (a failed probe only logs a WARN and never blocks connecting, for the same reason the schema statement "creates and never alters" so the channel can always come up); the criterion lives in the pure function `hasQualityCauseColumn` so it can be unit-tested, and it locates the `Field` column **by name rather than by index** (DESCRIBE's column shape varies by TDengine version, and index-based lookup would turn the probe into a statement that is always vacuously true).
  **Two hidden silent breakages**, both fixed along the way: (1) the "a failed read is not judged" gate in `alarm/threshold.go` was written as `quality == 0`, which stops firing once bad points are no longer 0 — it was only saved by luck (a bad point's `Value` is an empty string, which `evaluateCondition` rejects as unparseable), and that second line of defence is exactly what makes a wrong guard look perfectly healthy, so it now reads `!driver.QualityUsable(quality)` with a new `TestThresholdBadQualityNeverRaises` (each of the four bad codes paired with a **legitimate over-limit value**, leaving the gate as the only thing standing in the way); (2) the scattered `192`/`128` literals across the nine drivers became `driver.QualityGood`/`QualityUncertain` (and OPC UA's `r.Quality != 0` test for "is this value trustworthy" became `QualityUsable`).
  The driver side is a mechanical rename plus a careful per-shape rewrite of four different guards (a blanket replacement would change behaviour): `markCause`/`markPointsCause`/`setCause`/`setGroupCause` and `badCauses`/`planCache.bad` were renamed and retyped (`map[string]string` → `map[string]int`) so the words match the facts; modbus's two "only fill it while still unclassified" guards became `Quality == QualityBad` (a side effect: they no longer touch 128 — a correction); dlt645's `setGroupCause` **keeps its unconditional-overwrite asymmetry**; OPC UA's `statusCause`→`statusQuality` returns `QualityBad` for unrecognised codes (it does not guess); ABB's three local constants are gone in favour of `driver.Quality*`. **Cross-round persistence is still what makes or breaks this**: the four drivers with a plan cache now store quality codes in their `bad` map and replay them each round, otherwise "this address does not exist" would be visible in only 1/N rounds.
  **One hand-edited golden baseline**: the `missing` entry in `opcua.golden.json` moves from `quality: 0` to `1`. That point (`ns=1;i=777`) gets `BadNodeIdUnknown` from the server, and the built-in implementation recorded a bare `Quality=0` back in stage 0; the same fact is now expressed as `QualityBadAddress=1` — **same information, different encoding**, so this changes the encoding rather than relaxing an assertion (it is the only entry touched in the whole golden set; the other 47 are still 192). A line was added to the baseline's design note so a later reader does not assume it was never edited.
  Tests: every driver's `degrade_test`/`driver_test` assertion now speaks in quality codes (including the "error code → quality code" criterion tables, whose test names were renamed from `Cause` to `Quality`); `driversdk/binary_test.go`'s `TestBinaryPreservesQualityCause` became `TestBinaryRejectsLegacyPayloadWithCause` (append one `0x00` to a valid payload and you have exactly what the old version wrote for an all-empty cause — it must be rejected loudly by `Done()`, which is the source-level guard for the `APIVersion 3→4` bump); `TestHasQualityCauseColumn` (8 cases covering TDengine's various DESCRIBE shapes) and `TestThresholdBadQualityNeverRaises` are new; `alarm/point_test.go`'s criterion table, `collector/pointreport_test.go`'s `PointStateSink` double (the interface lost a parameter), `realtime/store_test.go`, and the three byte-level pins in mqtt/influxdb/tdengine all moved with it. Every new assertion was falsified (flip `point.go`'s `QualityBadAddress` to `QualityBadComms`, revert the threshold guard to `quality == 0`, make the TDengine probe index-based, add the cause field back to the wire protocol — each confirmed red). The frontend realtime page now maps quality codes to wording (1/2/3 render "Bad address"/"Comm failed"/"Decode failed", while `0` and `128` still fall back to the raw number — "unknown" is not disguised as a specific reason), the i18n keys were renamed from `qualityCause*` to `qualityBad*`, and after `npm run build` the changed files were synced into `backend/web/dist`.
